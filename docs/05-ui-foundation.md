# 화면 기반 (UI Foundation)

> 상태: 초안 v0.2 / 최종 수정 2026-07-27
> 2단계(웹페이지 구축) 문서. 착수 전에 쓰고 구현하며 밝혀진 사실을 반영했다. **1단계에서 적재한 데이터를 어떤 화면으로 내보내는가**를 정의한다.
> 서빙 형식·계산 위치·웹 프레임워크는 [`adr/05-web-serving.md`](adr/05-web-serving.md)에서 정한다.
> 이 문서의 수치는 1단계 적재 결과(`data/coverage.json` · 2026-07-25 스냅샷)와 선행 문서의 실측값이다.

## 1. 이 단계의 범위

`00-product.md` 6절의 2단계 성공 기준은 **"구축된 데이터 전체를 웹에서 조회·검색할 수 있다"** 이다.
따라서 대상은 제품 구조의 [1] 정보 제공 하나이며, [2] 런 상태 입력과 [3] 추천은 각각 4단계와 3단계다.

| 구분 | 내용 |
| --- | --- |
| 범위 | 51개 테이블 50,577행의 조회·검색, 로케일 전환, 출처 고지. 3단계가 더한 `gift_token` 은 엔진 입력이라 조회 대상이 아니다 |
| 범위 밖 | 런 상태 입력, 추천 점수·근거, 플레이 기록, 로그인, 데이터 갱신 UI |

**화면 구조는 [2]와 [3]이 뒤에 붙을 자리를 남긴다.** 4.5의 층별 등장 팩 화면이 그 접점이다.
난이도와 층을 골라 후보 팩을 보는 흐름은 4단계 런 상태 입력의 전신이며, 여기에 파티 구성과
보유 기프트가 더해지면 추천 화면이 된다. 2단계에서는 데이터가 그대로 나열되고, 이후 단계에서 순서가 점수로 바뀐다.

## 4. 화면별 정의

### 4.1 기프트

정보 제공의 중심 엔티티이며(`02-data-model.md` 3.5) 검색 빈도가 가장 높을 화면이다.

| 필터 축 | 값 | 주의 |
| --- | --- | --- |
| 등급 | 1–5 · EX | |
| 연관 키워드 | 10종 (상태 7 + 공격 타입 3) | **키워드 없는 기프트가 120종이다.** "없음"을 축의 값으로 둔다 |
| 강화 가능 | 참 / 거짓 | |
| hard 전용 | 참 / 거짓 | |
| MD 코스트 | 수치 구간 | 441/456만 값을 갖는다. 15종은 비어 있다 |
| 팩 소속 | 전용 / 범용 | **범용 226종은 결손이 아니다**(`02-data-model.md` 3.5) |

상세에 담는 것:

- **강화 단계 전환** — 0 / + / ++ 로 이름과 설명이 함께 바뀐다. 단계별로 별도 행이며 같은 기프트로 묶어 표시한다.
- **합성 레시피** — 슬롯 단위로 표시한다. 한 슬롯은 `count`개를 `options` 중에서 채우는 구조이므로
  재료 목록을 평탄하게 늘어놓으면 대체 관계가 사라진다.
- **이 기프트가 재료로 쓰이는 레시피** — 역방향 조회. 132종이 재료로 쓰인다.
- **등장 팩** — 기프트당 median 2 · 평균 22.9 · **최대 90**(`adr/01-data-storage.md` 3.1).
- **전용 팩** — 등장 팩과 구분해 먼저 표시한다.

### 4.2 테마 팩

**이 화면의 설계 문제는 밀도다.** 팩 하나에 딸린 기프트가 팩당 median 73 · 최대 188이다.

| 필터 축 | 값 |
| --- | --- |
| 분류 | `canto` · `event` · `extreme` 등 |
| 변형 | `normal` 등 |
| 중첩 · 극한 | 참 / 거짓 |
| 등장 층 | 난이도별 구간 |
| 전용 기프트 보유 | 117종 중 71종이 갖는다 |

상세의 기프트 목록은 세 단으로 나눈다.

1. **전용 기프트** — 이 팩에서만 나오는 것. 팩을 고를 이유에 해당하므로 맨 위에 둔다.
2. **전체 풀 요약** — 등급·키워드·죄악 축의 분포. 188개를 읽지 않고도 팩의 성격을 판단할 수 있어야 한다.
3. **전체 목록** — 접은 상태로 두고 목록 화면과 같은 필터를 적용할 수 있게 한다.

**층 정보가 없는 팩이 21종 있다**(20종 `extreme`, 1종 이벤트). 결손이 아니라 일반 층 순환에
등장하지 않는다는 뜻이므로 그렇게 표기한다(`02-data-model.md` 3.7).

**기프트 등장 확률은 표시하지 않는다.** 팩별 기프트 목록은 확보했으나 확률은 어느 출처에도 없다
(`02-data-model.md` 8절). 이 화면은 "이 기프트가 이 팩에서 나온다"까지만 말한다.

**보스전은 조우 이름이 아니라 등장 적을 낸다.** 구현 중 대조하니 팩당 조우가 정확히 하나이고
**조우 이름이 팩 이름과 같다**(실측 75/75). 이름을 내면 제목이 두 번 나올 뿐이다.
담을 값은 조우에 등장하는 적이며 그것은 팩 데이터에 없다. 등장 수가 원본에 없는 경우가 있고
그때 1로 지어내지 않는다.

### 4.3 인격

| 필터 축 | 값 | 주의 |
| --- | --- | --- |
| 수감자 | 12 | |
| 등급 | 1–3 (게임 표기 0 / 00 / 000) | 게임 표기로 노출한다 |
| 시즌 · 출시일 | | |
| 소속 | 93 | **필터 키는 원본 영문 태그이고 표시만 로케일 행에서 온다**(`adr/03-localized-text.md` 5절) |
| 스킬 죄악 속성 | 7종 + 없음 | **죄악이 없는 스킬이 131건 있다.** 패닉·조건부 스킬이 해당한다 |
| 스킬 공격 타입 | 3종 | |
| 보유 상태 | | |

상세에 담는 것:

- **스킬** — S1 / S2 / S3 / 방어 / E.G.O 슬롯. 덱 매수(`deckCount`)는 코인 수가 아니다.
- **방어 스킬을 공격 스킬과 같은 깊이로 기본 표시한다.** 836종 중 216종이 방어이며
  (`guard` 90 · `counter` 78 · `evade` 48) 동기화 단계·코인·수치·설명을 공격 스킬과
  똑같이 갖는다. 접어두거나 요약하지 않는다.
- **동기화 전환** — 1–4단계. 수치·설명·코인이 단계마다 다르다. 적재된 값은 델타가 아니라 병합된 최종값이다.
- **코인** — **개수에 상한을 두지 않는다.** 실측 최대 9개이므로 고정 슬롯 UI를 쓰지 않는다.
- **스탯** — `hp`는 스칼라가 아니라 `hpBase`와 `hpPerLevel`의 쌍이다. 단일 수치로 표시하려면 레벨 입력이 필요하다.
- **스태거 구간** — `breakSection`의 **길이가 인격마다 다르다**(실측 1개 32 · 2개 67 · 3개 85). 고정 3구간을 가정하지 않는다.
- **속도** — 동기화 단계별 최소–최대 쌍.
- **저항** — **공격 타입 3종이 축이다.**
- **패시브** — 전투/지원 구분과 해금 동기화 단계, 발동 조건의 요구치.

**인격을 서술하는 축은 셋이다** — 키워드 · 소속 · 상태 기믹(탄환·보호). 셋은 성격이 다르므로
화면에서 섞지 않고 나란한 독립 구획으로 둔다. 상태 기믹은 아직 담을 자리가 없다
([`backlog/04`](backlog/04-status-mechanics.md)).

**E.G.O 엔티티는 인격 상세에 담지 않는다.** E.G.O는 인격이 아니라 **수감자**에 붙는다(`Ego.sinnerId`).
인격 184종이 수감자 12명에 나뉘므로 인격 상세마다 E.G.O를 실으면 수감자당 평균 9.2종이
같은 수감자의 인격 15개 상세에 그대로 반복된다. 인격 상세에서는 4.4의 목록으로
수감자 필터를 걸어 링크하고, 둘을 함께 보는 자리는 4.6에 둔다.

### 4.4 E.G.O

| 필터 축 | 값 | 주의 |
| --- | --- | --- |
| 수감자 | 12 | |
| 등급 | ZAYIN · TETH · HE · WAW · ALEPH | **ALEPH은 실측 0종이지만 축에서 빼지 않는다.** 출시 시점에 화면이 깨진다 |
| 각성 죄악 · 공격 타입 | 7 · 3 | |
| 침식 | 있음 / 없음 | 침식이 없는 E.G.O가 12종이다 |
| 추출 가능 | 참 / 거짓 | |
| 죄악 자원 소모 | 속성별 수량 | |

**저항의 축이 인격과 다르다.** E.G.O는 죄악 7종, 인격은 공격 타입 3종이다.
두 화면에서 같은 저항 컴포넌트를 재사용하면 축이 어긋난다.

`cost`는 E.G.O 기능의 핵심이므로 상세에서 죄악별 수량을 그대로 보여준다.
팀의 죄악 공급과 대응해 읽는 화면은 3단계 이후의 대상이다(`02-data-model.md` 3.4).

### 4.5 층별 등장 팩

난이도와 층을 고르면 그 구간에 등장하는 팩 목록이 나온다.
구간은 hard가 1 · 2 · 3 · 4 · 5 · 6–10 · 11–15이고 normal이 1–5다.

거울 던전은 전체 15층 · 기본 5층이며 후반 층일수록 상위 등급 팩이 배정된다.
이 화면은 1절이 말한 이후 단계의 접점이며, 2단계에서는 순서 없는 목록으로 둔다.

### 4.6 편성

수감자 12명을 축으로 그 인격과 E.G.O를 나란히 둔다.

**이 화면이 필요한 이유는 E.G.O가 인격이 아니라 수감자에 붙기 때문이다.** 4.3이 E.G.O를
인격 상세에서 뺐으므로 둘을 함께 보는 자리가 따로 있어야 한다. 수감자당 인격 평균 15.3종,
E.G.O 평균 9.2종이다.

배치는 이전 프로토타입(`limbus-mirror-tracker-v1`)의 SQUAD 탭과 같은 축이다.
**다만 고르는 흐름은 없다.** 슬롯에 인격과 E.G.O를 담는 편집은 4단계 런 상태 입력의 몫이며
(1절), 2단계에서는 조회만 한다. 이 화면도 4.5와 함께 이후 단계의 접점이다.

### 4.7 용어 조회

상태 1,472종은 인격·E.G.O 상세에서 참조되며 독립 조회도 필요하다.
`buffType` 실측 분포는 Positive 678 · Neutral 416 · Negative 378이다.

**상태 판정은 이름 매칭이 아니라 메타데이터로 한다**(`02-data-model.md` 3.10). 화면의 그룹핑도 같다.

## 5. 검색

| 항목 | 결정 |
| --- | --- |
| 대상 | 엔티티 이름 전체와 설명문 |
| 대상 문자열 | **치환된 표시용 `desc`를 쓴다.** `descRaw`는 검색 대상이 아니다 |
| 진입 | 홈의 통합 검색과 각 목록 화면의 범위 내 검색 |
| 필터와의 관계 | 검색어와 필터는 AND로 결합한다 |

`descRaw`를 제외하는 근거는 사용자가 입력하는 것이 표시 문자열이기 때문이다.
원문에는 내부 식별자와 `<noparse>` 마커가 남아 있어(`adr/03-localized-text.md` 3.3) 검색어와 대응하지 않는다.
기계적 해석에 원문이 유리하다는 판단은 3단계 엔진의 것이지 검색의 것이 아니다.

**표시 문자열이 전체 산출물의 79%인 7,498 KB다**(`adr/03-localized-text.md` 1절).
설명문 검색을 어디서 수행하는가는 서빙 형식 결정의 주요 입력이며, 이 문서는 요구만 정하고 결정은 ADR로 넘긴다(9절).

### 6.1 결손과 부재의 구분

**없는 값을 0이나 빈 문자열로 지어내지 않는다**(`02-data-model.md` 6절). 화면은 두 가지를 다르게 표기한다.

**결손 — 데이터에 있어야 하는데 없는 것.** 명시적으로 표기한다.

아래는 변환기 리포트(`npm run convert`의 확인 항목)와 `data/coverage.json`의 실측이다.

| 항목 | 규모 |
| --- | ---: |
| 소속 한국어 없음 (영문 노출) | 7/93 |
| 상태 이름 원본 결손 | 7종 |
| 스킬 이름 한국어 없음 (영문 노출) | 3종 8행 |
| 스킬 이름이 어느 출처에도 없음 | 3종 — 동기화 1단계 |
| 코인 설명 한국어 없음 (영문 노출) | 3종 18행 |
| 스킬 수치가 어느 출처에도 없음 | 6종 — 분류만 적재했다 |
| 스킬 아이콘 | 13종 (7절) |

**앞의 셋과 뒤의 셋은 성격이 다르다.** 영문이 노출되는 항목은 표시할 문자열이 있고 언어만 다르며,
어느 출처에도 없는 항목은 표시할 값 자체가 없다. 화면에서 같은 기호를 쓰지 않는다.

**부재 — 없는 것이 정상인 것.** 결손으로 표기하지 않는다.

| 항목 | 규모 |
| --- | ---: |
| 전용 팩 없음 (범용 기프트) | 226종 |
| 연관 키워드 없음 | 120종 |
| 침식 없음 (E.G.O) | 12종 |
| 층 배정 없음 (팩) | 21종 |
| 설명 없는 코인 | 918행 — 효과가 없는 코인이다 |
| 아이콘 없는 상태 | 254종 — 수치 변화형이라 게임에도 아이콘이 없다 |

두 부류를 같은 기호로 표시하면 사용자가 데이터의 신뢰도를 잘못 판단한다.

## 7. 이미지 애셋

**이미지 애셋을 화면의 1급 요소로 사용한다.** `01-data-source.md` 8절과 `02-data-model.md` 8절의
미결 항목을 사용으로 정한다. 동종 팬 사이트가 같은 방식으로 운영되고 있는 것을 근거로 삼는다.

애셋은 네 엔티티 전부를 100% 덮으므로 목록·상세 어디서도 이미지가 비는 칸이 생기지 않는다.
아이콘을 축소해 쓰지 않고 엔티티를 식별하는 주 수단으로 노출한다.

| 화면 | 노출 |
| --- | --- |
| 목록 (기프트 · 팩) | 아이콘을 1급 요소로 둔 격자 |
| 목록 (인격 · E.G.O) | 프로필 이미지를 동반한 행 |
| 인격 상세 | 각성 전후 프로필과 전신 (184종 전부 보유, 712파일) |
| E.G.O 상세 | 각성 프로필 · CG · 침식 프로필 (CG 110 · 침식 98) |
| 스킬 · 상태 | 아이콘을 설명문 앞에 둔다 |

| 대상 | 파일 | 커버리지 | 매칭 키 |
| --- | ---: | --- | --- |
| 인격 | 712 | 184/184 | id |
| E.G.O | 318 | 110/110 | id |
| 기프트 | 476 | **456/456** | `sprite` — **id로 추정해 찾으면 안 된다** |
| 테마 팩 | 154 | 117/117 | `sprite` |
| 스킬 아이콘 | 984 | 824/837 | id |
| 상태 | 1,192 | 아이콘을 가진 상태 전수 | `sprite` |

기프트와 팩의 애셋 파일명은 id가 아니라 게임 내부 스프라이트 키다. 456종 중 `srcPath`가 숫자인 것은
75종뿐이며, id로 매칭하면 대부분 실패한다(`04-data-inventory.md` 7절).

### 7.1 제약

1. **애셋을 저장소에 커밋하지 않는다**(`01-data-source.md` 7절). `npm run fetch -- --assets`로 받아
   빌드 시점에 배치한다. 클론 직후에는 이미지가 없으므로 이 단계가 실행 절차에 들어간다.
2. **애셋 경로 해석을 한 모듈에 모은다.** 엔티티마다 매칭 키가 다르고(위 표) 기프트·팩은
   id로 추정하면 실패한다. 규칙이 화면마다 흩어지면 패치 때 갱신 지점을 놓친다.
3. **아이콘이 없는 항목에는 대체 표시가 필요하다.** 이미지 정책이 아니라 원본의 결손이다.
   - 인격 스킬 13종 — 대부분 이름 없는 반격·조건부 발동 스킬이다. 게임에서 기본 아이콘을
     공유하는 것으로 보이나 확정되지 않았다(`04-data-inventory.md` 7절).
     **프레임이 대체 표시가 된다**(아래).
   - 상태 254종 — 수치 변화형이라 게임에도 아이콘이 없다. 결손이 아니므로 텍스트로만 표시한다.

### 7.2 스킬 프레임

**`skill.tier`는 표시용 숫자이면서 애셋을 고르는 키다.** 스킬 아이콘 뒤에 프레임을 깔며,
파일이 `{죄악}-{1|2|3}.webp`와 배경 `-bg` 짝이고 방어 스킬은 `def` 하나다(실측 44개).

이 구조 덕분에 **아이콘이 없는 12종에서도 죄악과 등급이 읽힌다.** 프레임이 곧 대체 표시이며
별도 대체 아이콘을 만들 필요가 없다. 이전 프로토타입도 같은 구조였다.

`tier`가 4인 스킬이 1건 있으나 프레임은 3까지다. 넘치면 가장 높은 것을 쓴다.
죄악이 없는 스킬 131건과 방어 스킬은 `def`를 쓴다.

## 8. 디자인 기반

**게임 세계관 톤을 따른다.** 다만 두 제약이 톤보다 우선한다.

1. **표기는 게임 내 표기와 1:1로 대응한다**(`00-product.md` 3절). 자체 용어를 만들지 않는다.
   등급을 1–3이 아니라 0 / 00 / 000으로 쓰는 것이 그 예다.
2. **밀도가 장식보다 우선한다.** 팩 상세의 기프트 188개, 인격 상세의 스킬 × 동기화 4단계 × 코인 최대 9개는
   장식적 여백을 감당하지 못한다. 세계관 톤은 색·타이포·질감에서 구현하고 정보 밀도에서 양보받지 않는다.

| 항목 | 기준 |
| --- | --- |
| 색 축 | 죄악 7종 · 공격 타입 3종 · 등급처럼 게임이 고유 표기를 갖는 축은 게임 표기를 따른다 |
| 접근성 | **색만으로 구분하지 않는다.** 죄악 7종과 상태 키워드 7종은 색 단독으로 판별되지 않는다 |
| 반응형 | 모바일을 지원한다. 4단계의 층당 15초 목표가 플레이 중 참조를 전제한다 |
| 토큰 | 색·간격·타이포를 토큰으로 정의한다. 구체 값은 구현 시점에 정한다 |

## 10. 출처 표기와 고지

`01-data-source.md` 7절이 요구하는 표시 항목이다. 모든 화면에서 접근 가능한 위치에 둔다.

| 항목 | 내용 |
| --- | --- |
| 2차 창작물 표시 | 비공식 팬 프로젝트이며 Project Moon과 제휴·승인 관계가 없다 |
| 출처 크레딧 | 데이터 출처 저장소 목록 |
| 기준 버전 | `Dataset` 테이블의 게임 버전 · 거울 던전 버전 · 스냅샷 일자 |

거울 던전 버전은 내부 키 `MD7`이고 표시 명칭은 **이름과 거미의 거울**(영문 `Mirror of Names and Spiders`)이다.
화면에는 명칭을 쓰고 내부 키를 노출하지 않는다.
| 권리 고지 | 게임 데이터·텍스트·이미지의 권리는 Project Moon에 있다 |

**기준 버전은 `/about`에만 두지 않는다.** 데이터가 특정 스냅샷의 것이므로 조회 화면에서도 확인 가능해야 한다.
