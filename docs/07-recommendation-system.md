## 1. 이 단계의 범위

`00-product.md` 6절의 4단계 성공 기준은 **"사용자가 자신의 런 상황을 입력하고 추천과 근거를
받는 흐름이 층당 15초 이내에 끝난다"** 이다. 15초는 잠정 기준이며 이 문서가 재검토 대상으로 받는다.

| 구분 | 내용 |
| --- | --- |
| 범위 | 편성 편집 · 런 진행 추적 · 후보 팩 제시와 근거 · 획득 기프트 기록 · 덱 코드 입출력 |
| 범위 밖 | 추천 알고리즘 변경(엔진) · 인격·E.G.O 메카닉 저작(데이터) · 플레이 기록 서버 수집(이후 버전) |

**엔진과 시스템을 구분한다**(`00-product.md` 5절). 이 단계는 흐름을 만든다.
추천 결과의 타당성은 이 단계의 성공 기준이 아니다 — 흐름이 끝까지 도는 것이 기준이다.
결과 개선은 엔진 쪽에서 병행한다(9절).

## 2. 지켜야 할 것

1. **엔진 인터페이스를 건드리지 않는다.** `rankPacks` · `scoreState` · `marginalValue` ·
   `contextOf` · `deckFeature` 의 시그니처와 반환 타입은 이 단계에서 불변이다.
2. **같은 사실을 두 곳에 두지 않는다.** 보유 기프트는 저장하지 않고 층 이력에서 유도한다.
3. **결손을 지어내지 않는다**(`02-data-model.md` 6절). 저장 실패 · 스키마 불일치 ·
   참조 결손을 조용히 넘기지 않고 화면에 표기한다.
4. **편성과 출전을 구분한다.** 엔진이 이미 구분하므로(`06` 2절 4항) 입력도 구분해서 받는다.
5. **계산은 서버에서 한다**(`adr/05-web-serving.md` 3.3). 표시 문자열 7,498 KB를 내보내지 않는다.
6. **기록의 완전성을 파생 기능 유무로 깎지 않는다.** 편성은 게임의 실제 편성을 그대로 담는다.

## 4. 저장 모델

브라우저에 둔다. 서버 수집은 이후 버전이다(`00-product.md` 5절).

키를 셋으로 나눈다. 수명이 다르기 때문이다 — 덱은 오래 살고, 런은 한 번 돌고 버려진다.

```ts
// limbus:schema → 1
// limbus:decks  → StoredDeck[]   최대 10
interface StoredDeck {
  id: string;                       // crypto.randomUUID
  name: string;
  slots: Array<{                    // 항상 길이 12, 수감자 순서 고정
    sinnerId: number;               // 1..12
    identityId: number | null;
    egos: Partial<Record<EgoRank, number>>;   // 등급 → egoId
  }>;
  order: number[];                  // 편성 순서 sinnerId, 최대 12 — 덱 코드가 담는 것
  deployed: number[];               // 출전 sinnerId, 최대 7 — 덱 코드에 없다
  updatedAt: string;                // ISO
}

// limbus:run → StoredRun | null   진행 중인 런 하나
interface StoredRun {
  deckId: string;
  difficulty: 'normal' | 'hard';
  floors: Array<{
    floor: number;                  // 1..15
    pickedPackId: string | null;    // 아직 안 고른 층은 null
    gainedGiftIds: number[];
  }>;
  startedAt: string;
}
```

### 4.1 왜 이 모양인가

**슬롯은 수감자 12 고정 배열이다.** 거울 던전 편성이 수감자당 인격 1이고 `/squad` 가 이미 그 축이다.
배열 인덱스가 곧 수감자라 정렬·비교가 필요 없고, 한 수감자에 인격 둘이 들어가는 상태를 만들 수 없다.

**`deployed` 는 인격 id 가 아니라 수감자 id 를 담는다.** 인격을 바꿔도 출전 지정이 유지된다.

**편성 순서와 출전은 다른 것이며 필드도 다르다.** 한동안 `deployed` 하나가 둘을 겸했는데
(「출전 수감자 id. 순서가 곧 편성 순서다」) 실물 덱 코드가 그 설계를 무너뜨렸다 — 코드의
편성 순서 필드는 1..12 의 순열로 나오고, 그것을 출전으로 읽으면 12명이 되어 상한 7을 넘는다.
`order` 는 덱 코드가 담는 것이고 `deployed` 는 사용자가 화면에서 고르는 것이다(7.1).

**스키마 버전은 아직 올리지 않는다.** 이 모양은 정립 중이고 실사용자가 없다. 정립되지 않은
것에 계약 번호를 붙이면 되돌릴 마이그레이션만 쌓인다. 버전 관리는 모양이 굳고 저장분이
남의 것이 되는 시점 — 배포 — 부터 시작한다. 그때까지 예전 모양의 저장분은 `parseDeck` 이
사유와 함께 거부하고, 개발자가 직접 지운다.

**`egos` 는 등급 키 레코드다.** 편성에서 E.G.O 는 **등급마다 한 자리**이며, 레코드로 두면
그 제약이 타입으로 강제되어 위반이 표현 불가능해진다.

이것은 **장착 슬롯의 제약이지 보유의 제약이 아니다.** 수감자는 같은 등급 E.G.O 를 여럿 갖는다
— 실측 등급 분포는 수감자당 ZAYIN 1~2 · TETH 2~4 · HE 3~5 · WAW 1~2 이며, 그중 하나를 그 등급
자리에 올리는 것이다. 덱 코드가 등급마다 필드를 하나씩 두는 것도 같은 구조다(7절).

ALEPH 키는 항상 비어 있다. 슬롯과 개념은 게임에 존재하지만 해당 등급 E.G.O 가 아직 출시되지
않았고, 우리 데이터의 **ALEPH 0** 이 그것과 일치한다. **이것은 결손이 아니라 부재다.**

**보유 기프트를 저장하지 않는다.** `floors.flatMap(f => f.gainedGiftIds)` 로 유도한다.
이력과 보유가 어긋날 수 없게 하려는 것이다.

**층을 배열로 쌓는다.** 현재 상태만 두는 것보다 배열 하나가 늘 뿐인데 셋을 얻는다 —
마지막 층 되돌리기, 층별 복기, 그리고 `00-product.md` 4절이 피드백 루프의 입력으로 명시한
*"종료된 런의 결과와 실제 선택"* 이 이 구조 그대로다. 이후 버전에서 서버로 올릴 때 모양을 새로 짜지 않는다.

### 4.2 스키마 버전

`limbus:schema` 에 정수 하나를 둔다. 읽을 때 값이 다르면 **버리지 않고** 읽기 실패로 표기하고
사용자에게 알린다. 저장분을 조용히 폐기하지 않는다.

**저장소 계층이 지키는 것만으로는 부족하다 — 화면이 덮는다.** 실측으로 재현했다. 버전 0 으로
저장된 덱 셋이 있는 상태에서 `readDecks` 가 실패하면 화면의 `decks` 는 빈 배열인데, 그대로
「새 덱」을 누르면 `writeDecks` 가 `limbus:decks` 를 통째로 덮는다.

```
저장분 있음: [{"id":"a"},{"id":"b"},{"id":"c"}]
readDecks: 실패 — 저장분의 스키마 버전(0)이 현재(1)와 다르다
화면 decks: 0 개
클릭 후 저장분: [{"id":"new", ...}]     ← a·b·c 가 사라졌다
```

그래서 `DeckEditor` 가 읽기 실패 시 `locked` 로 **쓰기 자체를 막는다.** 「새 덱」·「삭제」는
비활성이고, 편집·가져오기가 `persist` 에 닿아도 잠금 사유를 배너로 돌려줄 뿐 쓰지 않는다.
`lib/storage/decks.test.ts` 의 「읽기가 실패해도 저장분을 건드리지 않는다」가 잠금이 지키는
소실 경로를 함께 고정한다.

## 5. 흐름

### 5.1 편성

```
덱 목록 (최대 10)   [새 덱] [복제] [삭제] [덱 코드 ⇄]
선택된 덱
  수감자 12 그리드 — 칸마다
    [인격 ▾]                        그 수감자의 인격만 (수감자당 14~16종)
    ZAYIN [▾] TETH [▾] HE [▾] WAW [▾] ALEPH [—]
    ☐ 출전                          최대 7
```

E.G.O 슬롯에는 **현재 추천 점수에 반영되지 않음**을 표기한다. 반영은 엔진 쪽 작업이다(9절).
표기 없이 두면 "입력했는데 왜 반영이 안 되나" 가 된다.

### 5.2 런 추적

```
런 없음 →  [덱 고르기] [난이도] → 런 시작

런 있음 →  현재 층
           후보 팩 그리드 — 그 난이도·층에서 등장 가능한 팩 전부
             상위 1~3 하이라이트 · 카드마다 점수와 [근거 펼치기]
             제외된 팩은 이유와 함께 별도 표기
           [이 팩 선택]
             → 획득 기프트 모달
                 한정 섹션 / 공용 섹션 분리
                 그 팩에서 등장 가능한 기프트 전부 나열
                 이미 획득분은 시각 구분 + 재선택 불가
                 멀티 선택 → [획득]
             → 층 +1
           하단: 층 이력 · [마지막 층 되돌리기] · [런 종료]
```

**제시받은 팩을 따로 입력받지 않는다.** 등장 가능한 팩 전부를 보이고 상위를 하이라이트한다.
입력 단계를 하나 줄이는 선택이며, 15초 기준에 직접 기여한다.

모달을 한정/공용으로 나누는 이유는 획득 경로가 다르기 때문이다. 팩 한정 기프트는 그 팩에서만
나오고(헬스 치킨의 닭다리·닭가슴살, 시간 살인 시간의 시계침 등), 그중에는 재료를 그 팩에서만
얻는 것도 있다. 실측으로 팩당 기프트 **평균 86.5종**(117팩, 18~188)이고, 전용 기프트는
**71팩이 갖고 있으며 그 71팩 기준 평균 4.5종**(1~17)이다. **46팩은 전용 기프트가 없다** —
그 팩의 모달은 공용 섹션만 갖는다.

## 6. 데이터 흐름

```
브라우저                            서버
 StoredDeck ─┐
 StoredRun  ─┴→ recommendAction({ deck, deployed, floor, difficulty, owned })
                      │  'use server'
                      └→ recommendForDeck()          기존 함수
                            loadIdentities · loadGifts · packIdsForFloor
                            loadPackCandidates · rankPacks
                 ←─── { ranked, dropped, feature, candidates }

 POST /api/recommend  ← 같은 함수에 위임. curl 검증 전용 이음새
```

호출 시점은 **상태가 바뀔 때만**이다 — 런 시작 · 층 이동 · 기프트 획득 · 되돌리기.

Server Action 을 주 경로로 둔다. 공개 API 표면이 생기지 않고 타입이 양쪽으로 이어진다.
다만 액션 ID 가 불투명해 curl 로 직접 칠 수 없으므로, 같은 함수에 위임하는 Route Handler 를
얇게 둬서 화면을 거치지 않고 계약을 확인할 수 있게 한다.

`recommendForDeck` 이 `deck` 과 `deployed` 를 나눠 받는다(`options.deployedIds`). `RunState` 가
이미 구분하므로 **엔진 변경이 아니라 호출부 정정**이었다. 인격을 다시 질의하지 않고 이미 받아 온
`deck` 에서 골라 낸다. 비우면 편성 전체를 출전으로 보므로 이전과 동작이 같다.

이 한 줄에 엔진 브랜치(`feat/engine-deck-feature`)의 소속 조건 판정 범위 작업이 달려 있다.
호출부가 `deployed: deck` 으로 두는 한 둘이 같은 값이라 **점수가 움직이지 않아 그쪽 작업이
관측되지 않는다.**

추천 슬라이스가 `?deployed=` 로 이를 열어 둔다 — 화면이 편성을 입력받는 흐름은 5.2(계획 B)의
몫이고, 여기서는 구분이 실제로 갈리는지 확인할 수 있게만 한다. 소속 패널이 어느 범위로 셌는지
(`출전 n/12`) 함께 표기한다.

## 7. 덱 코드

인게임 편성 코드를 우리 편성으로 가져오고, 우리 편성을 인게임에 넣을 수 있게 한다.

### 7.0 이 절의 근거는 외부 가이드다

파이프라인의 다른 값과 달리 **이 절의 형식과 비트 배치는 우리가 원본에서 뽑은 것이 아니다.**
커뮤니티 가이드 하나를 옮긴 것이며, 그 가이드 자체가 일부를 추정으로 적어뒀다.

| 저장소 기록 | **아직 없음** — `docs/reference/` 에 발췌를 남기고 이 표에 파일명·확인 날짜를 적는다 |
| 신뢰도 | 형식과 파이프라인은 왕복으로 확인 가능. **비트 배치는 실물 코드 없이는 확인 불가** |

**출처를 저장소에 남기기 전에는 7.1의 배치를 검증할 방법이 없다.** 이 절을 읽는 사람이
대조할 대상이 있어야 한다.

### 7.1 형식

```
디코드   base64 decode → gzip decompress → base64 decode → bits
인코드   bits → bytes → base64 encode → gzip compress → base64 encode
```

560비트 = 수감자당 46비트 × 12 + 더미 8비트. 가이드가 적은 수감자 블록의 배치는 다음과 같다.

| 비트 (블록 내 1-기준) | 내용 |
| --- | --- |
| 5–8 | 인격 — 캐릭터 내 출시 순서 |
| 9–12 | **편성 순서** (편성하지 않으면 0) |
| 16–19 | ZAYIN E.G.O |
| 23–26 · 30–33 · 37–40 | TETH · HE · WAW E.G.O (미편성 0) |
| (41–46) | ALEPH E.G.O — 가이드의 **추정** |

**가이드가 지정하지 않은 자리가 있다** — 1–4 · 13–15 · 20–22 · 27–29 · 34–36. 우리는 이 자리를
앞 필드에 붙여 넓게 읽는다(7.3). 값이 15 이하인 동안은 좁게 볼 때와 결과가 같고, 16 이상도
담긴다. 이 자리들이 실제 코드에서 0이라는 전제 위에 있었는데, **실물 코드로 확인했다**(7.4 #3).

**덱 코드는 출전을 담지 않는다.** 9–12 는 편성 순서이고, 실물 코드에서 1..12 의 순열로 나온다
— 12칸 전부 값을 갖고 겹치지 않는다. 온필드 인원은 전투를 시작할 때 고르는 것이라 편성
코드에 자리가 없다. 그래서 가져오기는 `order` 만 채우고 `deployed` 는 비운 채로 둔다. 없는
근거로 출전을 지어내면 상한 7을 넘겨 **저장분을 읽지 못하게 만든다**(4.2).

내보내기는 반대 방향이다. 편성 순서를 사용자가 정하는 화면이 아직 없어, `order` 가 비어 있으면
**인격이 든 칸을 수감자 번호 순으로 매긴다.** 지어내는 것이지만 0(미편성)으로 두면 게임이 빈
편성으로 읽는다 — 무엇을 지어냈는지 `codec.test.ts` 가 고정한다. 가져온 덱은 코드가 준 순서를
그대로 쓰므로 왕복이 성립한다.

### 7.2 인덱스 산출 — id 에서 바로 뽑는다

"캐릭터 내 출시 순서" 를 `releaseDate` 정렬로 구하면 안 된다. **동률이 있다** — 같은 수감자
안에서 인격 12건 · E.G.O 13건이 같은 날짜를 갖는다(이상의 초기 인격 3종이 모두 2023-02-27).

id 가 이미 순서를 담고 있다. 전수 검증으로 **위반 0건**을 확인했다(인격 184 · E.G.O 110).

```
수감자 = (id / 100) % 100
순번   = id % 100
인격 id = 1|수감자(2자리)|순번(2자리)      예: 10508 = 수감자 5, 8번째
E.G.O id = 2|수감자(2자리)|순번(2자리)     예: 20509 = 수감자 5, 9번째
```

### 7.3 미검증 — 인격 16종 수감자

가이드는 *"한 캐릭터에 15개 이상인 경우가 없어 상관 없다"* 를 전제하지만 **우리 스냅샷에서
이미 깨졌다.** 실측:

| 수감자 | 인격 수 | 4비트(최대 15) |
| --- | --- | --- |
| 그레고르 · 로쟈 · 이상 · 파우스트 · 히스클리프 | **16** | **초과** |
| 뫼르소 · 오티스 · 홍루 · 싱클레어 · 이스마엘 · 료슈 | 15 | 경계 |
| 돈키호테 | 14 | 여유 |

E.G.O 는 최대 10종이라 여유가 있다.

가이드는 16번째부터 앞의 빈 비트로 넘어갈 것이라고 **추정**했을 뿐 확인하지 않았다.
따라서 이 단계에서는 이렇게 다룬다.

- **읽기** — 필드를 4비트가 아니라 앞쪽 빈 비트를 포함한 넓은 필드로 읽는다.
  값 1~15는 결과가 같고 16 이상도 잡힌다. `lib/deck-code/codec.test.ts` 의 「16번째 인격도
  왕복한다」가 DB 실존 id(11216 — 수감자 12 의 16번째 인격, 조회로 확인)로 이를 검증한다.
- **쓰기** — 같은 규칙으로 쓰되, 게임이 받아들이는지는 **실물 코드로만 확인된다.**
  확인 전까지 16 이상이 포함된 덱의 내보내기에 **미검증 표기**를 붙인다.

### 7.4 미검증 목록

**실물 코드를 하나 확보했다.** 검계·거미집 편성이며 12칸이 무엇인지 사람이 게임 화면과
대조했다(`lib/deck-code/game-code.test.ts`). 그전까지 왕복 테스트는 우리 인코더와 우리
디코더를 맞춰 볼 뿐이라 아래 어느 것도 잡지 못했고, 실제로 5번이 틀려 있었다.

| # | 미검증이었던 것 | 지금 | 근거 |
| --- | --- | --- | --- |
| 1 | 인격 순번 16 이상의 인코딩 | **확인됨** | 실물 코드가 순번 16 둘(10716 · 10916)을 담는다. 좁은 4비트로 읽으면 그 칸이 0("인격 없음")이 되고, 넓힌 7비트라야 실제 편성과 맞는다. 다시 인코드한 560비트도 원본과 완전히 같다 |
| 2 | ALEPH 슬롯이 41–46 인지 | 미검증 | 실물 코드에서도 항상 0이라 출시 전까지 확인할 수 없다 |
| 3 | 가이드가 비워둔 자리가 실제로 0인지 | **확인됨** | 원본 560비트와 우리 산출물이 비트 단위로 같다. 빈 자리가 0이 아니었다면 어긋난다 |
| 4 | **E.G.O 필드의 인덱스가 수감자 내 전체 순번인지** | **확인됨** | 12칸의 E.G.O 가 실제 편성과 맞고 왕복 비트가 같다 |
| 5 | 편성 순서(9–12)가 `deployed` 배열 순서와 같은 의미인지 | **반증됨** | 1..12 의 순열로 나온다 — 12칸 전부 값을 갖고 겹치지 않으므로 출전(최대 7)일 수 없다. 편성 순서이며 `order` 로 분리했다 |
| 6 | 우리가 만든 gzip 컨테이너를 게임이 받아들이는지 | 미검증 | 내용물(560비트)은 같으나 압축 산출물이 다르다. 게임에 붙여 넣어 봐야 닫힌다 |

**남은 것은 2번과 6번뿐이며 둘 다 순번과 무관하다.** 그래서 순번 16 에만 붙던 내보내기 경고를
없애고, 6번을 내보내기 전체에 한 번 적는 것으로 바꿨다.

4번을 따로 적는 이유는 이렇다. 등급마다 필드가 하나씩 있으므로 그 안의 값이 **수감자 내
전체 순번**(`id % 100`, 1~10)인지 **그 등급 안에서의 순번**(1~5)인지가 갈린다. 둘 다 성립하는
인코딩이며 어느 쪽인지 가리키는 근거가 가이드에 없다.

우리는 전자로 읽고 쓴다. 근거는 두 가지뿐이고 둘 다 약하다 — `id % 100` 이 이미 그 값이라
변환이 필요 없다는 것, 그리고 가이드가 준 4비트가 전체 순번(최대 10)에는 맞고 등급 내
순번(최대 5)에는 세 비트면 충분해 넉넉하다는 것이다. **방증이지 확인이 아니다.**

검증에 필요한 것은 인게임에서 뽑은 실제 덱 코드와 그 덱의 인격·E.G.O 구성이다.
**16번째 인격과 등급당 둘 이상 보유한 E.G.O 가 함께 든 코드 하나면 1·3·4가 한 번에 갈린다.**

**지어내지 않는다.** 검증 전까지 미검증으로 표기하고, 검증되면 표기를 지운다.

## 8. 오류 처리

| 상황 | 처리 |
| --- | --- |
| localStorage 쓰기 실패 (프라이빗 모드 · 용량 초과) | 화면에 표기. 조용히 넘기지 않음 |
| 스키마 버전 불일치 | 버리지 않고 읽기 실패로 표기. **표기만으로는 부족하다 — 편집을 잠근다.** 읽지 못한 상태에서 새로 쓰면 저장분을 덮어 그때 사라진다 |
| 덱에 인격이 12명 미만 | 런 시작 가능하되 부족을 명시. 엔진은 적은 덱도 계산한다 |
| 참조된 인격·E.G.O·팩 id 가 DB에 없음 (패치 후) | 해당 항목만 결손 표기. 런 전체를 막지 않음 |
| 서버 액션 실패 | 이전 결과 유지 + 오류 배너. 상태를 잃지 않음 |
| 덱 코드 디코드 실패 | 어느 단계에서 실패했는지 표기 (base64 · gzip · 길이) |
| 읽을 수 없는 덱을 쓰려는 시도 | **쓰기가 읽기와 같은 계약을 건다** — `writeDecks` 가 `parseDeck` 으로 걸러 거부한다 |

**쓰기와 읽기의 계약을 갈라 두면 저장소가 스스로 잠긴다.** 한동안 `readDecks` 만 검증하고
쓰기는 그냥 넣었다. 실물 덱 코드 가져오기가 출전 12명짜리 덱을 만들어 그대로 저장했고, 다음
방문에서 `readDecks` 가 그 덱에서 실패하면서 **같은 저장소의 멀쩡한 덱까지 통째로** 못 읽게
됐다. 4.2 의 잠금이 발동하고, 잠긴 상태에서는 쓰기도 막히므로 저장소를 직접 지우기 전에는
복구되지 않는다. 못 읽을 것은 애초에 쓰지 않는다.

**디코드 실패 표기의 실측.** `lib/deck-code/codec.ts` 가 셋을 구분한다 — 실행해 확인했다.

```
decode("!!!not base64!!!")  → "덱 코드를 풀지 못했다: base64 가 아니다"
decode("aGVsbG8=")          → "덱 코드를 풀지 못했다: gzip 매직이 아니다"
decode(짧은 유효 gzip)      → "비트 길이가 560 이 아니다: 16"
```

**단계 이름은 우리가 붙인다.** `atob` 은 `Invalid character` 를 던지는데 — 「`atob` 과
`DecompressionStream` 의 `message` 가 비어 있다」는 서술이 있었으나 이 런타임에서는 성립하지
않는다 — 그대로 실으면 사용자에게 base64 얘기인지 알 길이 없다.

gzip 단계는 `DecompressionStream` 에 넣기 **전에** 매직(`1f 8b`)을 보고 가로챈다. 표기 때문만이
아니라 `bytes.ts` 의 미관측 프라미스가 처리되지 않은 거부로 새는 것을 막기 위해서다(7.1).
빈 문자열도 이 단계에 걸린다.

「압축을 푼 내용이 base64 가 아님」만은 gunzip 실패와 문구를 공유한다. **유효한 gzip 안에
비-base64 가 들어 있어야 도달하므로 실제 덱 코드로는 나오지 않는다** — 갈릴 일이 생기면 그때
쪼갠다.

## 9. 병행하는 엔진 작업과의 경계

엔진 개선을 별도 브랜치·워크트리에서 병행한다. 인터페이스를 건드리지 않으므로 각자 진행하고
병합하면 개선된 엔진 위에서 이 흐름이 그대로 돈다.

| | 이 문서(웹) | 엔진 |
| --- | --- | --- |
| 소유 | `app/**` · `components/**` · `lib/queries/**` · `lib/storage/**` · `lib/deck-code/**` | `lib/engine/**` · `src/engine-proof.ts` · `src/engine-golden.json` |
| 금지 | `lib/engine/**` 수정 | 공개 시그니처 변경 |

**경계에 걸친 것이 하나 있다.** 6절의 `recommendForDeck` 확장(편성과 출전을 나눠 받는 것)은
파일로는 웹 소유지만, 그것이 없으면 엔진 쪽의 **소속 판정 범위 작업이 관측되지 않는다** —
`deck === deployed` 인 동안 `편성` 과 `출전` 이 같은 값이라 점수가 움직이지 않는다.
**웹이 가져간다.** 엔진 브랜치는 구현만 하고 검증은 이 확장 뒤로 미룬다.

엔진 쪽 항목은 `06-recommendation-engine.md` 10절이 적어둔 근사에서 고른다.

1. **탄환·보호 축 추가** — 키워드와 별개인 **특수** 섹션으로 분류한다
2. **소속 판정 범위** — 편성 12 / 출전 7 구분. 지금은 `deck == deployed` 라 이 근사가 죽어 있고,
   이 문서의 편성 입력이 전제를 만들어준다
3. **소속 조건 인원수** — 기프트 설명문을 파싱해 실제 조건으로 바꾼다 (지금은 일괄 3인)

**특수 취급 7건은 보류한다.** E.G.O·기프트가 인격의 키워드나 소속 취급을 바꾸는 기믹이며
실측으로 다음이 전부다.

| 출처 | 건수 | 사례 |
| --- | --- | --- |
| E.G.O 패시브 | 2 | 착영휘도 → 출혈·호흡 · 엄숙한 애도 → 진동·침잠 |
| 인격 패시브 | 2 | 열선 무기 · 피와 불의 냄새 (화상·출혈) |
| 기프트 (키워드) | 1 | 9282 날개 모양 양초 → 새벽 사무소를 화상·진동으로 |
| 기프트 (소속) | 2 | 9280 본국검보 → 검계 · 9841 C형 정리 요원 세트 → W사 |

인격 패시브 2건은 이미 반영돼 있다 — 상류가 `statuses` 를 저작 목록으로 주고 거기에 효과가
녹아 있다(10814 거미집 중지 제자가 `Combustion` 과 `Laceration` 을 함께 갖는다).

**다만 검증이 선행되어야 한다.** 10508 검계 우두머리 뫼르소가 착영휘도를 끼지 않아도
`Breath` 를 갖고 있다. 상류 목록이 E.G.O 조건부 부여까지 무조건 포함했을 가능성이 있고,
그렇다면 엔진은 장착하지도 않은 효과를 이미 계산에 넣고 있다. 데이터 구조를 바꿔야 하는
사안이라 데이터 작업과 함께 다룬다.

### 9.1 접점

E.G.O 를 엔진이 보게 되는 시점에 이 시그니처가 필요하다. 미리 확정해 두어 양쪽이 각자 진행한다.

```ts
export async function loadIdentities(
  locale: Locale,
  ids?: number[],
  equipped?: ReadonlyMap<number, number[]>,   // 인격 id → 장착 E.G.O id
): Promise<Identity[]>
```

선택 인자이므로 추가해도 기존 호출이 깨지지 않는다. 이 인자와 `lib/queries/recommend.ts` 의
호출 한 줄은 **엔진 쪽이 함께 가져간다.** 충돌면이 한 줄로 줄어든다.
`Identity` 반환 타입은 불변이다.

| 덱 코드 | 왕복 일치: true. `lib/deck-code/codec.test.ts` 가 DB 실존 id — 인격 10101 · 10508 · 11216(수감자 12 의 16번째), E.G.O 20101 · 20503 — 로 디코드 → 인코드 → 원본과 동일함을 확인했다. 인게임 실물 코드로 쓰기 경로(7.3)를 대조하는 것은 여전히 미검증이다 |
| 흐름 | 편성 편집(`/squad` — 수감자 12칸 채우기 · 덱 코드 입출력)은 브라우저로 완주해 확인했다(Task 7·8 보고서). 런 시작 → 층 진행 → 되돌리기 → 종료(5.2)는 이 계획이 다루지 않는다 — 계획 B 의 몫이며 아직 구현되지 않아 미검증이다 |
| 저장분 소실 | 버전 불일치 상태에서 「새 덱」이 저장분을 덮는 것을 재현했고(4.2), `locked` 로 막았다. 소실 경로 자체는 `lib/storage/decks.test.ts` 가 회귀로 잠근다. **화면의 잠금은 단위 테스트가 없다** — 이 저장소에 DOM 테스트 배선이 없어 브라우저 확인에 의존한다 |
| 참조 결손 | 데이터에 없는 인격·E.G.O id 를 가리키는 칸에 「데이터에 없음」을 표기한다(8절). 덱 코드 가져오기로만 도달하는 경로라 **실측 재현은 하지 않았다** |
| 판정 범위 | `/ko/recommend?deployed=…` 로 편성과 출전을 갈라 소속 패널의 인원이 달라지는지 본다(6절). **엔진 브랜치 병합 전에는 숫자만 갈리고 점수는 같다 — 그것이 정상이다** |
| 15초 기준 | 런 추적(5.2, 계획 B)이 구현되어 위 흐름을 끝까지 완주할 수 있게 되면 그때 층당 소요를 실측해 이 문서에 기록하고 기준을 재검토한다. 이 단계에서는 측정하지 않았다 |

이 화면들은 데이터베이스를 읽기만 하므로 `npm run verify` 의 대상이 아니다.

## 12. 미결

- **15초 기준이 잠정이다.** `00-product.md` 6절이 4단계 설계 시 재검토하라고 남겼고,
  10절의 실측 전까지는 검증되지 않은 수치다.
- **추천 결과의 타당성은 이 단계가 보증하지 않는다.** 엔진의 알려진 근사 8종
  (`06` 10절)이 그대로 남아 있고, 9절의 병행 작업이 일부를 걷어낸다.
- **덱 코드에 미검증이 둘 남아 있다**(7.4). 실물 코드 하나로 셋이 확인되고 하나가 반증됐다.
  남은 것은 ALEPH 슬롯 배치와 **우리가 만든 gzip 컨테이너를 게임이 받아들이는가**이며,
  둘 다 인격 순번과 무관하다.
- **덱 코드 형식의 출처가 저장소에 없다**(7.0). 남기기 전까지 7.1의 배치는 대조할 대상이 없다.
- **소속 판정 범위는 6절의 `recommendForDeck` 확장 전까지 관측되지 않는다.** 엔진 쪽이
  구현해도 `deck === deployed` 인 동안은 점수가 같다(9절).
