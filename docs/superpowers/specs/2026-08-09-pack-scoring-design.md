# 팩 점수 모형 — M4 PR-B 설계

> 상태: 설계 / 2026-08-09
> [PR #28](https://github.com/MyLittleChicken/limbus-company-dossier/pull/28) 이 추천 화면을 `lib/engine/v2` 로 옮기면서 팩 순위를 비웠다.
> 이 문서가 그 자리를 채운다. 저울추는 **PR-A 를 실제로 돌려 보고** 정했다.
> 이 문서의 수치는 3층 hard · 화진 덱 실측이다.

## 1. 무엇을 만드나

**층마다 「어느 팩에 들어갈까」를 순위로 답한다.**

PR-A 는 기프트 등급(A/B/C)까지 냈고 **순위를 일부러 안 매겼다** — 점수 모형이 없는데
순서를 붙이면 그 순서가 거짓말이 되기 때문이다. 이제 모형을 세운다.

**레거시 점수를 되살리는 것이 아니다.** `marginalValue` · `ceiling` 은 「이 기프트가 얼마나
세지나」를 수치로 재던 것이고 `canonical` 에 그 값이 없다. v2 는 「켜지나」를 답하므로
점수도 **켜짐의 밀도와 정렬**로 세운다.

## 2. 제품 흐름이 모형을 정했다

```
팩 진입 → 그 팩에서 얻을 수 있는 기프트 나열 → 획득한 것을 사용자가 기입
        → 보유 저장 → 다음 층 진입 → 팩 선택  (반복)
```

여기서 셋이 따라 나온다.

**팩 선택은 풀 선택이다.** 전투 · 인카운터 · 상점 어느 경로로 얻든 그 팩의 풀에서
나온다. 획득 경로는 추적하지 않는다.

**크기가 아니라 밀도다.** 한 층에서 실제로 얻는 기프트 수는 팩이 58개든 187개든
비슷하다. 풀이 크면 원하는 것을 만날 확률이 오히려 묽어진다.

**보유가 누적된다.** 같은 팩이라도 층이 깊어지면 값이 달라진다. 이미 가진 것은 다시
얻을 수 없으므로 후보에서 빠지고, 대신 **다른 기프트를 켜는 다리**가 된다.

## 3. 실측이 두 모형을 기각했다

점수를 「등급 A 인 기프트 수」로 세려 했으나 실측이 막았다.

```
상관 — 팩크기 vs A수        0.923   A 수를 세면 사실상 팩 크기를 재는 것이다
상관 — 팩크기 vs A비율      -0.448   비율로 정규화하면 이번엔 작은 팩이 이긴다
```

정규화한 밀도도 갈리지 않았다.

```
밀도 상위 6개   0.862 · 0.856 · 0.844 · 0.831 · 0.825 · 0.819
                7% 안에 뭉쳐 있다.  순위가 사실상 무작위다
```

**이유는 트리거 상당수가 아무 편성에서나 켜지기 때문이다.** `Always` 나 흔한 죄악
조건은 어느 팩에나 있고, 그런 효과는 이 팩을 고를 이유가 못 된다.

빠진 것은 「이 팩이 **내 덱과** 맞나」였다.

## 4. 조건 결합의 모호함은 없다 — 실측으로 닫았다

설계 중에 「조건 5개 중 3개 충족」을 어떻게 셀지가 문제로 보였다. AND 로 접으면
과소, OR 로 접으면 과대다. `v2/types.ts` 결정 2 가 그래서 접기를 거부했다.

**실측하니 문제 자체가 없었다.**

```
트리거당 참조 수   1개   150개 트리거 전부.  예외 없음
기프트당 트리거 수  1~8개  2개가 161건으로 최다
```

트리거 하나에 참조가 하나뿐이라 **결합할 것이 없다.** 「4개 중 3개」는 조건 논리가
아니라 **기프트의 효과 4개 중 3개가 내 편성에서 산다**는 뜻 그대로다.

```
9052 휴대용 전지 소켓        충족 3/4
  Always                    충족        무조건 발동
  Sloth Absolute Resonance  충족(가능)  나태 공명
  Sloth Resonance           충족(가능)  나태 공명
  Allies have Charge Skill  미충족      충전 스킬 없음
```

**그러므로 부분 점수는 가정을 들이는 것이 아니라 사실을 그대로 세는 것이다.**

## 5. 점수 모형

팩마다 두 수를 곱한다. **보유한 기프트는 후보에서 뺀 뒤** 계산한다.

```
적합도 F   Σ fit(기프트 키워드) / 후보 수
           fit(kw) = 덱의 그 축 공급 인원 / 최대 축 공급 인원
           「이 팩에서 하나 뽑으면 내 덱 축에 얼마나 기여하나」

켜짐  L    Σ 살아있는 발동 조건 / Σ 전체 발동 조건
           확정 1.0 · 가능 0.5
           보유가 켜주는 연쇄 — 1홉 1.0 · 2홉 0.5 가산
           「이 팩 기프트의 발동 조건 중 몇 %가 내 편성에서 사나」

점수 = F × L
```

**분모의 「최대 축 공급 인원」은 `refKind === 'axis'` 안에서만 본다.** `Profile` 은
죄악 · 공명 · 코인 등 여덟 갈래를 함께 내는데(PR-A 실측), 그중 가장 큰 값으로
나누면 축의 차이가 뭉개진다.

**연쇄 가산은 그 기프트의 미충족 발동 조건 수를 넘지 않는다.** 안 그러면 편성으로
이미 전부 켜진 기프트에 연쇄가 덧붙어 `L` 이 1 을 넘는다 — 「발동 조건 중 몇 %가
사나」라는 정의와 어긋난다. 연쇄는 **편성이 못 켜는 것을 보유가 대신 켜 주는
경우**를 세는 것이다.

### 5.1 왜 곱인가

둘이 각각 다른 질문에 답한다. **합으로 하면 한쪽이 0 이어도 다른 쪽이 메운다** —
덱과 전혀 안 맞는 팩(F≈0)은 켜짐이 높아도 고를 이유가 없다.

실측이 두 축의 독립을 보였다.

```
내쉬어진 한숨   켜짐 0.568 (최고)   적합도 0.052 (최하)
                아무 덱에서나 켜지지만 이 덱과는 안 맞는다.  곱이 그것을 잡는다
```

### 5.2 「확정」과 「가능」

공명처럼 전투 중 코인 결과로 갈리는 조건은 편성만 보고 단정할 수 없다. 엔진이
이미 `certainty: 'certain' | 'possible'` 로 갈라 낸다.

```
확정   Allies have Wrath Skill · 분노 스킬 7개 보유    편성만 보면 판정 끝
가능   Sloth Resonance · 나태 6개 보유 / 3개 필요      전투 중에 갈린다
```

**실측으로 충족 45건 중 13건(29%)이 「가능」이다.** 확정과 같은 값으로 두면 공명
덧어진 팩이 과대평가된다. 반으로 센다.

`have` 와 `need` 의 여유(6/3 이 3/3 보다 터진다)로 더 정밀하게 가중할 수 있으나
**하지 않는다** — 저울추가 하나 늘고 설명이 어려워진다.

### 5.3 저울추가 둘뿐이다

```
확정 1.0 / 가능 0.5      한 단계 불확실해지면 반
연쇄 1홉 1.0 / 2홉 0.5   한 홉 멀어지면 반
```

**같은 규칙이고 나머지는 전부 실측값에서 나온다.** 손으로 정한 상수를 늘리면 순위가
설명 불가능해진다.

### 5.4 안 쓰는 것

```
tier · tier_label   티어가 가치와 어떻게 이어지는지 증거가 없다
cost                획득 비용.  상점 경로에만 걸리는데 경로를 추적하지 않는다
hard_only           난이도 필터는 floor_pack 이 이미 한다
gift_requirement    획득 조건 142건.  풀에 들어오나 마나를 가르지만 이번 범위가 아니다
```

증거 없이 저울추를 늘리지 않는다. 필요해지면 다음 회차에서 실측으로 연다.

## 6. 실측 결과 — 순위가 상식과 맞는다

3층 hard · 화진 덱(화상 7 · 진동 6 · 탄환 3 · 호흡 1) · 보유 0개.

```
 점수    적합도  켜짐   크기   이름
0.1396   0.273  0.511    58   타오르는 일렁임      화상·진동 테마.  1순위가 옳다
0.1209   0.247  0.490    59   어지러운 파동         진동
0.0890   0.213  0.417    71   흘리는 것들
0.0765   0.218  0.351   110   어느 세계
0.0628   0.170  0.370   187   뽕.황               187개 괴물 팩이 15위로 내려앉는다
0.0446   0.087  0.515    61   빠져드는 색욕         죄악 테마.  덱과 무관
0.0064   0.014  0.448    60   잠겨드는 아림         침잠.  가장 안 맞다
```

**22배 변별이고 1위가 사람 판단과 일치한다.** 크기 편향이 사라졌다 —
187개짜리 「뽕.황」이 15위다.

보유 12개를 넣으면 후보가 줄고 점수가 따라 움직인다. 1위는 유지되며(0.1264)
켜짐이 0.511 → 0.541 로 오른다 — 연쇄가 붙기 때문이다.

## 7. 구조

```
lib/engine/v2/score.ts                        새로 만든다.  순수 함수.  DB 를 모른다
  axisSupplyOf(rows): AxisSupply              refKind === 'axis' 만 접는다
  fitOf(keywordId, supply): number            축 공급으로 적합도
  liveOf(gift: ScoreGift): number             확정 1.0 · 가능 0.5 · 연쇄 1홉 1.0 · 2홉 0.5
  scorePack(gifts, supply): PackScore         팩 하나.  호출자가 map 한다

lib/engine/v2/score.test.ts                   순수 검사.  DB 없이 돈다

lib/queries/canonical/recommend.ts
  scorePack 을 부르고 PackLine 에 { score, fit, live } 를 더한다
  packs 를 score 내림차순으로 정렬 — 지금은 id 순이다

app/[locale]/recommend/page.tsx
  순위 번호와 분해 한 줄.  레이아웃 · 색 · 간격은 안 건드린다
```

**점수 계산이 엔진에 있고 질의에 없다.** 순수 함수라 DB 없이 검사할 수 있고 저울추가
코드로 잠긴다 — [ADR-08](../../adr/08-authored-facts-as-data.md) 의 「규칙은 코드 ·
사실은 데이터」와 같은 자리다.

**`ScoreGift` 는 기프트 id 를 안 받는다.** 셈에 필요 없고, 받으면 엔진(문자열 id)과
화면(숫자 id) 사이의 변환이 점수 층까지 새어 든다. 보유 여부는 호출자가 `owned`
불리언으로 표시해 넘긴다.

`recommend.ts` 는 `gift` 를 `include` 로 가져오므로 **`keywordId` 가 이미 따라온다** —
질의를 고칠 필요가 없다(실측 확인).

**화면은 정렬과 한 줄뿐이다.** 정보 제공 화면의 디자인 작업이 별도로 진행 중이고,
추천 화면은 제품 표면이 아니라 **엔진이 도는지 보이는 창**이다(PR-A 5절).

## 8. 지어내지 않는 자리

```
후보 0개 (전부 보유)      score 0.  나누기 0 을 안 만든다
효과 0개인 기프트          L 분모에서 빠진다.  0 으로 세지 않는다
팩 전체가 효과 0개         L 분모 0 → L 0.  score 0
축 공급이 0 인 덱          maxSupply 0 → F 전부 0.  순위가 없다고 낸다
keywordId 가 null         fit 0
keyword 가 축이 아닌 것    None · Random · Slash · Penetrate · Hit → fit 0
                          공격 타입 3종과 범용이 키워드 표에 섞여 있다.  축이 아니다
연쇄가 미충족보다 많음      미충족 수에서 자른다 (5절).  L 이 1 을 못 넘는다
```

**점수가 0 인 것과 계산을 못 한 것을 안 섞는다.** 축 공급이 0 인 덱은 F 가 전부 0 이라
순위가 무의미하다 — 화면이 「순위를 매길 수 없다」고 적고 등급 분포만 낸다. 0 점을
매겨 늘어놓으면 그 순서가 거짓말이 된다.

```

상식 검사    화진 덱 1위가 「타오르는 일렁임」인가.  6절 실측을 회귀로 건다
```

**골든에 추천을 더하는 것이 중요하다.** 지금 골든 20건에 추천이 빠져 있다. PR-A 에서
`options.deployedIds ?? identityIds` 가 빈 배열을 값으로 받아 출전 분모가 0 이 된
버그를 **화면을 띄워서야** 잡았는데, 골든에 있었으면 대조로 잡혔을 것이다.

## 11. 구현 결과

```
파일   lib/engine/v2/score.ts (신규) · lib/engine/v2/score.test.ts (신규)
       lib/queries/canonical/recommend.ts · app/[locale]/recommend/page.tsx
       scripts/golden-queries.ts
검사   순수 15건 추가.  전체 457 → 472 · 0 실패 · 12 skip
골든   20 → 23건.  기존 20건 변화 없음
앱     경로 18개 200 · 서버 에러 0 · 분해 줄 27개
순위   1위 타오르는 일렁임 0.1396 (적합 0.273 × 켜짐 0.511)
       2위 어지러운 파동 0.1209 · 187개짜리 「뽕.황」은 15위
       L 최대 0.568 (보유 12개일 때 0.653) — 1 을 안 넘는다
보유   3개를 넣으면 첫 팩이 0.140 → 0.143 으로 갈린다
```

**6절의 실측값이 구현에서 그대로 나왔다.** 다르면 모형이 아니라 배선이 틀린
것이므로 여기서 확인한다.

**골든이 처음엔 목적을 못 이뤘다.** 9절이 「골든에 추천을 더하는 것이 중요하다」고
적은 이유는 PR-A 에서 `options.deployedIds ?? identityIds` 가 빈 배열을 값으로
받아 출전 분모가 0 이 된 버그를 화면을 띄워서야 잡았기 때문이다 — 다음엔 골든의
대조로 잡자는 것이었다. 그런데 처음 넣은 두 케이스는 `deployedIds` 를 아예 안
넘겼다(`undefined`). `[] ?? x` 는 `[]` 이고 `undefined ?? x` 는 `x` 라 **두
버전(버그 있음/없음)의 결과가 같았고, 코드를 버그 버전으로 되돌려도 골든이
안 갈렸다.** `deployedIds: []` 를 명시적으로 넘기는 세 번째 케이스
(`recommend.floor3.emptyDeployed`)를 더해 고쳤다. 코드를 버그 버전으로 일시
되돌려 그 케이스 하나만 갈리는 것을 실측으로 확인했다(같다 22건 · 다르다
1건). 회귀 검사는 「무엇을 잡는가」를 실제로 재 봐야 한다는 사례다 — 골든에
넣었다는 사실 자체가 검증이 아니다.

**`ownedGifts` 질의에 `orderBy` 가 없었다.** PostgreSQL 은 `ORDER BY` 없는
결과 순서를 보장하지 않는다. `owned` 배열이 골든에 그대로 들어가므로 재실행
때 순서가 뒤집히면 거짓 경보가 난다. `orderBy: { id: 'asc' }` 를 더했다.

**고층에서는 이 지표의 변별이 약하다.** 12층 hard 의 후보 24팩 중 서로 다른
점수가 6개뿐이다(3층은 27팩 전부 서로 다른 점수가 나온다). DB 로 확인한
원인은 모형이 아니라 데이터다 — 16팩이 기프트 187개를 완전히 같은 집합으로
공유하고, 3팩이 또 다른 184개를 공유한다. 팩 이름만 다르고 내용물이 같으므로
점수가 같은 것이 옳다. 다만 고층에서 팩 선택이 이 지표로 거의 안 갈린다는
것은 실용적 한계이며, **점수 모형의 결함이 아니라 데이터의 성질**이다.

**최종 리뷰가 어휘 혼동을 잡았다.** `ScoreGift.total` 은 「전체 효과 수」로
문서화돼 있었지만 `recommend.ts` 가 거기 채우는 값은 `GiftVerdict.total` =
`reasons.length` = 트리거 참조 수다. `canonical` 은 `gift_effect` 와
`gift_trigger` 를 별개 표로 갖고, `giftEffects` 는 연쇄(`chain()`)에만 쓴다 —
한 기프트의 효과 수와 트리거 수는 같을 이유가 없다. 셈 자체는 처음부터 옳았다
(4절의 `9052 휴대용 전지 소켓` 예가 넷 다 발동 조건이다). 틀린 것은 이름이었고,
그 이름이 `score.ts` 의 주석 · `recommend.ts` 의 필드 주석 · 이 설계서 · 추천
화면 문구까지 네 층에 퍼져 있었다. 다음 사람이 「그럼 `giftEffects` 를 왜 안
쓰지」하고 배선을 고치러 들어올 자리였다. 어휘를 「발동 조건」으로 통일했다 —
필드 이름 `total` 은 `GiftVerdict.total` 과 짝을 맞춰야 하므로 그대로 두고,
주석과 문서와 화면 문구만 고쳤다. 셈과 저울추는 손대지 않았다.
