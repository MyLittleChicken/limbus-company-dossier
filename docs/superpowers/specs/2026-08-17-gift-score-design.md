# 기프트 점수 모형 3단계 — 순위 표본과 저울추

## 1. 왜 하나

기프트 발동 판정을 절 단위로 옮기는 일은 세 단계다. 1단계(#36)가 데이터를,
2단계(#37)가 엔진을 옮겼다. **이 문서는 3단계 — 점수다.**

2단계가 끝난 뒤 163덱으로 실측한 결과가 이 단계의 이유다.

```
기프트 456건 중 354건이 전 덱에서 켜진다
```

**`fireable` 로는 순위가 안 나온다.** 기프트 대다수가 실제로 범용이라 이진
판정이 변별을 못 한다. 옛 모형의 208건은 잘못 죽여서 낮았던 것이고 354가
정직한 수다. 변별은 **점수**가 해야 한다.

### 지금 점수가 무엇을 잘못하나

```
점수 = (적합도 F + 합성 도달 C) × 켜짐 L

F = keywordId 가 내 덱 축과 맞나 × (전용 1.0 / 범용 0.5)
```

`F` 가 **절반 가까이 0** 이다. 절을 가진 456건 기준:

| 갈래 | 수 | 지금 F |
|---|---|---|
| 축 키워드 (Combustion·Laceration·Burst·Breath·Vibration·Sinking·Charge) | 276 | 잰다 |
| 공격 타입 (Slash·Hit·Penetrate) | 60 | **0** — 축이 아니라서 |
| 키워드 없음 (null 또는 `None`) | 120 | **0** |

그리고 **`tier` 를 안 쓴다.** 456건에 등급이 다 매겨져 있는데도 쓰지 않는다.

```
1등급 58 · 2등급 139 · 3등급 136 · 4등급 119 · 5등급 2 · EX 2
```

등급은 비용과 단조롭게 맞물린다(1등급 평균 151 → 4등급 403 → 5등급 600 →
EX 999). **게임이 스스로 매긴 위력 표시**이며 공짜로 쓸 수 있다.

## 2. 결정

### 2.1 「맞는가」와 「강한가」를 둘 다 본다

사용자 확인 2026-08-17. 지금은 「맞는가」만, 그것도 절반만 본다.

### 2.2 적합도 `F` 는 **부여**만 잰다 — 요구는 `L` 이 이미 잰다

`L`(켜짐)은 「이 기프트의 조건을 내 편성이 채우나」다. 절 조건을 `F` 에 또
넣으면 **같은 것을 두 번 센다.**

둘은 실제로 다른 것을 가리킨다. 화상 키워드 기프트 14건 중 **9건은 조건이
없다** — 「편광」·「부화하지 않은 불씨」처럼 화상을 **주기만** 한다. 화상 덱에
좋은 기프트인데 절 조건으로는 잴 것이 없다.

```
keywordId    이 기프트가 무엇에 관한 것인가     「화상을 준다」        → F
절 조건       이 기프트가 무엇을 요구하는가      「화상 인격 5인 필요」  → L
```

### 2.3 부여 어휘는 **축 + 공격 타입**까지만 넓힌다

사용자 확인 2026-08-17. 죄악(`gift.sin`, 441건)은 뺀다 — 「그 기프트가 그
죄악을 키운다」는 보장이 약하고, 색 분류일 뿐일 수 있다.

넓히면 456건 중 336건(74%)이 잴 것을 갖는다. 남는 120건은 **범용 기프트**이고,
읽어 보면 축을 안 키운다.

```
쪽빛 지포라이터   턴 시작 시 우울 E.G.O 자원 +1, 나머지 무작위 2종 +1
저주 인형        턴 시작 시 적 전체에게 질투 피해 3
굴레            스테이지 시작 시 최대 체력 +(층×2)%, 최대 20%
달의 기억        모든 적의 물리·속성 내성이 취약으로 변경
```

E.G.O 자원 · 체력 · 고정 피해 — **어느 덱에나 똑같이** 좋다. 어휘를 넓혀도
「이 덱에 특별히 맞는다」가 안 나오는 것이 **맞다.**

### 2.4 점수는 **곱이 아니라 합**이다

```
기프트 값  V = w_적합 · fit + w_등급 · tier + w_전용 · [전용인가]
```

사용자가 낸 제약이 이 모양을 강제한다 — 「달의 기억(5등급·범용)이 화상
2등급보다 위일 수 있다」. **곱으로는 불가능하다**: 적합도가 0 이면 등급이
무엇이든 0 이다.

「범용에 바닥값을 준다」는 안 한다. 합이면 필요 없다 — 적합도가 0 이어도 등급
항이 값을 낸다.

`L` 은 **지금처럼 곱한 채로 둔다.** 「이 편성에서 안 켜진다」는 성격이 다르고,
요구는 이미 거기서 답한다.

### 2.5 저울추는 **지어내지 않고 표본에서 찾는다**

```
범용 5등급  >  화상 2등급 전용   이어야 하나?
```

참이 되려면 등급 항의 무게가 적합도 항보다 커야 하고, 거짓이 되려면 작아야
한다. **어느 쪽이든 숫자 하나로 정해지는데 그 숫자에 근거가 없다.**

그래서 사람이 매긴 순위를 먼저 모으고, 그것을 재현하는 저울추를 찾는다.
**이 저장소는 「좋은 추천」의 정의를 아직 한 번도 적어 둔 적이 없다** — 지금
점수가 좋은지 나쁜지도 사실 모른다.

### 2.6 손보정 표는 이번에 안 만든다

3등급 136건 안의 차이는 등급으로 안 갈린다. 그러나 456건에 손으로 위력을
매기는 것은 유지가 안 되고, 게임을 안 해 본 판단이 데이터로 굳는다.

**표본이 「등급만으로는 이 둘을 못 가른다」를 보여 주면 그때 근거를 갖고
만든다.** 이 문서의 범위 밖이다.

## 3. 순위 표본

### 3.1 판정 방식 — 4단 바구니

사용자 확인 2026-08-17. 완전 순서는 중간 순위가 억지로 매겨져 골든으로
굳을 위험이 있고, 짝 비교는 판정 수가 많다.

```
【반드시 집는다】  3
【좋다】          2
【보통】          1
【안 집는다】      0
```

칸 **안**은 순서를 안 따진다. 칸이 다르면 순서 제약이 생긴다 — 저울추를
맞추기엔 그것으로 충분하다.

### 3.2 덱 열하나 — 성격이 달라야 한다

> **v2 로 고쳤다(2026-08-18).** 원래는 A 화상·B 소속·C 섞임 셋이었다. 셋으로는
> 갈래별 확인이 세 갈래뿐이라 확인 덱 하나가 우연히 쉬우면 그대로 결론이 되고,
> 소속 덱은 「같은 수감자 12명 금지」라는 거울 던전 편성 규칙과 부딪혀 짤 수
> 없었다. 축 여덟과 공격 타입 셋을 하나씩 세우고 방향이 안 잡힌 덱을 하나 더해
> 열하나로 갔다.

| 덱 | 짜임 | 이 덱이 정하는 것 |
|---|---|---|
| 1~8 | 축마다 하나 — 화상·열상·파열·호흡·진동·침잠·충전·(그 밖) | 적합도가 살아 있을 때의 순서 |
| 9~10 | 공격 타입 — 관통·타격 | 축이 아니라 타입으로 붙는 기프트의 자리 |
| 11 | 방향이 안 잡힌 덱 (축이 흩어진다) | **적합도가 없을 때 등급이 얼마나 말하는가** |

**덱 11 이 핵심이다.** `w_등급` 은 저 덱에서만 정해진다 — 그래서 그 덱만
엇갈리는 카드를 배로(20장) 싣는다.

편성은 **거울 던전 규칙 그대로** 짠다: 12인 편성 · 출격 7 · 대기 5 · 수감자
열둘이 서로 달라야 한다. `rank-deck.ts` 가 덱마다 그 자리에서 관문으로 센다.

### 3.3 기프트를 어떻게 고르나 — 세 무더기

> **v2 로 고쳤다(2026-08-18).** 「네 축을 고르게 덮는다」로는 뽑힌 20장의
> 대부분이 **어떤 저울추로도 맞는 짝**이 됐다. 저울추를 실제로 가르는 것은
> 신호가 서로 어긋나는 카드뿐이라, 그것을 목표량으로 못 박는 쪽으로 바꿨다.

덱마다 세 무더기를 채운다.

```
확실히 좋다    10  높은 등급 + 이 덱 축과 맞음        어떤 저울추로도 맞는다
엇갈린다      10  신호가 어긋난다 — 네 갈래를 돌아가며  **저울추는 여기서만 정해진다**
확실히 아니다  10  낮은 등급 + 안 맞음                어떤 저울추로도 맞는다
```

「엇갈린다」의 네 갈래: 고등급·부적합 · 저등급·적합 · 상위 합성 재료 ·
전용·저등급. 갈래를 돌아가며 채워 한 갈래가 무더기를 다 먹지 않게 한다.

**목표량을 못 채우면 채운 수를 적고 넘어간다.** 「확실히 좋다」 조건을 다
만족하는 카드가 후보 383장 중 그만큼뿐인 덱이 있다 — 덱 11 은 0장, 덱 8 은
2장이다. 그래서 덱마다 22~30장이고 **전부 307판정**이다. 억지로 채우면 그
무더기의 뜻이 흐려진다.

카드는 **거울 던전에서 집을 수 있는 것**만이다. 합성으로만 나오는 결과물 60장과
획득 경로가 없는 13장을 빼서 후보는 383장이다. 재료 카드에는 무엇을 만드는
재료인지 함께 적는다 — 그 값어치는 카드 자체 효과가 아니라 상위로 가는 길에서
온다.

카드 하나가 지고 있는 것:

```
등급     1 · 2 · 3 · 4 · 5/EX
키워드   축 일치 · 축 불일치 · 키워드 없음
팩       전용 · 공용
요구     조건 없음 · 조건 충족 · 조건 미충족
```

**조건 미충족(죽는 것)도 넣는다.** 다만 이것들은 저울추를 맞추는 데 안 쓴다 —
`scorePack` 이 `fireable` 이 거짓인 기프트를 **후보에서 아예 빼기** 때문에
모형이 값을 매기지 않는다.

그럼 왜 넣나. **그 거르기가 옳은지를 표본이 판정하기 때문이다.** 사용자가
「안 켜지는 4등급」을 「안 집는다」에 두면 거르기가 맞고, 「보통」 이상에 두면
거르기가 너무 세다는 뜻이다(예: 지금은 안 켜져도 나중 층에서 편성이 바뀌면
켜질 수 있다). 후자면 그 사실을 적고 `L` 의 자리를 다시 본다.

저울추 셈에서는 **`fireable` 이 참인 짝만** 센다. 이 규칙을 안 적어 두면
「죽는 기프트를 0점으로 두면 정확도가 오른다」는 가짜 이득이 생긴다.

**같은 기프트를 여러 덱에 겹쳐 넣는다.** v1 은 「20개 중 6개는 세 덱 공통」으로
못 박았는데, 열한 덱에서는 그 규칙이 도리어 서로 다른 덱을 같은 서른으로 만든다
— 등급·전용은 덱과 무관해서 같은 카드가 계속 앞에 선다. 그래서 **앞 덱이 쓴
카드를 뒤로 미루되 자리가 남으면 그대로 쓴다**로 바꿨다(자리를 비우느니 겹친다).
실측 겹침은 덱쌍 최댓값 9 이고, 서로 다른 기프트 246 / 판정 307 이다.

겹침이 없으면 두 가지를 못 가른다.

```
같은 카드가 열한 덱 모두 「반드시 집는다」   → 적합도와 무관한 값이다
어떤 카드가 화상 덱에서만 위               → 적합도가 실재한다
```

(v1 은 이 자리에 달의 기억·진혼을 예로 들었는데, 둘 다 합성으로만 나오는
결과물이라 **애초에 카드로 안 나온다** — 예가 틀렸다.)

### 3.4 페이지

1단계의 절 검수 페이지와 같은 자리다 — 제가 보여 주고, 사용자가 판정하고,
내보내면 받는다.

```
보여 줄 것   이름 · 등급 · 키워드 · 전용/공용 · 설명문 전문 · 이 덱에서 켜지나
            덱 머리에 출격 7인 · 대기 5인의 이름과 공급(분모까지: 열상 5/7)
            합성 재료면 무엇을 만드는지 · 함께 필요한 칸(칸 안은 「또는」)
조작        네 칸으로 옮긴다
내보내기     JSONL 한 줄 = 한 판정
```

**화면의 무더기는 둘이다 — 「애매한 것」과 「나머지」.** `stratum` 셋은 JSON 과
저울추 보고에 그대로 남기되, 화면에는 「확실히 좋다」·「확실히 아니다」를 소제목으로
안 적는다. 그것은 모형의 결론이라, 187장 위에 붙여 놓으면 사람이 칸을 통째로
던지게 되고 그 판정들은 무더기 안 짝을 하나도 안 만든다. 「애매한 것」은 남긴다 —
그건 결론이 아니라 신호가 어긋난다는 사실이고, 사람이 힘을 어디 쓸지 알아야 한다.

**설명문 전문을 보여야 한다.** 이름과 등급만으로는 「달의 기억」이 얼마나
센지 알 수 없다.

내보내기 형식:

```json
{"deck":"A","giftId":"9083","bucket":3}
```

파일은 `src/v2/authored/gift-rank.jsonl` 에 둔다. **`data/` 아래에 두지
않는다** — 그 디렉터리는 커밋 훅이 막는다(Project Moon 저작물 스냅샷 정책).

## 4. 저울추 맞추기

### 4.1 격자 탐색

저울추가 셋뿐이라 값 범위를 잘게 훑어 **바구니 순서를 가장 많이 맞히는 조합**을
고른다. 학습 라이브러리가 필요 없고, 결과가 결정적이며, 「왜 이 숫자인가」를
「짝 몇 개 중 몇 개를 맞혔다」로 답할 수 있다.

**전체 정확도만 내면 안 된다.** 짝의 대부분은 무더기가 서로 다른 짝이고, 그건
후보를 고를 때 이미 갈라 놓은 것이라 어떤 저울추로도 맞는다. **무더기별로 따로
세서** 「애매한 무더기 안에서 몇 개를 맞혔나」를 함께 낸다 — 그 수가 이 표본이
실제로 정한 것이다. 무더기가 서로 다른 짝은 「섞임」으로 따로 센다.

**안 켜지는 카드의 판정도 히스토그램으로 낸다.** 그 30장은 저울추 셈에서 빠지지만
(§3.3), 어느 칸에 갔는지를 안 내면 그것들을 넣은 이유 자체가 사라진다.

**맞혔다의 뜻** — 같은 덱의 두 기프트 `x`, `y` 에 대해 바구니가 다르면
(`b(x) > b(y)`), 값도 그 순서여야 한다(`V(x) > V(y)`). 그런 짝이 몇 개나
지켜지는지를 센다. 같은 칸의 짝은 안 센다.

### 4.2 덱 하나를 빼고 맞춘 뒤, 뺀 덱으로 확인한다

> **v2 로 고쳤다(2026-08-18).** 덱이 열하나가 되어 갈래도 열하나다. 셋일 때는
> 확인 덱 하나가 우연히 쉬우면 그것이 곧 결론이었다.

307판정에 저울추 셋이면 외워버릴 위험이 크진 않지만, **확인 없이 「맞췄다」고
하면 그것은 증명이 아니다.** 덱을 하나씩 빼며 열한 갈래를 모두 돌려 전부
보고한다.

**확인 쪽은 동점 저울추 전부로 재서 폭을 함께 찍는다.** 대표 저울추는 항을 적게
쓰는 쪽이라 체계적으로 `w_적합 = 0` 을 고르는데, 그 하나만 보고 「확인 0%」를
「모형이 틀렸다」로 읽으면 정반대인 일이 실제로 생긴다.

확인 덱의 정확도가 맞춘 덱보다 **크게 낮으면 모양이 틀린 것**이다 — 저울추를
더 늘리지 말고 그 사실을 적는다.

### 4.3 적합도 `fit` 을 어떻게 셈하나

```
축 키워드      덱의 그 축 공급  / 출격 인원(7)        0~1
공격 타입      덱의 그 타입 공급 / 출격 인원(7)        0~1
키워드 없음    0
```

> **v2 로 고쳤다(2026-08-18) — 이 브랜치의 가장 중요한 수정이다.** v1 은 분모를
> 「그 덱이 가장 많이 가진 것」(최댓값 정규화)으로 적었는데, 그러면 **공급이
> 평평한 덱에서 한 명짜리 축도 1.0** 이 된다. 축이 흩어진 덱 11 은 모든 축이
> 1~2명이라 거기 있는 모든 키워드가 「완벽히 맞는다」로 잡히고, 하필 그 덱이
> `w_등급` 을 정하는 유일한 덱이라 저울추가 통째로 어긋난다. 분모는 **덱과
> 무관한 고정된 자**여야 한다 — 출격 인원이 그것이다.
>
> 인원은 표에서 되계산할 수 없다(아무도 안 대는 축이 있으면 표의 합은 인원과
> 다르다). 그래서 `DeckSupply.fieldSize` 로 따로 들고 다니고, 후보 셋 JSON 에도
> 적어 저울추가 페이지와 같은 자로 셈하게 한다.
>
> **PR-B 를 여는 사람에게:** `lib/engine/v2` 의 `fitOf` 를 넓힐 때 최댓값
> 정규화를 쓰면 이 수정이 되돌아간다. 분모는 출격 인원이다.

**분모를 같은 모양으로 둔다** — 축과 공격 타입 둘 다 출격 인원으로 나눈다.
한쪽만 다른 자로 재면 두 갈래를 `w_적합` 하나로 못 덮는다.

지금 `fitOf` 가 축에 대해 하는 것과 같은 셈을 공격 타입으로 넓힌다. 공격
타입 공급은 2단계가 만든 `SupplyTables.attackType` 이 이미 들고 있다.

**`exclusive` 는 `fit` 에 곱하지 않고 따로 뗀다.** 지금은 `fit × (전용 ? 1 :
0.5)` 라 키워드가 없으면 전용 여부가 아예 안 보인다. 별도 항으로 빼면
「전용인데 키워드가 없는 기프트」도 값을 갖고, 표본이 `w_전용` 을 직접 정한다.

### 4.4 `tier` 를 어떻게 넣나

```
tier 1~5 → (tier - 1) / 4     0 ~ 1
EX(없음) → 1.0
```

0~1 로 맞춰야 `fit` 과 같은 자로 잴 수 있다. EX 2건은 5등급 위이지만 5등급도
2건뿐이라 갈라 봐야 표본이 안 나온다 — 1.0 으로 묶는다.

## 5. 무엇이 바뀌나

**PR 을 둘로 가른다.** 표본을 받아 보기 전에 엔진을 고치기로 정해 두면, 표본이
「모양이 틀렸다」고 말할 때 되돌릴 것이 많아진다. 확인 덱의 정확도가 크게
낮으면 합이 아니라 다른 모양이어야 한다는 뜻이고, 그 답은 표본이 오기 전에는
알 수 없다.

### PR-A — 표본과 저울추 (엔진을 안 건드린다)

```
scripts/rank/{fit,pairs,grid,pick,squad,fusion,types}.ts
                                  DB 를 모르는 순수 함수. 표본 전에도 검사가 돈다
scripts/rank-deck.ts              덱 열하나를 짜고 덱마다 세 무더기를 고른다 (DB)
scripts/rank-page.ts              표본 수집 페이지를 만든다
scripts/fit-weights.ts            격자 탐색 · 갈래별 확인 · 무더기별 정확도
src/v2/authored/gift-rank-candidates.json   후보 셋 — 판정 줄의 뜻을 정한다
src/v2/authored/gift-rank.jsonl   표본 307줄 — 사람이 매긴 것
docs/.../2026-08-17-...-결과.md    저울추 후보와 정확도
```

**후보 셋을 함께 커밋한다.** 판정 줄은 `{덱, giftId, bucket}` 뿐이라 그 뜻(편성 ·
축 공급 · `fireable` · 무더기)을 정하는 것이 없으면 저울추를 재현할 수 없다.

`lib/engine/v2` 를 **한 줄도 안 고친다.** 격자 탐색은 `fitOf` 와 같은 셈을
스크립트 안에서 다시 해서, 엔진을 안 건드리고도 값을 낼 수 있다. 실서비스
추천은 이 PR 동안 지금 그대로 돈다.

**`rank-deck.ts` 와 `rank-page.ts` 는 한 번 쓰고 마는 도구다.** 저장소에
남기는 이유는 표본을 다시 짤 일이 생겼을 때 같은 기준으로 짜기 위해서다.

### PR-B — 엔진에 붙인다 (결과가 쓸 만할 때만)

```
lib/engine/v2/score.ts            fitOf 가 공격 타입을 잰다 · valueOf 가 생긴다
                                  scorePack 이 valueOf 를 쓴다
lib/engine/v2/weights.ts          저울추 셋. 표본에서 나온 값과 그 근거
lib/engine/v2/rank-golden.test.ts 표본을 재현하는지 검사
```

`ScoreGift` 에 `tier: number | null` 이 는다. `PackScore` 의 칸은 안 바뀐다 —
화면이 그 모양에 매여 있다.

**PR-A 의 결과를 보고 PR-B 를 열지 정한다.** 확인 덱 정확도가 맞춘 덱보다 크게
낮으면 이 PR 은 안 연다.

**이 문서의 계획은 PR-A 만 다룬다.** PR-B 는 결과를 본 뒤 따로 쓴다.

```
단위    덱 짜기 · 기프트 고르기 · 합성 관계 · 바구니 제약 세기 · 격자 탐색

못 찾으면 진짜 표본에서도 못 찾는다.

### PR-B

```
단위    valueOf 가 합인지 · tier 정규화 · 공격 타입 fit · exclusive 분리
        **fit 의 분모가 출격 인원인지**(§4.3) — 최댓값 정규화면 회귀다

**골든은 「전부 맞힌다」가 아니라 실측 수치를 적는다.** 사람의 판정에도 흔들림이
