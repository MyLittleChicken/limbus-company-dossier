# 팩 점수 모형 v2 — 도그푸딩 피드백 설계

> 상태: 설계 / 2026-08-09
> [PR #30](https://github.com/MyLittleChicken/limbus-company-dossier/pull/30) 이 팩 점수를 세웠고, 사용자가 실제로 돌려 보고 넷을 지적했다.
> 이 문서가 그 넷을 닫는다. 선행 설계는 [`2026-08-09-pack-scoring-design.md`](2026-08-09-pack-scoring-design.md).
> 이 문서의 수치는 3층 hard · 화진 덱 실측이다.

## 1. 무엇이 잘못됐나

도그푸딩이 넷을 찾았다. **넷 다 데이터는 이미 있고 우리가 안 쓴 것이다.**

```
③ 중심 조건 미충족   기프트 자신의 축이 죽었는데 곁가지로 A 등급이 되어 근거로 뜬다
②  전용 기프트       「이 팩에서만 얻는 것」과 범용을 같은 무게로 센다
①  합성 경로         층이 서로 이어지는데 층마다 독립으로 평가한다
④  근거 조회         팩당 상위 5만 보여 왜 이 순위인지 검증할 수 없다
```

의존 순서가 있다. ③이 잘못된 항을 걷어내야 ②·①의 효과를 판단할 수 있고, ④가 그 전부를 눈으로 확인하는 자리다.

## 2. ③ 켜질 수 없는 것을 최우선으로 걸러낸다

### 2.1 사용자가 찾은 것

```
9120 죽음바라기 · 키워드 Burst · 등급 A · 충족 2/3
  Rupture Skill Used      axis BURST      미충족(확정)   ← 이 기프트의 존재 이유
  Deployment Position     deployment      충족(가능)     곁가지
  Single-Coin Skill Used  coin single     충족(가능)     곁가지
```

화진 덱은 파열을 하나도 공급하지 않는다. **그런데 곁가지 둘이 충족돼 A 등급이 되고 「이 팩의 볼거리」로 뜬다.** 7층 「LCB 정기검진」 2위, 노멀 5층 1위 팩의 근거가 이것이었다.

**한 건이 아니다** — 3층 A등급 96 중 14가 제 축이 미충족이다.

### 2.2 판정은 옳았다. 셈이 틀렸다

엔진은 `BURST 미충족·확정` 을 정확히 냈다. 문제는 `liveOf` 가 조건 셋을 **같은 무게로** 세고, 화면이 그 결과를 근거로 내민 것이다.

**규칙: 하나라도 「확정 불가」인 조건이 있으면 그 기프트는 켜질 수 없다.** 비율을 세기 전에 먼저 판정한다.

```
fireable = reasons 에 (verdict === 'unsatisfied' && certainty === 'certain') 이 하나도 없다
fireable === false  →  이 기프트는 F 에도 L 에도 C 에도 안 들어간다.  목록에는 남는다
```

**목록에는 남긴다**는 것이 중요하다. 등급 분포(`tally`)는 지금처럼 전량을 세고, 근거 모달(7절)이 「이건 켜질 수 없다」를 이유와 함께 보여준다. **점수에서 빼는 것과 사용자에게 숨기는 것은 다르다** — 왜 빠졌는지 볼 수 없으면 판정을 검증할 수 없다.

**이것이 조건 결합 문제의 출구다.** 「셋 중 둘이 맞았다」가 AND 인지 OR 인지는 데이터가 답하지 않지만(4절), **「하나가 확정 불가라 못 켠다」는 결합을 몰라도 참이다.**

### 2.3 붕괴하지 않는다 — 실측으로 확인했다

「너무 많이 빠지면 순위가 다시 안 갈린다」가 이 규칙의 위험이었다. 쟀다.

```
후보 기프트 230 · 확정 불가 조건을 가진 것 57 (25%)
              A 96 → 29 가 빠진다 · B 90 → 28 · C 44 → 0

팩별 생존율
  98%  타오르는 일렁임 (1위)
  98%  어지러운 파동   (2위)
  82%  잠겨드는 아림   (꼴찌)
  최소 75% · 최대 98%
```

**덱에 맞는 팩은 거의 안 잃고 안 맞는 팩이 더 잃는다.** 변별을 평평하게 만들기는커녕 강화한다.

### 2.4 배치는 자리에 누가 있는지까지 본다

**거울 던전은 편성과 전투 편성 순서까지 정하고 진입한다.** 그러므로 「1번·2번 인격」은 추측이 아니라 **확정 판정**이다.

지금 배치 판정은 자리 **번호가 편성 크기 안에 드는지**만 본다.

```
evaluate.ts 현행
  const filled = gate.slots.filter((s) => s >= 1 && s <= squad.field.length).length;
  return { verdict: filled > 0 ? 'satisfied' : 'unsatisfied', have: filled, need: 1 };
```

7명 편성이면 `slots {1,2}` 는 무조건 충족이다. **누가 그 자리에 있는지 안 본다.**

**바꾼다** — 자리 조건이 있는 기프트는 그 자리 인격만을 분모로 삼아 **같은 기프트의 다른 조건 전부**를 판정한다. 축뿐 아니라 죄악·공명·코인·스킬 갈래까지 같다. 자리 조건 자체는 「그 자리가 편성에 있나」로 남는다.

```
9120 죽음바라기 · slots {1,2}
  지금   BURST 를 편성 전체(7명)에서 센다
  이후   BURST 를 1·2번 자리 인격만으로 센다
```

데이터는 있다 — `gift_trigger_param.slots` 가 `{1}` · `{1,2}` · `{1,2,3}` 을 담고, 배치 트리거를 가진 기프트 63 중 23이 축 조건도 함께 갖는다.

**죽음바라기는 2.2 규칙만으로 이미 잡힌다**(전체 BURST 공급이 0이라 확정 불가다). 자리 인지가 필요한 것은 **축이 전체로는 공급되는데 그 자리에는 없는** 더 미묘한 경우다 — 파열 인격이 3번 자리에만 있는 덱에서 `slots {1,2}` 기프트가 켜진다고 판정하는 사고를 막는다.

### 2.5 이것은 추론이다 — 기록해 둔다

`gift_effect` 와 `gift_trigger` 를 잇는 표가 **없다.** 어느 조건이 어느 효과를 켜는지 데이터가 답하지 않는다.

자리 조건을 같은 기프트의 다른 조건에 씌우는 것은 **효과 문구를 읽은 판단**이다(「[편성 1번, 2번 인격 전용 효과] 파열 위력 … 을 부여하는 공격 스킬의 …」). 데이터가 보장하지 않는다. 틀린 것으로 드러나면 되돌릴 자리다.

## 3. ② 전용 기프트를 무겁게 센다

### 3.1 실측

```
전용 기프트 230종
  172  팩 풀에 있다
   58  팩 풀에 없다  →  그중 38 이 합성으로만 만든다

팩당 전용은 3~7개 (기프트 74~81 중).  5~9%
```

**②와 ①은 같은 이야기다.** 「이 팩을 골라야만 재료가 생기고, 그 합성 결과가 이 팩 전용」인 구조다. 사용자가 든 서릿발 발자국이 정확히 그것이다.

### 3.2 5%가 팩을 고르는 이유다

나머지 90%는 어느 팩에서나 나오므로 선택의 근거가 못 된다. **선행 설계에서 밀도가 안 갈리던 것과 정확히 같은 구조다** — 아무 데서나 켜지는 조건이 변별을 죽였듯, 아무 데서나 얻는 기프트가 적합도를 뭉갠다.

**새 저울추를 만들지 않는다.** 기존 「한 단계 멀어지면 반」을 재사용한다.

```
fit(기프트) = 덱의 그 축 공급 / 최대 축 공급  ×  (전용 1.0 · 범용 0.5)
```

## 4. ① 합성 경로 — 층을 잇는다

### 4.1 사용자가 든 예가 데이터로 확인된다

```
공장 자동화(팩 1004, 1·2층)     → 귀신 들린 신발 9408
사랑할 수 없는(팩 1005, 1·2층)  → 얼어붙은 아우성 9409
                                 합성 → 서릿발 발자국 9410
9410 은 gift_pack 에 0건 — 합성이 유일한 경로다
```

**지금 점수는 층마다 독립으로 평가해 이것을 전혀 모른다.** 그리고 합성으로만 얻는 59종은 팩 풀에 없어 **점수에 한 번도 안 잡힌다.**

### 4.2 런 이력을 추적할 필요는 없다

이미 보유 기프트를 입력받는다. 한 층의 팩 선택에 답할 질문은 이렇게 좁혀진다.

```
레시피 R 의 필요 재료 M(R)
보유 O · 이 팩 P

도달 = |M(R) ∩ (O ∪ P)| / |M(R)|,  모자란 수만큼 반씩 깎는다
       완성(0개 모자람)  1.0
       1개 모자람        0.5
       2개 모자람        0.25
```

**1층부터 작동한다.** 보유가 0이어도 「이 팩을 고르면 재료 하나를 잡아 다음 층에 노릴 수 있다」를 반영한다.

### 4.3 재료의 가치는 결과물의 가치다

사용자의 말 그대로다 — 「자체는 별다른 효과를 누릴 수 없거나 약해도 그 조합 결과가 효과를 누릴 수 있다면 그것도 고려 대상」.

```
C = Σ (도달 × 결과물의 fit)  /  후보 수
    합은 **레시피 68건 전부**를 훑는다.  도달이 0 이면 안 더해지므로
    실질적으로 이 팩이 기여하는 것만 남는다

    분모가 레시피 수가 아니라 **후보 기프트 수**인 것에 유의한다 —
    F 와 같은 분모라야 둘을 더할 수 있고, 큰 팩이 유리해지는 것도 막는다
```

결과물의 값을 그대로 쓰므로 **새 저울추가 안 는다.** 결과물이 덱과 안 맞으면 `fit` 이 낮아 자동으로 작아진다.

**결과물의 `fit` 에도 전용/범용 가중이 걸린다**(3.2절). 합성 결과물 60종 중 38이 전용이므로 이 항은 대체로 무겁게 매겨진다 — 그것이 의도다.

### 4.4 합성 구조 실측

```
재료로 쓰이는 기프트  135
2단 합성            8건 (재료가 자기도 합성 결과물)
레시피당 재료 칸     2 / 3 / 4  (중앙 3)
선택지형 칸          1건 — fusion_slot_option 에 재료 7종
```

**거의 평면이다.** 2단 합성 8건은 1단으로만 본다 — 연쇄를 2홉으로 자른 것과 같은 이유이며, 3단계 앞을 내다본 근거는 사람이 검증할 수 없다.

**선택지형 칸은 「그중 하나라도 있으면 찬 것」으로 센다.** `material_id` 가 null 인 칸이 그것이고 실측 1건이다.

## 5. 모형

```
기프트마다 먼저 묻는다 — 켜질 수 있나
  하나라도 확정 불가 → fireable = false.  F 에도 L 에도 C 에도 안 들어간다

F  Σ fit(기프트) / 후보 수
   fit = 덱의 그 축 공급 / 최대 축 공급 × (전용 1.0 · 범용 0.5)
   자리 조건이 있으면 그 자리 인격만으로 센다

L  Σ 살아있는 조건 / Σ 전체 조건        선행 설계와 같다

C  Σ (합성 도달 × 결과물 fit) / 후보 수   새 항

점수 = (F + C) × L
```

**안쪽은 합, 바깥은 곱인 이유** — `F` 와 `C` 는 둘 다 「이 팩에서 무엇을 얻나」를 답한다. 직접 얻는 것과 합성으로 얻는 것이다. `L` 은 「그것이 내 편성에서 도나」라 성격이 다르므로 곱한다.

### 5.1 저울추는 여전히 하나의 규칙이다

```
확정 1.0 / 가능 0.5        선행
연쇄 1홉 1.0 / 2홉 0.5      선행
전용 1.0 / 범용 0.5         신규
합성 도달 1.0 / 0.5 / 0.25  신규
```

넷 다 **「한 단계 멀어지면 반」** 이다. 손으로 정한 새 상수는 없다.

## 6. 구조

```
lib/engine/v2/profile.ts     countInSlots(refKind, refId, slots)
                             counts 가 이미 Map<key, Set<인격id>> 라 자리와 교집합만 하면 된다

lib/engine/v2/evaluate.ts    기프트의 자리 범위를 먼저 모아 다른 조건에 씌운다
                             GiftVerdict 에 fireable: boolean

lib/engine/v2/fusion.ts      신규.  순수 함수
                             reachOf(recipe, have): number  — 0 · 0.25 · 0.5 · 1.0

lib/engine/v2/load.ts        fusion_recipe · fusion_slot · fusion_slot_option

lib/engine/v2/score.ts       fireable=false 는 후보에서 뺀다
                             fitOf 에 전용/범용
                             fusionOf(...) → C.  점수 = (F + C) × L

lib/queries/canonical/recommend.ts   전용 표와 합성 데이터를 넘긴다
app/[locale]/recommend/page.tsx      말줄임표 → 근거 모달
```

**엔진 파일을 건드린다.** 선행 PR 은 `evaluate.ts` · `profile.ts` 를 안 건드렸는데 이번엔 판정 자체가 바뀌므로 불가피하다. 검사 411줄이 회귀를 잡는다.

## 7. ④ 근거 모달 — 계측기다

**대충 만든다. 나중에 제거한다.** 사용자가 보기 편한 것이 유일한 기준이다.

```
지금    팩당 A등급 상위 5
이후    말줄임표 → 모달 → 그 팩 기프트 전량 + 각각의 판정 근거 전부
```

담을 것 — 기프트마다 등급·`fireable`·조건별 충족/미충족/확정여부, 전용 여부, 합성 도달. **왜 0.0 인지가 보여야 한다.**

레이아웃·색·간격에 공들이지 않는다. 정보 제공 화면의 디자인 작업은 별도 세션의 몫이고, 이 모달은 그 대상이 아니다.

## 8. 지어내지 않는 자리

```
fireable 인 후보가 0      점수 0.  나누기 0 을 안 만든다
자리 조건의 자리가 빔      편성이 그 자리보다 짧으면 그 조건은 미충족·확정
레시피 재료가 0개인 것     도달 0.  1.0 으로 치지 않는다
선택지형 칸               하나라도 있으면 찬 것으로 센다
결과물이 이미 보유         그 레시피는 안 센다 — 다시 만들 이유가 없다
2단 합성                  1단으로만 본다.  중간 결과물을 재료로 안 친다
```

## 9. 검증

```
골든 3회      단계마다 뜬다 — 각 변화의 효과를 따로 귀속시킨다
              ① 켜질 수 없음 뒤  ② 전용 뒤  ③ 합성 뒤
상식 검사      죽음바라기가 0.0 인가
              서릿발 발자국이 보유{9408} + 공장 자동화 에서 도달 1.0 으로 잡히나
순수 검사      countInSlots · reachOf · fireable 판정.  DB 없이 돈다
붕괴 감시      팩별 생존율.  지금 75~98%.  크게 떨어지면 순위가 안 갈린다
앱 확인        모달이 뜨고 전량이 보이는지
```

**골든을 단계마다 뜨는 것이 이 PR 의 핵심 검증이다.** 점수를 세 군데서 바꾸므로 한 번에 대조하면 어느 변경이 순위를 움직였는지 알 수 없다.


## 11. 구현 결과

### 11.1 골든 단계별 순위 이동 — 이 PR 의 핵심 산출물

점수를 세 군데서 바꾸므로(③ 켜질 수 없음 → ② 전용 → ① 합성) 한 번에 대조하면 어느 변경이 순위를 움직였는지 알 수 없다. 그래서 단계마다 떴다.

**읽는 법** — 전용 가중(t5)이 적합도를 절반으로 깎는다. 팩당 전용이 5~9%뿐이고 나머지 90%는 범용이므로(3.1절) 이건 정상이다. 합성(t7)이 그 절반의 상당 부분을 되돌린다 — 합성 결과물 60종 중 38이 전용이라(4.3절) `C` 항이 전용 가중을 우회해 값을 되찾아 주기 때문이다.

### 11.3 구현 중 밝혀진 것 넷

**① `fireable` 이 조건 결합 문제의 출구임이 실제로 확인됐다.** 2.2절의 주장 — 「셋 중 둘이 맞았다」가 AND 인지 OR 인지는 몰라도 「하나가 확정 불가라 못 켠다」는 결합을 몰라도 참이다 — 이 코드로 성립했다. `evaluate.ts` 의 `fireable` 계산과 `score.ts` 의 `pool = gifts.filter(g => !g.owned && g.fireable)` 필터가 검사 20건(evaluate) + 2건(score) 으로 뒷받침된다.

**② 자리 한정이 실제로 잡은 것은 죽음바라기가 아니었다.** 죽음바라기(9120, slots `{1,2}`)는 「하나라도 미충족·확정이면 못 켠다」 규칙(2.2절)만으로 이미 잡힌다 — 이 덱은 파열을 편성 전체로도 하나도 안 준다. 자리 한정(2.4절)이 실제로 잡은 것은 **9143·9210(slots `{4,5}`)** 이다. 무기 갈래(pierce · blunt)가 편성 전체로는 공급되는데(3번 자리 pierce, 6번 자리 blunt) 4·5번 자리에는 없어, 자리 한정을 씌우기 전에는 「편성 전체로 세어」 충족으로 잘못 판정됐다. 골든 검사(`golden.test.ts`)의 「전부 충족」이 95 → 93 으로 바뀐 것이 이 둘이다.

이 사례는 처음엔 슬롯 번호를 죽음바라기의 것(`{1,2}`)으로 잘못 옮겨 적었다가, 리뷰 과정에서 DB 재조회로 9143·9210 이 실제로는 `{4,5}` 임을 정정했다(Task 3 보고서 참조). 결론(자리 한정 전에는 과대 판정됐다)은 그대로 옳았고, 틀린 것은 슬롯 번호의 서술뿐이었다. **2.4절이 말한 「더 미묘한 경우」의 실제 사례다** — 축이 전체로는 공급되는데 그 자리에는 없는 경우.

**③ 빌드가 한 번 깨졌다.** `score.ts` 가 `reachOf` 를 값으로 끌어오며 `import { reachOf, type Recipe } from './fusion.js'` 처럼 값 import 에 `.js` 확장자를 썼다. `tsc` 는 이걸 `.ts` 로 풀어 통과시키지만 Next 의 Turbopack 번들러는 못 풀어 `Module not found: Can't resolve './fusion.js'` 로 빌드가 죽었다. `lib/engine/v2/` 의 다른 상대 import 는 전부 `import type` 이라 컴파일 때 지워져 번들러에 안 닿으므로 이 함정이 여태 안 드러났다 — `score.ts` 가 그 디렉터리에서 처음 나온 값 import 였다.

**`npm run typecheck` 로는 절대 안 잡히는 종류다.** 두 도구의 모듈 해석기가 다르기 때문이다. 값 import 를 확장자 없이(`from './fusion'`), 타입 import 만 `.js` 로 분리해 고쳤다. 같은 문제가 있는 다른 자리를 `lib/engine/v2/` 전체에서 찾았으나 없었다. 계획서의 Global Constraints 에 **「`lib/engine/v2/` 를 건드린 태스크는 반드시 `npm run build` 를 돌린다」** 를 추가해 재발을 막았다.

**④ 점수가 옳아도 화면이 틀릴 수 있다.** 점수(`score.ts`)·검사(500건)·골든(23건)이 전부 통과한 뒤에도, 사용자가 원래 신고한 증상이 화면에 그대로 남아 있었다 — `app/[locale]/recommend/page.tsx` 의 상위-5 미리보기가 `p.gifts.filter(g => g.grade === 'A')` 로만 뽑아 `fireable` 을 안 걸렀다. `grade` 는 「조건이 전부 판정 가능한가」만 보고 `fireable` 은 「확정 미충족이 있는가」를 별도로 보므로, grade A 이면서 fireable:false 인 기프트(죽음바라기가 정확히 이 경우)가 미리보기에 섞여 들었다. 점수 수치(`(F+C)×L`) 자체에는 죽음바라기가 안 들어갔지만, 화면의 「이 팩의 볼거리」 줄에는 그대로 노출된 것이다.

앱을 실제로 띄우는 단계(Task 9)가 이것을 잡았다. `shown = p.gifts.filter(g => g.grade === 'A' && g.fireable).slice(0, 5)` 로 고쳐 재확인하니 3층·7층·1~11층 전부에서 모달 밖 죽음바라기가 0 이 됐다. 선행 PR(#30) 에서도 같은 자리(`[] ?? x` 함정)가 버그를 잡았다 — **질의를 직접 부르는 것과 화면이 부르는 것은 다르다.**
