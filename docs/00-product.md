# 제품 정의 (Product Definition)

> 상태: 초안 v0.2 / 최종 수정 2026-07-26
> 이 문서는 "무엇을, 누구를 위해, 왜 만드는가"를 다룬다. 기술 선택은 `docs/adr/`의 결정 기록에서 정한다.

## 1. 한 줄 정의

림버스 컴퍼니 **거울 던전** 플레이어가 현재 자신의 런 상황(파티 구성, 보유 E.G.O 기프트)을 기준으로
**다음 층에서 어떤 팩을 고를지** 판단할 수 있게 돕는 정보·추천 서비스.

## 2. 문제 인식

제품은 다음 전제 위에 선다. 각 전제의 검증 항목은 8절에 정리한다.

- 거울 던전 15층 클리어의 난이도는 E.G.O 기프트와 팩 선택의 숙련도에 크게 좌우된다.
- 숙련된 유저는 어떤 기프트가 어떤 조합에서 강한지 이미 체득했고, 15층을 반복적으로 클리어한다.
- 컨텐츠를 어려워하는 유저는 같은 선택지 앞에서 판단 근거를 갖지 못한다. 선택의 영향이 층마다 누적되어 실패로 이어지고, 실패 후에도 원인을 특정하기 어려워 학습으로 연결되지 않는다.
- 인격·E.G.O·E.G.O 기프트·팩의 개별 정보는 이미 커뮤니티에 존재하나, "현재 상황에서 무엇을 고를지"의 형태로는 정리되어 있지 않다.

제품이 해결하려는 것은 정보의 부재가 아니라, 숙련 유저와 그렇지 않은 유저 사이의 **판단 근거 격차**다.

## 3. 대상 사용자

**거울 던전에 입장 가능한 모든 유저.** 성격이 다른 두 부류가 있다.

- **거울 던전 컨텐츠를 어려워하는 유저** — 제품의 존재 이유.
- **거울 던전 컨텐츠에 숙련된 유저** — 효율화 도구이자, 피드백 루프에 양질의 로그를 공급하는 쪽(7절 리스크 5).

이 대상 설정에서 따라 나오는 설계 제약 두 가지:

1. 추천은 점수와 함께 **선택의 근거**를 제시한다. 사용자의 판단력이 서비스를 쓰는 동안 향상되어야 한다.
2. UI 표기는 게임 내 표기와 1:1로 대응한다. 용어를 모르는 사용자를 전제한다.

## 4. 제품 구조

아래는 완성 시점의 구조다. 각 구성요소를 어느 단계에서 만드는지는 5절에서 정한다.

```
        게임 패치
            │  (외부 입력: 신규 인격·E.G.O·기프트·팩)
            ▼
   ┌──────────────────┐
   │  [1] 정보 제공    │  인격 / E.G.O / 기프트 / 팩
   └────────┬─────────┘
            │ 선택지의 정적 속성 (양쪽에 공급)
     ┌──────┴───────────────────┐
     ▼                          ▼
┌──────────────┐ 현재 런 상태  ┌──────────────────┐
│[2] 런 상태   │──────────────▶│    [3] 추천       │
│    입력      │               │ 층별 팩 추천+근거 │
│ 파티·보유    │◀──────────────│                  │
│ 기프트·현재층│   추천 결과    └────────▲─────────┘
└──────┬───────┘                        │
       │                                │
       │ 종료된 런의 결과 + 실제 선택   │ 갱신된 가중치
       ▼                                │
   ┌───────────────────────────┐        │
   │  [4] 피드백 루프           │────────┘
   │  로그 집계 → 가중치 학습   │
   └───────────────────────────┘
```

- **[1] 정보 제공**: 인격, E.G.O, E.G.O 기프트, 팩의 조회·검색. [2]와 [3] 양쪽이 참조하는 토대.
- **[2] 런 상태 입력**: 진행 중인 런의 상태(파티 구성, 보유 기프트, 현재 층)를 사용자가 입력한다.
- **[3] 추천**: [2]의 상태를 [1]의 데이터와 매칭해 다음 층 팩 선택지를 점수화하고 근거를 제시한다.
- **[4] 피드백 루프**: 종료된 런의 결과와 실제 선택을 집계해 [3]의 가중치를 갱신한다.

### 구성요소별 구축 단계

| 구성요소 | 구축 단계 |
| --- | --- |
| [1] 정보 제공 | 1단계(데이터), 2단계(조회 화면) |
| [2] 런 상태 입력 | 4단계 |
| [3] 추천 | 3단계(엔진), 4단계(사용자 대상 제공) |
| [4] 피드백 루프 | 이후 버전 |

### 갱신 경로

| 대상 | 갱신 주체 | 주기 |
| --- | --- | --- |
| [1] 정보 DB | 게임 패치 (현재는 수동 갱신) | 패치 시점 |
| [3] 추천 가중치 | 플레이 로그 | 상시 |

두 경로는 서로 독립적이다.

### [2]가 내보내는 데이터

| 데이터 | 소비처 | 시점 |
| --- | --- | --- |
| 진행 중인 런의 상태 | [3] 추천 | 실시간 |
| 종료된 런의 결과와 실제 선택 | [4] 피드백 루프 | 런 종료 후 |

제품의 차별점은 [3]에 있다. [1]만으로는 기존 위키와 기능이 같다. [4]는 [3]의 정확도를 시간에 따라 개선한다.

## 5. 단계별 범위

순서의 근거: 추천 엔진은 인격·E.G.O·E.G.O 기프트·팩 데이터와 그 사이의 관계 정의 위에서 성립한다. 플레이 로그는 초기 추천의 전제가 아니라 이후 개선의 재료다.

| 단계 | 내용 | 이 단계의 목적 |
| --- | --- | --- |
| 1 | 데이터베이스 구축 (인격 / E.G.O / E.G.O 기프트 / 팩) | 데이터 확보와 스키마 확정 |
| 2 | 웹페이지 구축 | 화면 구조, 디자인 기반, 데이터 조회 UI 등 서비스의 기반 마련 |
| 3 | 추천 엔진 구축 | 1단계 데이터를 바탕으로 엔티티 간 관계와 메카닉을 정의하고, 팩 선택지를 점수화하는 로직 구현 |
| 4 | 추천 시스템 구축 | 사용자의 런 상황을 입력받아 엔진과 매칭하고, 추천과 근거를 제시하는 흐름 완성 |

3단계와 4단계의 구분: **엔진**은 상황이 주어졌을 때 점수와 근거를 산출하는 로직이고, **시스템**은 사용자가 실제 플레이 중 자신의 상황을 입력해 그 결과를 받는 서비스 형태다.

### 데이터 취급

데이터는 정적으로 관리한다. 자동 수집·갱신 파이프라인은 현재 범위에 없으며 이후 버전에서 지원한다.

### 플레이 기록 취급

플레이 기록은 **서버에 수집한다.** 식별은 쿠키 기반 식별자로 하며, 계정 없이 브라우저 단위로 기록이 귀속되고
이후 버전에서 로그인 계정으로 확장한다.

서버 수집은 피드백 루프([4])의 전제다. 여러 사용자의 기록을 집계해야 추천 가중치를 갱신할 수 있고,
6절 성공 기준의 클리어율 비교도 집계된 기록 위에서만 측정된다.
저장소 결정은 `docs/adr/01-data-storage.md`에 있다.

### 이후 버전 (범위 미확정)

- 플레이 기록 수집 및 로그 기반 추천 가중치 개선
- 로그인 계정 — 쿠키 기반 기록의 확장
- 데이터 갱신 파이프라인

### 하지 않을 것

- 로그인 기능 (현재 범위 밖. 이후 버전에서 확장)
- 소셜 기능
- 모바일 네이티브 앱
- 그 외 이 문서에 정의되지 않은 모든 기능

## 6. 성공 기준

- **1단계** (미충족): 명시된 게임 버전 기준으로 인격·E.G.O·E.G.O 기프트·팩 데이터가 누락 없이 구축된다. 데이터의 기준 버전을 함께 기록한다.
  — 네 엔티티의 수량(184 · 110 · 456 · 117)은 수집 시점 실측과 일치하고 값도 전수 대조에서 불일치 0이며, `MD7` · 스냅샷 `2026-07-25`을 기록했다.
  **다만 인격 스킬 12종이 정본에 정의가 없어 적재되지 않는다.** "누락 없이"를 아직 충족하지 못한다.
- **2단계**: 구축된 데이터 전체를 웹에서 조회·검색할 수 있다.
- **3단계**: 임의의 런 상황을 입력했을 때 엔진이 팩 선택지를 점수화하고, 그 점수를 데이터상의 관계로 설명한다.
- **4단계**: 사용자가 자신의 런 상황을 입력하고 추천과 근거를 받는 흐름이 층당 15초 이내에 끝난다. (15초는 잠정 기준이며 4단계 설계 시 재검토한다.)
- **이후 버전**: 추천을 따른 런의 클리어율이 따르지 않은 런보다 유의하게 높다. 측정에는 플레이 기록 수집이 선행되어야 한다.
- **최종**: 거울 던전을 어려워하는 사용자의 15층 클리어율이 서비스 이용 전후로 상승한다. 최우선 지표이며, 다른 지표가 개선되더라도 이 값이 오르지 않으면 목표 미달로 판정한다. 이 지표 역시 플레이 기록 수집이 선행되어야 측정할 수 있다.

## 7. 핵심 리스크

1. **데이터 확보와 유지보수** — 인격·E.G.O·기프트·팩 데이터를 어디서 얻고 패치마다 어떻게 갱신할 것인가. 직접 입력, 클라이언트 리소스 파싱, 커뮤니티 자료 활용 중 무엇을 쓰든 정확성·합법성·운영비의 트레이드오프가 있다. 미해결 시 제품 전체가 성립하지 않는다. 현재 범위에서는 정적 데이터를 수동으로 관리하므로 패치가 누적될수록 갱신 비용이 증가한다.
2. **입력 마찰** — 4단계는 판이 진행 중인 사용자가 런 상태를 수동 입력하는 것을 전제한다. 마찰이 크면 추천 시스템이 실사용되지 않고, 이후 버전의 피드백 루프도 재료를 얻지 못한다. 스크린샷 인식 등 입력 자동화는 난이도가 높아 현재 범위 밖이다.
3. **초기 추천 품질** — 3단계 엔진은 플레이 로그 없이 데이터상의 관계 정의만으로 구축된다. 따라서 초기 추천의 품질은 관계와 메카닉 정의의 정확도에 전적으로 의존한다.
4. **공개 서비스 부담** — 2차 창작물 이용 정책, 서버 비용, 장기 운영 책임. 플레이 기록을 쿠키 기반으로 **식별**하므로 초기에는 계정 정보를 다루지 않는다. 다만 쿠키는 브라우저·기기 단위이므로 기기 변경이나 쿠키 삭제 시 해당 기록이 단절된다. 이 한계는 로그인 확장으로 해소한다.
5. **로그 공급자와 수혜자의 불일치** — 가중치 학습에 가장 유용한 것은 성공한 런의 로그, 즉 숙련 유저의 플레이다. 그러나 숙련 유저에게는 이 서비스의 필요성이 낮다. 반대로 서비스를 필요로 하는 쪽의 로그는 실패 비중이 높아 학습 신호의 성격이 다르다. 숙련 유저가 서비스를 사용할 별도의 유인(기록 관리, 통계, 빠른 입력 등)이 없으면 이후 버전의 피드백 루프가 작동하지 않는다.

## 8. 확인이 필요한 전제

- **게임 사양** — 층별 팩 테이블을 데이터로 확인했다. hard는 1, 2, 3, 4, 5, 6–10, 11–15 구간이고 normal은 1–5다.
  즉 문서 전반의 "15층"은 hard 난이도 기준이다. 다만 게임 클라이언트와 직접 대조하지는 않았고,
  게임 업데이트로 변경될 수 있다(`03-data-provenance.md` 5절).
- **2절 전제의 사실 여부** — 숙련도에 따른 클리어율 차이가 실제로 존재하는가, 크기는 어느 정도인가.
- **추천의 최소 단위** — 팩 단위인가, 팩에 포함된 개별 기프트 단위인가.
- **입력 범위** — 사용자가 런 상태를 어느 수준까지 입력할 의사가 있는가 (파티 구성만인가, 보유 기프트 전부인가).
