# v1 편성 UI 구조 — 분석

> 상태: 분석 / 작성 2026-07-29
> 대상: `../limbus-mirror-tracker-v1/prototype/index.html` (2,198행 단일 파일)
> 목적: v1이 편성창을 **어떤 구조로 짰는가**를 밝히고, 현행 `/squad` · `/recommend` 와 대조한다.
> 엔진·데이터 축은 [`v1-engine-data-model.md`](v1-engine-data-model.md) 가 다룬다. 이 문서는 화면만 본다.
> 이 문서는 구현을 바꾸지 않는다. 개선 판단의 근거로만 쓴다.

## 1. 한 줄 결론

**칸은 결과만 보이고 고르는 일은 모달로 뺐다.**

v1의 편성 칸은 초상 카드다. 눌러야 전면 모달이 열리고, 거기에 필터 다섯 축과 인격 카드 격자가 있다.
현행 우리 편성은 칸 안에 `<select>` 를 넣어 **표시와 선택을 한 자리에 겹쳤다.**

이 차이가 나머지 전부를 낳는다. 칸이 표시 전용이면 초상·희귀도·키워드를 실을 수 있고,
모달이 선택 전용이면 필터와 스킬 타일을 실을 수 있다.

## 2. 레이아웃 — 3열

```
172px            1fr                      340px
┌──────────┐  ┌──────────────────┐  ┌──────────────┐
│ 편성      │  │ 수감자 12 그리드   │  │ 편성 프로필   │
│ 덱 레일 10 │  │ 6열 × 2행         │  │ 키워드 비중   │
│ (고정)     │  │                  │  │ 공격 타입     │
│           │  │                  │  │ 죄악 공급/수요 │
└──────────┘  └──────────────────┘  └──────────────┘
```

| 폭 | 배치 |
| --- | --- |
| 기본 | `172px 1fr 340px` |
| ≤1180px | `150px 1fr` — 프로필이 아래 전폭으로 내려간다 |
| ≤760px | 1열 |

그리드는 6열 → `≤900px` 4열 → `≤580px` 3열이다. **12는 6·4·3으로 모두 나누어떨어진다** —
어느 폭에서도 마지막 행이 비지 않는다.

## 3. 칸 하나의 구성

```
┌──────────────────┐
│ ★                │  좌상 희귀도
│      초상         │  aspect-ratio 1 / 1.08
│                  │  우상 기믹(특수) 아이콘 세로 나열
│ ●●              │  좌하 키워드 아이콘
├──────────────────┤
│ 이상             │  수감자명 (금색 소형)
│ W사 L3 정리 요원   │  인격명
├──────────────────┤
│ E.G.O ●○○○○     │  등급 5칸 원형
└──────────────────┘
```

**버튼이 둘이다.** 초상+이름 영역(`.sbtn`)과 E.G.O 스트립(`.egostrip`)이 각각 버튼이며,
어느 쪽을 눌렀는지가 모달의 첫 탭을 정한다(`openPicker(sid, 'id' | 'ego')`).

세 가지가 이 칸에서 특히 눈에 띈다.

**E.G.O 빈 칸이 흐린 등급 아이콘을 깐다.** 비어 있음을 공백이 아니라 자리로 표현한다.
등급이 다섯이라는 사실이 항상 보이고, 우리 문서가 말하는 결손과 부재의 구분과 같은 취지다
(`05-ui-foundation.md` 6.1). ALEPH 자리도 같은 규칙으로 늘 비어 있다.

**좌측 금색 바 = 기본 인격이 아닌 것을 배정한 칸.** 12칸을 훑을 때 손댄 자리가 구분된다.
원래는 "배정됨" 표시였는데 기본 인격이 항상 장착되면서 모든 칸에 붙어 의미를 잃었고,
그래서 뜻을 바꾼 흔적이 주석에 남아 있다.

**초상 배경이 그 인격의 첫 스킬 죄악 색을 쓴다**(`--sc: var(--sin-{죄악})`).
색만으로 판별하게 두지 않고 아이콘과 함께 쓴다.

## 4. 선택 모달

한 모달이 인격과 E.G.O 를 함께 맡는다. 상단에 탭 둘, 각 탭 옆에 개수가 붙는다.

```
┌─ 문장 · 이상 / Yi Sang ─────────────────── ✕ ┐
├ 인격 16 │ E.G.O 3/5 ─────────────────────────┤
│ 키워드 [침잠][출혈]  죄악 [우울][색욕]…        │  .mtools (max-height 150px)
│ 소속   [전체 (21) ▾]              [필터 해제 3] │
├────────────────────────────────────────────┤
│ ┌────────┐ ┌────────┐ ┌────────┐            │  .mbody 카드 격자
│ │초상 이름 │ │        │ │        │            │
│ │스킬 타일 │ │        │ │        │            │
│ │HP SPD   │ │        │ │        │            │
│ │키워드 칩 │ │        │ │        │            │
│ └────────┘ └────────┘ └────────┘            │
├────────────────────────────────────────────┤
│ 희귀도·코인 수·… 모두 실제 게임 데이터   16 / 16 │
└────────────────────────────────────────────┘
```

시트는 `min(1180px, 100%) × min(860px, 88vh)` 고정이고 도구 영역만 따로 스크롤한다.
목록이 길어져도 필터가 화면 밖으로 밀리지 않는다.

### 4.1 필터 축

| 탭 | 축 | 형태 |
| --- | --- | --- |
| 인격 | 키워드 · 죄악 · 공격 타입 · 특수(기믹) | 칩 |
| 인격 | 소속 | **드롭다운** |
| E.G.O | 등급 · 키워드 · 죄악(비용) · 공격 타입 | 칩 |

**소속만 드롭다운인 이유가 코드 주석에 있다** — 수감자당 20종을 넘어 칩으로 깔면 목록 공간을 다 먹는다.
축의 카디널리티가 형태를 정한 것이며, 우리 인격 목록 화면이 소속 93종을 다루는 문제와 같은 건이다.

결합은 **그룹 간 AND, 그룹 내 OR** 이다. 우리 `components/filters.tsx` 와 같은 규칙이다.

**필터 선택지를 그 수감자의 풀에서 만든다.** 전역 목록을 깔지 않고 `pool` 을 훑어
실제로 등장하는 값만 칩으로 낸다(`has()`). 눌러도 0건인 필터가 생기지 않는다.

### 4.2 카드가 담는 것

**인격** — 초상 + 희귀도 / 이름(한국어 + 영어 보조) / **스킬 타일 행**(코인 표시 포함) + 방어 타일 /
HP · 속도 범위 · 출시일 / 키워드 칩. 키워드가 없으면 `키워드 없음` 을 적는다.

**E.G.O** — 이미지 / 이름 / 등급 아이콘 + 기본 여부 / **비용 pip** / 각성 죄악 · 키워드 칩.

E.G.O 카드의 비용 pip 가 이 모달에서 가장 특징적이다.

```js
`<span class="costpip ${(sup[k] || 0) < v ? 'short' : ''}"
   title="${SINKO[k]} ${v} 필요 · 팀 공급 ${sup[k] || 0}">`
```

**팀의 죄악 공급보다 요구량이 많으면 붉게 칠한다.** 고르는 자리에서 자원 수급을 바로 본다.
같은 등급에 이미 장착된 것이 있으면 카드에 `taken` 을 붙여 "누르면 교체됩니다" 를 알린다 —
등급당 하나라는 제약을 막지 않고 표기로 처리한다.

## 5. 편성 프로필 패널

세 구획이며 편성 탭과 트래커 진입 화면이 같은 함수(`profileHTML`)를 공유한다.

| 구획 | 내용 | 산출 |
| --- | --- | --- |
| 키워드 비중 | 막대 + 수치 | 인격의 표시 키워드 카운트 |
| 공격 타입 · 코인 가중 | pip | **덱 매수가 아니라 코인 수 합** |
| 죄악 자원 | 공급(스킬) vs 수요(E.G.O) | 스킬 죄악 카운트 · 장착 E.G.O 비용 합 |

세 번째가 v1 편성창의 고유한 값이다.

```
분노  ████████░░░░  3 / 5   ← 붉은 행: 수요 5 > 공급 3
```

수요가 공급을 넘는 행을 붉게 칠하고 하단에 문장을 붙인다 —
*"붉은 항목은 장착 E.G.O 비용이 팀의 해당 죄악 스킬 수보다 많습니다."*

**우리 화면에 대응물이 없다.** 우리 `/recommend` 의 죄악 패널은 공급만 낸다.

## 6. 덱 레일과 저장

10칸 **고정**이다. 추가·삭제가 없다.

슬롯 하나가 `{ name, code }` 이며 **`code` 는 덱 코드 문자열**이다. 인격·E.G.O·편성 순서를 전부
담으므로 저장 형식이 그것 하나로 끝난다. 편집할 때마다 현재 슬롯 코드에 자동 반영한다(`commitDeck`).

첫 실행 시드는 슬롯 1이 데모 편성, 나머지 9가 기본 인격 편성이다.

```js
function persistDecks(){
  try{ localStorage.setItem(DECK_KEY, JSON.stringify({sel, decks})); }catch(e){}
}
```

**저장 실패를 삼킨다.** 프라이빗 모드·용량 초과가 조용히 지나간다.
우리 `lib/storage` 는 `Result` 로 돌려주고 화면이 배너와 잠금으로 처리한다(`07` 4.2).

## 7. 출전과 백업

**v1 편성 탭에는 출전 구분이 없다.** 있는 것은 편성 순서(`state.order`)뿐이고,
출전 7은 트래커 진입 화면에서 순서 앞 7명으로 잡힌다.

```js
function resolveDeployed(deck, deployedIds) {
  if (deployedIds && deployedIds.length) { … }
  return deck.length <= DEPLOY.onfieldMax ? deck : deck.slice(0, DEPLOY.onfieldMax);
}
```

엔진은 `deployedIds` 를 받을 수 있게 열려 있으나 화면이 넘기지 않는다.
v1 자체 진단도 같은 자리를 짚었다 — *"남은 격차는 출격7/백업5 구분과 로드아웃 보너스 표시"*
(`docs/05-design/screen-analysis.md` 1절).

우리는 `StoredDeck.deployed` 를 편성에 직접 두고 체크박스로 받는다. **이쪽이 앞선다.**

## 8. 현행 편성 화면과의 대조

| 항목 | v1 | 우리 (`/squad` · `DeckEditor`) |
| --- | --- | --- |
| 축 | 수감자 12 | 같음 ✅ |
| 칸 표현 | 초상 카드 격자 (6열) | 세로 목록 + `<select>` |
| 인격 선택 | 모달 + 필터 5축 + 스킬 타일 | 드롭다운. **필터 없음** |
| E.G.O 선택 | 같은 모달의 둘째 탭 + 필터 4축 | 등급별 `<select>` 5개 |
| E.G.O 빈 자리 | 흐린 등급 아이콘 | 빈 `<option>` (`ZAYIN —`) |
| 인격 미배정 | **불가** — 기본 인격이 항상 장착 | `null` 허용 |
| 편성 프로필 | 3구획 (죄악 공급/수요 포함) | **없음** — `/recommend` 에만 |
| 출전 지정 | 없음 (순서 앞 7) | 체크박스 ✅ |
| 덱 목록 | 10칸 고정 레일 | 칩 + 새 덱 · 삭제 |
| 저장 형식 | 덱 코드 문자열 | `StoredDeck` 구조체 |
| 덱 코드 | 저장 형식 그 자체 | 입출력 전용 |
| 참조 결손 표기 | 없음 | 「데이터에 없음」 ✅ |
| 저장 실패 처리 | `catch(e){}` | 배너 + 편집 잠금 ✅ |
| 반응형 | 3단 → 2단 → 1단 | 단일 열 |

**우리가 앞선 넷은 유지 대상이다** — 출전 지정 · 참조 결손 표기 · 저장 실패 처리 · 인격 미배정 허용.
넷 다 "결손을 지어내지 않는다"(`02-data-model.md` 6절)에서 나온 것이며 v1에 없다.

**v1이 앞선 넷은 가져올 후보다** — 초상 격자 · 필터 모달 · 등급 자리의 시각화 · 편성 프로필.

## 9. 추천 화면의 대조

| | v1 트래커 탭 | 우리 `/recommend` |
| --- | --- | --- |
| 흐름 | 진입(편성 고정 + 난이도) → 층 → 팩 → 기프트 → 다음 층 | **없음.** 덱 고정, 층만 주소로 |
| 덱 | 편성 탭에서 고른 것 | `HWAJIN_DECK` 상수 |
| 팩 제시 | 그 층 후보 전체 격자 + 검색 | 상위 3 |
| 점수 근거 | 사유 코드 목록 | **항목별 분해 + 근거 문자열** ✅ |
| 제외 팩 | `dropped` 배열 | 이유와 함께 노출 ✅ |
| 기프트 획득 | 목록에서 다중 선택 → 확정 | 없음 |
| 조합 진행 | 패널로 상시 표시 | `fusionProgress = 0` (미구현) |
| 덱 특성 표시 | 프로필 패널 (편성 탭과 공유) | 상태·죄악·소속 패널 |

우리 화면이 이미 나은 것은 **근거의 구조**다. `components` 를 항목별로 펼치고 `reasons` 를
평가가 남긴 근거에서 옮겨 적는다. v1은 사유 코드(`ENABLER` · `SYNERGY_LIFT`)만 배열로 담고
화면 문자열은 따로 만들었다.

없는 것은 **런 진행 전체**다. `07-recommendation-system.md` 5.2가 그 흐름을 이미 설계했고,
v1의 트래커 탭이 그 설계의 실물 선례다.

## 10. 결합할 때 갈리는 것

v1을 그대로 옮길 수 없게 만드는 것이 셋이다.

### 10.1 질의 범위 — 모달의 필터가 데이터를 요구한다

v1은 전체 데이터가 메모리에 있어 `IDENTITIES[id].sk` 를 즉시 읽는다.
우리는 Prisma 질의이고 계산을 서버에 둔다(`adr/05-web-serving.md` 3.3).

현행 `listSquad` 가 인격에 싣는 것은 `id` · `rarity` · `season` · 이미지 · 이름뿐이다.
**필터 다섯 축 중 넷이 실리지 않는다** — 키워드(상태) · 죄악 · 공격 타입 · 소속.

| 축 | 필요한 관계 | 현행 `listSquad` |
| --- | --- | --- |
| 키워드 | `IdentityStatus` → `statusKeyOf` | 없음 |
| 죄악 | `Skill.affinity` | 없음 |
| 공격 타입 | `Skill.atkType` | 없음 |
| 소속 | `IdentityAffiliation` | 없음 |
| 특수(기믹) | `IdentityStatus` 의 `ammo` · `protection` | 없음 |

`lib/engine/load.ts` 의 `loadIdentities` 가 이미 다섯을 전부 만든다.
**같은 모양을 두 번 만들지 않는 것이 판단의 갈림길이다** — 엔진의 `Identity` 를 편성 화면이
그대로 쓸지, 화면용 질의를 따로 넓힐지.

### 10.2 기본 인격 개념을 들여오지 않는다

v1은 `BASE_ID[sinner]` 를 두고 해제 불가로 잡았다. 게임의 LCB 수감자가 항상 보유이기 때문이다.

우리 `StoredDeck` 은 `identityId: null` 을 허용한다. **바꾸지 않는 편이 낫다.**
편성하지 않은 칸을 표현할 수 있어야 덱 코드의 "편성 순서 0"(`07` 7.1)과 대응하고,
"12명을 다 채우지 않은 덱"도 엔진이 계산한다(`07` 8절).

v1의 시각 표기(기본 인격 칸은 테두리를 죽인다)는 **다른 뜻으로 재사용할 수 있다** —
비어 있는 칸과 채운 칸의 구분.

### 10.3 E.G.O 는 아직 점수에 없다

v1도 편성 프로필에서 죄악 공급과 E.G.O 비용을 대조하는 데까지만 갔고 팩 점수에는 넣지 않았다.
우리도 같은 자리다(`07` 5.1이 화면에 그 사실을 적는다).

**다만 프로필의 대조는 엔진 변경 없이 지금 가능하다.** 죄악 공급은 `deckFeature.sinSupply` 로
이미 있고, E.G.O 비용은 `listSquad` 가 이미 `costs` 로 싣는다. 둘을 나란히 두는 것은 화면 일이다.

점수 반영은 별개이며 `07` 9.1이 시그니처를 미리 정해 두었다.

## 11. 엔진 쪽 요약

[`v1-engine-data-model.md`](v1-engine-data-model.md) 12절이 순서를 매겨 두었다. 다시 적지 않는다.

화면 작업과 맞물리는 것만 옮긴다.

| 항목 | 화면과의 관계 |
| --- | --- |
| 기프트를 공급원에 포함 + 폐포 | 프로필의 공급 수치가 보유 기프트에 따라 움직인다 |
| 파생 엣지 (`mechanics.json`) | 프로필에 저SP·치명타 축이 생긴다 |
| 공급을 수치 합으로 | 프로필 막대가 인원 수가 아니라 수치가 된다. **데이터가 먼저다** |

셋째는 `Skill` 에 상태 부여 수치가 없어(`prisma/schema.prisma` — `IdentityStatus` 는
`(identityId, statusId)` 쌍뿐이다) 지금 데이터로는 되지 않는다.

## 12. 이 문서가 보증하는 범위

**보증하는 것** — 2026-07-29 시점 `../limbus-mirror-tracker-v1/prototype/index.html` 과
현행 `app/[locale]/squad/page.tsx` · `components/deck-editor.tsx` ·
`app/[locale]/recommend/page.tsx` · `lib/queries/squad.ts` · `lib/storage/schema.ts` 를
직접 읽고 구조를 옮겼다. 인용한 코드와 CSS 값은 원문이다.

**보증하지 않는 것** — v1 화면을 브라우저로 띄워 보지 않았다. 레이아웃 서술은 CSS 와 렌더 함수를
읽은 결과이며 실제 표시를 확인한 것이 아니다. v1의 배치가 게임 편성창과 얼마나 맞는지도
판단하지 않았다 — 그쪽 `docs/05-design/screen-analysis.md` 가 위키·커뮤니티 서술을 근거로 적어둔
것이며 실측 스크린샷 대조는 일부에만 있다.
