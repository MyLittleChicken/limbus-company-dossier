# ADR-07. `canonical` 은 승격으로만 바뀐다 (Canonical Promotion)

> 결정 2026-08-04 · 구현 완료 2026-08-04
> 설계 [`docs/superpowers/specs/2026-08-04-pipeline-cutover-design.md`](../superpowers/specs/2026-08-04-pipeline-cutover-design.md)
> 선행 [ADR-06 3스키마 데이터베이스](06-three-schema-database.md) · [ADR-02 파이프라인](02-pipeline.md)

## 1. 맥락

ADR-06 은 `canonical` 을 **재생성 대상**으로 두었다. `npm run v2:canonical` 이 매번
TRUNCATE 하고 `raw` 에서 다시 굽는다. 안전장치는 스키마 경계였다 — `app` 만 그 범위
밖에 있으면 사람이 채운 값은 안 날아간다.

**그 전제가 깨졌다.** `canonical` 이 코드로 재현할 수 없는 값을 갖기 시작했다.
지금 94테이블 152,399행 중 상당 부분은 판정·저작·위키 대조의 결과이고, 그중 일부는
`raw` 에 없다. 재적재는 그것을 **지우는 일**이 된다.

```
지금까지   canonical = f(raw, 코드).  매번 다시 굽는다
이제부터   canonical 은 승격으로만 바뀐다.  파괴적 적재의 대상이 아니다
```

`raw` 는 그대로 매 패치마다 받는다. `canonical` 은 잃지 않는다.

## 2. 결정

### 2.1 이름 돌려쓰기로 간다

새 판을 옆 스키마에 굽고 이름만 바꿔 다는 것이 가장 단순하지만, **그렇게 못 한다.**
Prisma `multiSchema` 가 `@@schema("canonical")` 을 SQL 에 **정적으로 굳힌다.**

```sql
SELECT COUNT(*) FROM (SELECT "canonical"."axis"."id" FROM "canonical"."axis" …) AS "sub"
```

`?schema=` 접속 인자는 `multiSchema` 가 아닐 때의 기본 스키마만 정한다. 적재기를
`wip` 스키마로 돌리려면 모델 94개를 `@@schema("wip")` 로 한 벌 더 둬야 하고,
그것은 유지가 안 된다. 검사 203건과 골든도 전부 `prisma.<model>` 로 읽으므로 같은
제약을 받는다.

**따라서 새로 굽는 것은 `canonical` 이라는 이름으로 서 있는 순간이 필요하다.**
살아있는 판을 먼저 옆으로 치우고(`canonical_hold`), 그 이름 자리에 새로 굽고,
다 구운 것을 `wip` 으로 옮기고, 살아있는 판을 제자리로 되돌린다.

별도 데이터베이스(대조가 덤프 비교가 된다)나 적재기를 Prisma 에서 떼기(전면 수정)는
쓰지 않는다. 후자는 증분 파이프라인을 짤 때 자연히 필요해지면 그때 한다.

### 2.2 정정은 성격으로 가른다

```
값 정정     app.field_override    「mj 가 틀렸다」.  데이터고, 자주 늘고, 근거가 외부다
구조 저작    코드                  규칙이고, 테스트가 필요하다
```

경계를 3절에 예로 못 박는다. 이것이 이 ADR 의 실질이다 — 다음에 정정할 게 생겼을 때
어디에 넣을지가 이 문서 하나로 정해져야 한다.

### 2.3 이전 판은 하나만 남긴다

`canonical_bak` 하나. 다음 승격이 이전 `bak` 을 지운다.

**두 판 이상 거슬러 올라갈 일이 없다.** 34 MB × N 이 쌓이고, 되돌리기는 승격 직후에
하지 한 달 뒤에 하지 않는다. 더 오래 남겨야 하면 그건 백업의 일이지 스키마의 일이
아니다.

### 2.4 맨손 적재는 검사로 거부한다

**권한이 아니라 검사로 막는다.** 적재기가 시작할 때 `canonical` 에 **행**이 있으면
거부한다.

```
npm run v2:canonical 맨손 실행   →  거부.  「canonical 에 이미 행이 있다」
npm run v2:build 안에서 실행     →  통과.  build 가 먼저 옆으로 치웠다
```

`REVOKE` 를 안 쓴 이유는 **접속 계정이 하나**라서다. 적재기와 마이그레이션과 화면이
같은 역할로 붙으므로 적재기만 골라 막을 수 없고, 막으면 마이그레이션도 같이 막힌다.
검사는 이유를 말해 주고 우회로를 알려 준다.

**조건은 테이블 수가 아니라 행 수다.** 처음엔 테이블 존재로 쟀는데, `v2:build` 3단계
(DDL) 직후는 `canonical` 이 테이블 94개·행 0개다 — 테이블로 재면 갓 구운 빈 판까지
걸려 `v2:build` 가 안에서 적재기를 못 부른다. 위험의 실체는 "테이블이 있다"가 아니라
**"데이터가 있다"**이다(`hasAnyRow`, `EXISTS` 로 직접 확인 — `pg_stat_user_tables`
추정치는 ANALYZE 시점에 따라 틀려서 안 쓴다). 이 결정은 조건이 행 기준일 때만
성립한다 — 다시 테이블 수로 되돌리지 않는다.

> 중간에 환경변수로 가드를 우회하는 안이 나왔다가 리뷰에서 기각됐다. **가드에 구멍을
> 내는 것**이기 때문이다. 우회로가 아니라 조건이 원래 이래야 맞았다.

## 3. 정정은 어디에 사는가 — 경계

새 정정이 생기면 **먼저 이 판별을 한다.**

| | 값 정정 | 구조 저작 |
| --- | --- | --- |
| 사는 곳 | `app.field_override` | 코드 |
| 판별 | `raw` 의 **한 필드**가 틀렸고, 옳은 값을 안다 | 값 하나가 아니라 **규칙**이고, 테스트로 지켜야 한다 |
| 근거 | 외부 대조(위키·게임 확인). 문서에 남는다 | 우리가 정한 어휘·예외. 테스트에 남는다 |
| 늘어나는 속도 | 자주. 패치마다 | 드물게. 모델을 바꿀 때 |
| 재적재 | 마지막 단계에서 다시 덮인다 | 적재기가 매번 다시 적용한다 |

**값 정정 — `app.field_override`**

```
gift 9212 · 9249 · 9427 · 9428 · 9431 의 hardOnly = false
「위키가 맞고 mj 가 틀렸다」.  근거 docs/audit/wiki/03-gift.md §2
```

9427·9428 의 소속 팩 Crawling Abyss 가 노멀 4F·5F 에 나오므로 노멀 합성이 된다.
mj 단독으로 `hardOnly` 를 붙인 오적재다. 이런 것은 **한 필드에 옳은 값이 하나** 있고
근거가 우리 밖에 있으므로 데이터로 둔다. 지금 5행이며 늘어난다.
([`docs/audit/wiki/03-gift.md`](../audit/wiki/03-gift.md) §2)

**구조 저작 — 코드**

```
EGO_GRANTED        어느 E.G.O 가 축을 주는가              src/v2/canonical/identity-axis.ts
TRIGGER_EXCEPTION  「Bloodfiend Identities」는 소속이      src/v2/canonical/axis.ts
                   아니라 유닛 키워드다
TOKEN_EXCEPTION    토큰 → 참조 대상 매핑의 예외            src/v2/canonical/gift-trigger-param.ts
분모 어휘           무엇을 분모로 세는가(출전·편성·대기)     src/v2/canonical/gift-trigger-param.ts
```

넷 다 **필드 하나를 고치는 게 아니라 해석 규칙을 정하는 것**이다. 「Bloodfiend
Identities」를 소속으로 붙이면 어느 한 행이 틀리는 게 아니라 그 이름이 나오는 모든
곳이 틀린다. 그래서 코드에 있고 테스트가 지킨다.

**애매하면 이렇게 가른다.** 같은 판단을 다음 패치에서 또 해야 하는가 — 그렇다면
규칙이다(코드). 이 id 하나로 끝나는가 — 그렇다면 값이다(`field_override`).

## 4. 결과

### 4.1 명령 넷

```
npm run v2:build      살아있는 판을 옆으로 → 빈 canonical 에 적재 → 검사 203건 →
                      새 판을 wip 으로, 살아있는 판을 canonical 로 복귀
npm run v2:diff       wip vs canonical 대조.  읽기 전용 트랜잭션
npm run v2:promote    한 트랜잭션 교체 + app 재조준.  이전 판은 canonical_bak
npm run v2:rollback   역연산.  canonical_bak 으로 되돌린다
```

`v2:canonical` 은 남긴다 — `v2:build` 가 안에서 부른다. 맨손 실행만 2.4가 막는다.

### 4.2 실측

```
canonical    94테이블 · 152,399행       승격 전후 동일(이번 판은 차이 0)
raw           43,270 개체              안 건드림
app.field_override    5행              안 건드림
public       52테이블                   안 건드림
검사 203건 · 테스트 432건 전부 통과(건너뜀 12)
```

승격은 한 트랜잭션이다. 실패하면 통째로 되돌아간다 — `canonical_bak` 을 일부러
실패시켰을 때 **같은 oid(50458)로 되살아났다.** 새로 만들어진 것이 아니라 그
객체가 돌아온 것이고, 그것이 원자성의 증거다.

**FK 재부착이 승격의 검사 역할을 한다.** `app.run_gift` 가 새 판에 없는 기프트를
가리키면 트랜잭션이 통째로 되돌아간다. 콜라보 기프트가 원본에서 빠지는 일이
실재하므로 이 실패는 실제로 일어날 수 있고, **일어나야 옳다.**

## 5. 구현에서 나온 것 — 코드만 봐서는 알 수 없는 둘

### 5.1 수동 `BEGIN`/`COMMIT` 은 못 쓴다

Prisma 커넥션 풀은 **동시 호출에서 커넥션을 가른다**(실측 pid 51430/51431/51432).
`$executeRawUnsafe('BEGIN')` 은 문장이 끝나면 커넥션을 곧바로 반납하므로 다음 문장이
같은 커넥션이라는 보장이 없다. 갈리면 뒤따르는 DDL 이 **자동 커밋으로 나가고**,
설계 3.4 가 「존재하지 않는다」고 못 박은 반쯤 바뀐 상태가 그때 생긴다.

`prisma.$transaction(async (tx) => …)` 은 콜백이 도는 동안 커넥션을 점유한다.
**그것만이 안전하다.** 설계 6.2 의 SQL 문장 순서는 그대로 옳고, 그 순서를
`$transaction` 안에서 내야 한다는 것이 여기서 더해지는 제약이다.

같은 판단이 `v2:diff` 의 `SET TRANSACTION READ ONLY` 에도 서 있다 — 세션이 아니라
**트랜잭션에** 건 이유가 이것이다.

### 5.2 통짜 `pg_depend` 로는 스키마 밖 의존을 못 센다

`DROP SCHEMA … CASCADE` 는 밖에서 들어온 의존을 말없이 같이 지운다. 지우기 전에
세야 하는데, `pg_depend` 를 통째로 훑고 `pg_identify_object` 로 스키마를 알아내는
방법은 **쓸 수 없다.**

```
pg_rewrite  (뷰의 재작성 규칙)   schema = NULL
pg_attrdef  (컬럼 기본값)        schema = NULL
```

그 카탈로그들에 namespace 컬럼이 없고 소유 테이블만 가리키기 때문이다. 스키마가
`NULL` 이면 "밖"과 구분이 안 되므로 **안쪽 의존이 전부 밖으로 잡힌다** — 실측에서
멀쩡한 `canonical_bak` 이 기본값 수십 건으로 걸렸다.

대신 설계 3.2 가 꼽은 **세 갈래(FK · 컬럼 타입 · 뷰)를 따로 물어 `UNION`** 한다.
살아있는 `canonical` 에 돌리면 설계 3.2 가 적은 정확히 그 셋이 나오고, 사람이 읽기도
낫다. ([`src/v2/schema-ops.ts`](../../src/v2/schema-ops.ts) `outsideDependents`)

> DDL 생성에 `prisma migrate diff --from-url` 을 못 쓰는 이유는 설계 9절에 있다
> (P4002 또는 `DROP` 105건). 여기 옮기지 않는다.

## 6. 이 PR 이 검증하지 못한 것

숨기면 다음 사람이 검증된 줄 안다. **넷이다.**

**차이가 있는 새 판을 승격해 본 적이 없다.** 검증에 쓴 `wip` 은 전부 `canonical` 과
완전히 동일했다(행 152,399=152,399 · 인덱스 130=130 · 제약 179=179). 선검사 거부
경로는 인위적으로 태워 확인했으나(app FK 선검사를 임시로 비틀어 실패시킴), 차이가
있는 판이 통과하는 경로의 첫 실전은 **다음 패치**다.

> **그리고 그 첫 실전에서 `v2:diff` 는 값 변경을 못 본다.** diff 가 보는 것은 테이블
> 집합 · 행수 · 네 테이블의 id 집합 · `app` FK 무결성뿐이다. 3절이 이 프로젝트의
> 전형이라고 못 박은 **`gift.hardOnly` 정정 같은 컬럼 값 변경은 id 도 행수도 그대로라
> diff 에 한 줄도 안 나온다.** diff 요약이 그 범위를 스스로 찍지만(설계 7절과
> 어긋나지 않는다 — diff 는 원래 값을 안 본다), 「차이가 있는 판의 첫 승격」과
> 「diff 가 그 차이의 가장 흔한 종류를 못 본다」가 **같은 순간에 겹친다.** 첫 패치
> 승격 때는 diff 만 믿지 말고 무엇을 고쳤는지 손으로 확인해라.

**enum 재지정이 실제 값을 옮기는 것을 못 봤다.** `app.run` 이 0행이라
`USING …::text::canonical."Difficulty"` 가 값을 옮기는 것도, 새 판에서 라벨이
사라졌을 때 실패하는 것도 실측하지 못했다. 문장이 도는 것만 확인했다.

**교체는 `ACCESS EXCLUSIVE` 락을 잡는다.** 지금은 앱이 `public` 을 읽으므로 무해하다.
**앱 전환 뒤에는 승격이 짧게 앱을 멈춘다** — 설계 6.1 이 적어 둔 그 창이다. 그때는
전체 재적재가 아니라 증분이라 이 절차를 안 쓰게 되지만, 안 쓰게 되는 것이 확인되기
전까지는 열린 문제다.

**`outsideDependents` 는 FK · 컬럼 타입 · 뷰 셋만 본다.** 지금 스키마에 함수·트리거·
도메인이 하나도 없어 충분하다(저장소 전체 확인됨). **쓰기 시작하면 같이 늘려야 한다**
— 특히 함수 시그니처가 `canonical` 타입을 쓰는 경우, 지금 질의는 그것을 못 본다.

### 6.1 다음 승격 전에 해야 할 일 — 원본 판 덤프

**다음 `v2:promote` 가 이 브랜치 이전의 원본 판을 영구히 지운다.**

지금 `canonical_bak` 에 들어 있는 것이 그 원본이다. 결정 3 에 따라 백업 세대는 하나뿐
이라 다음 승격의 트랜잭션 **첫 문장**이 `DROP SCHEMA "canonical_bak" CASCADE` 다.
DB 는 이미 승격된 상태이므로 그 한 번은 곧 온다.

```
지금        canonical 새 판 · canonical_bak 브랜치 이전의 원본 판 · wip 없음
다음 승격    canonical_bak 을 지우고 그 이름에 지금 canonical 을 넣는다
```

그 원본을 오래 보관할 것이라면 **다음 승격 전에 덤프해라.** 되돌리기는 승격 직후에
하는 것이지 한 달 뒤에 하는 것이 아니고(결정 3), 한 달 뒤를 위한 보관은 스키마가
아니라 백업의 일이다.

```
pg_dump --schema=canonical_bak …
```

**떴다 (2026-08-05).** 저장소 밖 `../limbus-db-backups/canonical_bak-2026-08-05.sql`
에 있다 — 브랜치·워크트리 정리에 휩쓸리지 않게 하려는 것이다. 덤프와 DB 실측이
94테이블 · 뷰 1 · 타입 11 · **152,399행**으로 일치한다. 복원 절차는 그 옆
`README.md` 에 적었다. 이로써 다음 승격이 `canonical_bak` 을 지워도 잃는 것이 없다.

## 7. 남은 것

**저작 표가 아직 코드에 있다.** 3절이 「구조 저작은 코드」라고 정했지만, 그것은
파이프라인이 매번 도는 동안만 성립한다. `canonical` 이 승격으로만 바뀌게 된 지금,
`EGO_GRANTED` · `TRIGGER_EXCEPTION` · `TOKEN_EXCEPTION` · 분모 어휘는 **한 번 구워진
뒤로는 아무도 다시 읽지 않는 좀비**가 된다. 코드를 고쳐도 `canonical` 이 안 바뀐다.

다음 PR 이 이것을 데이터로 내린다. 그때 3절의 표는 「어디에 사는가」가 아니라
「무엇이 규칙인가」의 기준으로 남는다 — 판별은 그대로 옳다.

```
snapshot_id 심기      canonical 이 자기 출처를 모른다.  증분의 기준점
저작 표 데이터화       위의 그것
증분 파이프라인        raw v1 vs v2 diff → 추가·변경 판정
앱 전환 · public 폐기  읽는 곳을 바꾸는 작업.  데이터는 안 바뀐다
```

## 8. 재검토 시점

- **앱이 `canonical` 을 읽기 시작할 때** — 6절 셋째(교체 락)가 그 순간 실제 문제가 된다.
- **`canonical` 에 함수·트리거·도메인이 생길 때** — `outsideDependents` 를 같이 늘린다.
- **차이가 있는 판을 처음 승격한 뒤** — 6절 첫째·둘째를 실측으로 지운다.
