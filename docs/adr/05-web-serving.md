# ADR-05. 웹 서빙 (Web Serving)

> 상태: 채택 / 결정일 2026-07-27
> 2단계(웹페이지 구축)의 화면을 **무엇으로 만들고, 어디서 계산해, 어떻게 내보내는가**를 정한다.
> 화면 요구는 `docs/05-ui-foundation.md`, 저장 형식은 `01-data-storage.md`, 질의 계층은 `02-pipeline.md`에서 정했다.
> 이 문서의 수치는 1단계 적재 결과와 2026-07-25 스냅샷 실측이다.

## 1. 맥락

`01-data-storage.md` 10절이 **서빙 형식 · 계산 위치 · 웹 프레임워크 · 배포 환경** 넷을 2단계 착수 전으로 미뤘다.
이 문서가 그 넷을 다룬다.

결정의 폭은 선행 ADR이 이미 좁혀 두었다.

| 제약 | 출처 |
| --- | --- |
| PostgreSQL이 진실의 원천이고, 런 기록도 같은 저장소로 들어온다 | `01-data-storage.md` 4절 |
| **웹 서비스 코드도 Prisma Client를 ORM으로 쓴다** | `02-pipeline.md` 2절 |
| 게임 데이터는 패치마다 전체 재생성한다 | `02-pipeline.md` 5절 원칙 2 |
| 표시 문자열이 전체 산출물의 79%(7,498 KB)다 | `03-localized-text.md` 1절 |
| 상세 화면 867개, 팩 하나에 기프트 최대 188, 설명문 전문 검색, 로케일 전환 | `05-ui-foundation.md` 9절 |
| 이미지 애셋 4,737개를 저장소에 커밋하지 않는다 | `01-data-source.md` 7절 |

두 번째 제약이 특히 크다. 웹 서비스가 Prisma Client를 쓴다는 것은 **Node.js 런타임을 전제**하므로,
서버 없는 구성은 이미 선택지에서 빠져 있다.

## 2. 결정

| 항목 | 결정 |
| --- | --- |
| 웹 프레임워크 | **Next.js (App Router)** |
| 서빙 형식 | **요청 시점 서버 렌더.** 사전 렌더하지 않는다 |
| 계산 위치 | **서버.** 질의·필터·정렬·검색·로케일 해석을 전부 서버에서 한다 |
| 데이터 접근 | **Prisma Client로 PostgreSQL을 직접 질의한다.** 읽기 전용 산출물을 따로 만들지 않는다 |
| 배포 환경 | **정하지 않는다**(3.5). 2단계의 실행 환경은 로컬이다 |

## 3. 근거

### 3.1 Next.js

`02-pipeline.md` 3.2가 Prisma를 고른 근거는 생태계의 두께였고, 같은 기준을 여기에 적용한다.
당시에는 "웹 프레임워크가 아직 미정"인 것이 그 근거의 일부였는데, 이제 그 미정이 해소되는 자리다.

- **서버 컴포넌트에서 Prisma 질의를 직접 한다.** 2단계 화면은 전부 읽기이므로 별도 API 계층이 값을 하지 않는다.
- **4단계가 같은 프레임워크에 들어온다.** 런 상태 입력은 클라이언트 상태를 갖는 인터랙션이고,
  추천 결과는 그 상태를 서버로 보내 받는 응답이다. 조회 화면과 한 프레임워크에 두면 경계가 하나 줄어든다.

### 3.2 요청 시점 서버 렌더

게임 데이터는 스냅샷마다 고정이므로 상세 867개를 빌드 시점에 렌더할 수 있다. 그럼에도 요청 시점으로 정한다.

- **데이터가 고정되는 시점이 하나다.** 사전 렌더를 섞으면 화면마다 데이터의 기준 시점이 갈린다.
  3·4단계에서 런 기록과 추천이 붙으면 **한 화면 안에 빌드 시점 데이터와 요청 시점 데이터가 공존**하게 된다.
- **서버는 어차피 필요하다.** 런 기록의 서버 수집이 확정이므로(`01-data-storage.md` 4절)
  사전 렌더는 구조를 단순하게 만드는 선택이 아니라 부하를 줄이는 최적화다. 최적화는 부하가 관측된 뒤에 얹는다.
- **데이터 갱신이 재배포와 분리된다.** 패치 시점에 파이프라인을 다시 돌리면 화면이 즉시 따라온다.
  사전 렌더는 재빌드를 요구하며, 갱신 경로가 둘로 갈린다(`00-product.md` 4절의 갱신 경로).
- **규모가 이를 감당한다.** 전체 산출물이 raw 9.4 MB이고 최대 관계가 10,115행이다.
  단일 PostgreSQL 인스턴스가 이 규모에서 병목이 되지 않는다.

### 3.3 계산 위치는 서버

- **표시 문자열 7,498 KB를 클라이언트로 보내지 않는다.** 필터·정렬·검색이 서버에서 끝나면
  브라우저가 받는 것은 그 화면에 실제로 보이는 분량뿐이다.
- **URL이 곧 질의가 된다.** `05-ui-foundation.md` 3절이 목록 화면의 필터 상태를 URL에 담기로 했다.
  서버가 그 URL을 읽어 질의하면 별도 클라이언트 상태 계층이 필요 없다.
- **로케일 폴백 판정도 서버에서 한다.** 한국어 행이 없어 영어로 폴백한 사실을 화면이 표기해야 하는데
  (`03-localized-text.md` 5절), 그 판정은 두 로케일 행을 모두 볼 수 있는 쪽에서 해야 한다.

**검색은 데이터베이스에서 수행한다.** 다만 색인 방식은 이 ADR에서 확정하지 않는다.
PostgreSQL에는 **한국어 전문 검색 사전이 내장되어 있지 않아** `tsvector`의 기본 설정으로는
한국어가 어절 단위로만 분리된다. 사용자는 "출혈"로 "출혈 피해 증가"를 찾으므로 부분 문자열 일치가 필요하다.
`pg_trgm`의 트라이그램 색인이 후보이며, 대상 규모(엔티티 867 · 설명문 7,498 KB)에서 실측해 정한다(9절).

### 3.4 읽기 전용 산출물을 따로 만들지 않는다

`01-data-storage.md` 9절이 "클라이언트 직접 조회가 필요해지면 읽기 전용 산출물을 따로 만들지 결정한다"고 남겼다.
3.3에서 클라이언트가 데이터베이스를 직접 조회하지 않기로 했으므로 **이 산출물은 필요 없다.**

정규화 JSON은 변환 결과를 사람이 검토하기 위한 중간 산출물로 남으며(`01-data-storage.md` 4절)
서빙 경로에 들어가지 않는다.

### 3.5 배포 환경을 지금 정하지 않는다

`01-data-storage.md` 10절이 배포 환경을 이 ADR의 대상으로 지목했으나 **정하지 않는다.**

- **공개 배포의 전제가 미해결이다.** Project Moon 2차 창작 가이드라인 원문을 확보하지 못했고
  (`01-data-source.md` 7·8절), `05-ui-foundation.md` 7절이 이미지 사용을 결정하면서 이 미결의 영향 범위가 커졌다.
- **근거 없이 정하면 ADR의 목적에 어긋난다.** 배포 환경은 되돌리기 어려운 결정인데
  운영 형상을 판단할 실측이 아직 없다.
- **2단계 성공 기준이 공개를 요구하지 않는다.** "구축된 데이터 전체를 웹에서 조회·검색할 수 있다"
  (`00-product.md` 6절)는 로컬 실행으로 충족된다.

2단계의 실행 환경만 정한다 — **로컬.** `compose.yaml`의 PostgreSQL과 같은 호스트에서 개발 서버를 띄운다.
공개 배포를 결정하는 시점에 별도 ADR로 다룬다.

## 4. 검토한 대안

| 대안 | 기각 사유 |
| --- | --- |
| 전부 정적 + 클라이언트 검색 | 표시 문자열 7,498 KB를 검색 인덱스로 내보내야 한다. 런 기록 수집이 확정이라 서버를 없애지도 못하므로, 정적화로 얻는 것이 서버 제거가 아니다 |
| 하이브리드 — 상세는 사전 렌더, 검색은 서버 | 데이터의 기준 시점이 화면마다 갈린다. 3·4단계에서 한 화면 안에 두 시점이 공존한다(3.2) |
| SvelteKit | 번들이 작고 경계가 단순하나 Prisma 연동 선례가 얕다. `02-pipeline.md` 3.2가 생태계 두께를 기준으로 삼았고 그것을 뒤집을 근거가 없다 |
| Astro + 아일랜드 | 2단계의 조회 화면에는 잘 맞으나 4단계 인터랙션에서 아일랜드 경계 관리 비용이 생긴다. 2단계만 보고 정할 문제가 아니다 |
| 별도 API 서버 + SPA | 2단계 화면이 전부 읽기다. 경계를 하나 더 두는 값을 하지 않는다 |

## 5. 구조

```
브라우저
   │  HTTP
   ▼
Next.js (App Router)
   │   서버 컴포넌트에서 질의
   │   필터 · 정렬 · 검색 · 로케일 해석 · 폴백 판정
   │
   │  Prisma Client
   ▼
PostgreSQL
     게임 데이터 47테이블 50,121행
     (이후 런 기록이 같은 저장소에 추가된다 — 01-data-storage.md 4절)

이미지 애셋 4,737개
     저장소에 없다. `npm run fetch -- --assets` 로 받아 정적 경로에 배치한다
```

**클론 직후에는 이미지가 없다.** `data/`를 커밋하지 않으므로(`01-data-source.md` 7절)
애셋 수집이 실행 순서에 들어간다. 애셋이 없는 상태에서도 화면은 떠야 한다
(`05-ui-foundation.md` 7.1 제약 2).

## 6. 제약

1. **웹 애플리케이션은 게임 데이터를 읽기만 한다.** 쓰기는 파이프라인의 몫이다(`02-pipeline.md` 4절).
2. **마이그레이션 러너를 쓰지 않는 결정은 유지된다**(`02-pipeline.md` 3.2). 스키마 변경은 재생성으로 처리한다.
   런 기록 테이블이 들어올 때 다시 판단한다.
3. **애셋 참조를 한 계층에 모은다**(`05-ui-foundation.md` 7.1 제약 4). 가이드라인 원문 확인 결과에 따라
   그 계층만 교체할 수 있어야 한다.
4. **웹 애플리케이션 코드는 커밋한다.** 애셋과 정규화 JSON은 커밋하지 않는다(`01-data-storage.md` 6절).

## 7. 결과

**얻는 것**

- 데이터가 고정되는 시점이 하나다. 파이프라인을 다시 돌리면 화면이 즉시 따라온다.
- 3·4단계에서 런 기록과 추천이 붙을 때 서빙 구조를 바꾸지 않는다.
- 표시 문자열 7,498 KB가 클라이언트로 나가지 않는다.
- 타입 정의가 여전히 한 벌이다(`02-pipeline.md` 3.1). 스키마를 바꾸면 화면 코드가 컴파일 단계에서 깨진다.

**감수하는 것**

- **매 요청 데이터베이스 질의가 발생한다.** 팩 상세가 최대 부하이며 기프트 최대 188개와 그 표시 문자열을 조인한다.
- 서버 없이는 화면이 뜨지 않는다. CDN 정적 배포라는 저렴한 선택지를 버린다.
- Next.js App Router의 캐시 기본값을 명시적으로 다뤄야 한다. 사전 렌더를 쓰지 않기로 했으므로
  프레임워크가 조용히 응답을 고정하지 않도록 하는 것이 구현의 책임이 된다.
- **배포 환경이 미정이라 운영 형상을 검증하지 못한다.** 로컬에서 도는 것이 공개 환경에서 도는 것의 근거는 아니다.
- PostgreSQL에 한국어 전문 검색 사전이 없어 색인 전략을 실측으로 정해야 한다.

## 8. 재검토 시점

- **팩 상세의 응답 시간이 문제가 될 때** — 사전 렌더나 캐시 계층을 부분 도입할지 판단한다.
  구조를 바꾸는 것이 아니라 얹는 것이므로 이 ADR을 뒤집지 않는다.
- **공개 배포를 결정할 때** — 배포 환경을 별도 ADR로 정한다. 가이드라인 원문 확인이 선행한다.
- **런 기록 테이블이 들어올 때** — 마이그레이션 관리 방식과 함께 본다(`02-pipeline.md` 8절).
- **검색 품질이 부족할 때** — 색인 방식 변경이나 외부 검색 엔진 도입을 판단한다.

## 9. 정하지 않은 것

**검색 색인 정정 (2026-07-27).** 3.3이 `pg_trgm` 을 후보로 두고 실측에 맡겼다. 구현 후 재보니
**색인 없이 충분하다.** `ILIKE` 순차 훑기로 기프트 이름·설명 검색이 7 ms, 상태 1,472종 검색이 11 ms 다.
검색 대상 텍스트가 작기 때문이다 — `gift_text` 1,346행 · `status_text` 약 2,900행이며,
7,498 KB 의 대부분은 검색하지 않는 스킬·코인 설명이다. 색인을 지금 넣으면 쓰지 않는 것을 유지하게 된다.
`postgresqlExtensions` 로 `pg_trgm` 과 GIN 색인을 `schema.prisma` 에 선언하면
`migrate diff` 가 그대로 뽑아내는 것은 확인했다(별도 SQL 파일이 필요하지 않다). 필요해질 때 넣는다.

| 대상 | 다룰 곳 |
| --- | --- |
| 배포 환경 · 도메인 · 운영 형상 | 공개 배포를 결정하는 시점의 별도 ADR |
| ~~검색 색인의 구체 방식~~ | **해소** — 위 정정. 색인 없이 7–11 ms |
| UI 컴포넌트 라이브러리와 스타일링 도구 | 구현 시점. 요구는 `05-ui-foundation.md` 8절 |
| 런 기록 테이블의 스키마와 쿠키 기반 식별 | 4단계 문서 |
| 추천 계산을 서버 어디에서 수행할지 | `06-recommendation-engine.md` (3단계) |
