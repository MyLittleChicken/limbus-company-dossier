# ADR-02. 변환·적재 파이프라인 (Transformation Pipeline)

> 상태: 채택 / 결정일 2026-07-26
> 원본 스냅샷을 정규화하고 PostgreSQL에 적재하는 프로그램을 **어떤 언어로, 어떤 구조로** 만드는가를 정한다.
> 산출물의 형식과 적재 대상은 `01-data-storage.md`에서 정했다. 무엇을 저장하는가는 `docs/02-data-model.md`에 있다.
> 이 문서의 수치는 2026-07-25 스냅샷을 직접 측정한 값이다.

## 1. 맥락 — 변환이 실제로 해야 하는 일

| 항목 | 규모 |
| --- | ---: |
| 입력 JSON (`entities/` 아래) | 1,664 |
| BOM 제거 | 12 |
| 소속 태그 마크업 정제 | 원본 94종(정제 후 93종) 중 5종 |
| 설명문 내부 토큰 치환 | **한국어 119종 / 1,513회 · 영어 123종 / 1,425회** |
| 동기화 델타 병합 | 인격 상세 184파일 |
| 출력 관계 행 | 12,512 |

이 작업은 **단순한 필드 이름 바꾸기가 아니다.** 두 가지가 난이도를 만든다.

**같은 개념이 소스마다 다른 키로 표현된다.** 기프트의 강화 단계가 대표적이다.
구조 소스에서는 `names[]` 배열의 인덱스이고, 로컬라이즈 소스에서는 **별도 id**다.
두 소스를 잇는 규칙은 `강화 단계 id = 기본 id + 10000 × 단계`이며, 실측이 이를 뒷받침한다 —
`enhanceable` 플래그 110개와 로컬라이즈의 10000번대 id 110개가, `names[]` 3단계 이상 107개와
20000번대 id 107개가 정확히 일치한다. 이런 규칙은 소스 어디에도 문서화되어 있지 않다.

**정제 대상에 예외가 섞여 있다.** 소속 태그의 스포일러 마크업 5종 중 2종은 닫는 태그가 깨져 있다.

```
<color=#d40000><s>Great Sister</s></color>       정상
<color=#d40000><s>Le Sette Famiglie<s></color>   닫는 태그가 </s>가 아니라 <s>
```

`<s>...</s>` 패턴에 의존하는 정제기는 이 2종을 놓친다.

따라서 파이프라인에는 **출처 간 조인 규칙과 정제 규칙을 명시적으로 두는 계층**이 필요하다.

## 2. 결정

| 항목 | 결정 |
| --- | --- |
| 언어 | **TypeScript (Node.js)** |
| 스키마 정의 | **Prisma 스키마 (`schema.prisma`)** |
| 질의 | **Prisma Client를 ORM으로 사용한다.** 적재기와 이후의 웹 서비스 코드 모두 해당한다 |
| DDL 적용 | **생성한 SQL을 직접 적용한다.** 마이그레이션 러너는 쓰지 않는다 |
| 구조 | 변환기와 적재기를 **분리한다** |

도구의 부분을 구분해서 읽어야 한다.

| 구성요소 | 사용 | 이유 |
| --- | --- | --- |
| `prisma migrate diff` | 사용 | 스키마에서 `CREATE TABLE` SQL을 생성한다. 데이터베이스에 적용하지 않고 파일로 뽑는다 |
| `prisma generate` | 사용 | 스키마에서 타입이 붙은 클라이언트를 생성한다 |
| `prisma migrate dev` · `deploy` | **미사용** | 실행 시 `_prisma_migrations` 관리 테이블이 데이터베이스에 생성된다 |
| Prisma Client (런타임) | 사용 | 적재기와 웹 서비스의 질의 |

## 3. 근거

### 3.1 TypeScript

산출물의 스키마는 변환기만 쓰는 것이 아니라 적재기, 이후의 추천 엔진, 웹페이지가 모두 읽는다.
같은 언어를 쓰면 **타입 정의가 한 벌**로 끝나고, 스키마를 바꿨을 때 소비 측이 컴파일 단계에서 깨진다.
언어가 갈리면 정의를 두 벌 유지해야 하며, 한쪽만 고친 어긋남이 실행 전까지 드러나지 않는다.

`docs/02-data-model.md`가 규정한 함정(동기화 델타 병합, 코인 수 상한 없음, 강화 단계 id 규칙)은
주석이 아니라 타입으로 박아둘 때 실제로 지켜진다.

JSON 가공 자체는 다른 선택지가 더 짧게 쓰이지만, 이 프로그램은 게임 패치 시점에만 실행된다.
작성 편의보다 **스키마 정의의 단일성**이 오래 간다.

### 3.2 Prisma를 쓰되 마이그레이션 러너는 쓰지 않는다

**ORM은 사용한다.** 웹 서비스와 적재기 모두 질의 계층이 필요하고, 스키마 정의에서 테이블 타입이
그대로 따라오는 이점이 3.1의 근거와 같은 방향이다.

Prisma를 고른 이유는 생태계다. 자료와 연동 사례가 가장 두껍고, **웹 프레임워크가 아직 미정인 상태**에서는
어느 쪽으로 정하든 선례를 찾을 수 있는 도구가 선택지를 덜 좁힌다.

피하는 것은 **마이그레이션 러너 하나**다. DDL은 `prisma migrate diff`로 SQL을 뽑아 직접 적용하며,
그 결과 데이터베이스에 `_prisma_migrations` 관리 테이블이 만들어지지 않는다.
런타임 클라이언트는 `prisma generate`로 만들어 그대로 사용한다.

이 선택으로 잃는 것은 마이그레이션 이력인데, **게임 데이터 테이블에는 이력이 필요 없다.**
`01-data-storage.md`가 정한 대로 패치마다 전체를 재생성하므로 재생성이 정상 경로다.
이력이 의미를 갖는 시점은 런 기록 테이블이 들어올 때이며, 그때 다시 판단한다(8절).

### 3.3 변환기와 적재기의 분리

`01-data-storage.md`가 정규화 JSON을 중간 산출물로 두기로 했으므로, 그 경계에서 프로그램도 나눈다.
실패했을 때 원인이 변환에 있는지 적재에 있는지 분리되고, 변환 결과를 적재 없이 검토할 수 있다.

## 4. 파이프라인 구조

```
원격 저장소 5곳 (커밋 고정)
  │
  └─ 수집기      매니페스트의 파일 목록대로 내려받고 체크섬 대조
        │
        ▼
원본 (data/entities/**)
  │
  ├─ 읽기      BOM 제거, JSON 파싱
  ├─ 정제      마크업 제거, 내부 토큰 치환 (로케일별 119~123종)
  ├─ 조인      출처 간 id 대응 (강화 단계 id 규칙 등)
  ├─ 병합      동기화 1→4 델타 누적
  └─ 추출      엔티티 / 관계 분리
        │
        ▼
  정규화 JSON  ── 파일 하나 = 테이블 하나
        │
        ▼
  적재기        DDL 적용 → COPY/INSERT → 제약 검사
        │
        ▼
  PostgreSQL
```

### 수집기 — 원본을 코드가 아니라 매니페스트로 복원한다

`data/`는 커밋하지 않으므로(ADR-01 6절) 클론 직후에는 원본이 없다. 수집기가 이것을 채운다.

**무엇을 어디서 가져올지 코드에 적지 않는다.** `data/manifest.json`이 파일 1,749개마다
출처·원격 경로·체크섬을 갖고 있고 이 파일은 git이 추적하므로, 그것이 곧 복원 레시피다.
출처 목록을 코드에 박으면 매니페스트와 어긋날 수 있고, 어긋난 사실을 알 방법이 없다.

커밋을 고정해 받으므로 몇 번을 돌려도 같은 바이트가 나온다(5절 원칙 3). 최신 데이터를 받는
동작이 아니다 — 그것은 스냅샷 재수집이며 `coverage.json`의 기준값도 함께 다시 만들어야 한다.

**줄 끝은 정규화해 비교하고 저장한다.** 상류 저장소마다 규약이 다르고(실측: `limbus-data-mj`
17개는 CRLF, 나머지는 LF), Windows의 `core.autocrlf`가 체크아웃 때 또 바꾼다.
줄 끝은 JSON의 내용이 아니므로 그것 때문에 같은 파일이 달라 보이면 안 된다.

이 때문에 매니페스트의 체크섬 필드가 둘이다.

| 필드 | 담는 것 | 용도 |
| --- | --- | --- |
| `sha256` | 최초 수집 당시 로컬 파일 그대로 | 기록. **대조에 쓰지 않는다** |
| `sha256Lf` | 줄 끝을 LF로 되돌린 내용 | 수집기의 대조 기준 |

`sha256`은 수집이 `core.autocrlf=true`인 Windows에서 이루어진 탓에 CRLF로 바뀐 바이트를
담고 있다. **상류의 내용이 아니라 수집한 기계의 산물**이라 다른 환경에서 재현되지 않는다.
1,749개 중 1,742개가 이에 해당한다.

### 파이프라인이 만들지 않는 것

이 파이프라인이 생성하는 것은 **기반 게임 데이터 테이블뿐이다.** 같은 데이터베이스에 들어가지만
소유자와 갱신 주기가 다른 데이터가 둘 더 있으며, 이 파이프라인은 그것을 건드리지 않는다.

| 데이터 | 생성 주체 | 갱신 시점 | 이 파이프라인 |
| --- | --- | --- | --- |
| 기반 게임 데이터 | 변환기 | 게임 패치 | **생성한다** |
| 추천용 저작 데이터 (가중치, 상태 파생 관계) | 사람 | 로직 수정 시 | 건드리지 않는다 |
| 런 기록 | 사용자 | 상시 | 건드리지 않는다 |

기반 게임 데이터는 정보 조회 화면과 추천 엔진이 **함께 읽는 토대**다(`docs/00-product.md` 4절).
특정 소비자가 소유하지 않으며, 전체 재생성(5절 원칙 2)의 대상도 이 층에 한정된다.

## 5. 원칙

1. **조용한 누락을 금지한다.** 매핑되지 않은 입력(미분류 토큰, 대응 없는 id, 정제 실패 값)은
   버리지 않고 리포트한다. 로케일별 토큰(한국어 119종 · 영어 123종) 중 하나라도 표에 없으면
   그 사실이 출력에 드러나야 한다.
   변환이 조용히 성공하는 것보다 시끄럽게 실패하는 편이 낫다.
2. **전체를 재생성한다.** 증분 갱신을 하지 않는다. 산출물이 작아(raw 9.4 MB) 전체 재생성이 저렴하고,
   증분은 스냅샷 간 일관성을 깨뜨릴 여지를 만든다.
3. **멱등하다.** 같은 입력으로 여러 번 돌려도 같은 결과가 나온다. 실행 시각이나 순서에 의존하지 않는다.
4. **정제 규칙을 한 곳에 모은다.** 토큰 치환표와 마크업 규칙이 여러 파일에 흩어지면
   패치 때 갱신 지점을 놓친다.
5. **원본을 수정하지 않는다.** `data/`는 읽기 전용으로 다룬다.

## 6. 검증

변환과 적재를 서로 다른 수단으로 검사한다.

| 단계 | 검사 |
| --- | --- |
| 변환 후 | 엔티티·관계별 행 수를 `data/coverage.json`의 대조 수치와 맞춘다 |
| 변환 후 | 미분류 입력 리포트가 비어 있는지 확인한다 |
| 적재 후 | 외래 키로 12,512행의 참조 무결성을 검사한다 |
| 적재 후 | 테이블별 행 수가 JSON과 일치하는지 확인한다 |

검증 결과는 커밋한다. 산출물 자체는 커밋하지 않는다(`01-data-storage.md` 6절).

## 7. 결과

**얻는 것**

- 스키마 정의가 한 벌이며 소비 측 전체가 같은 타입을 본다.
- 데이터베이스에 도구 흔적이 남지 않는다.
- 변환 실패와 적재 실패가 분리되어 진단된다.

**감수하는 것**

- Node.js 실행 환경과 PostgreSQL 인스턴스가 개발 환경에 필요하다.
- 마이그레이션 이력이 없으므로 스키마 변경 시 재생성이 전제된다.
- **스키마의 정본이 TypeScript가 아니라 전용 문법(`schema.prisma`)이다.** 타입은 생성 클라이언트로 따라오지만
  스키마 파일 자체는 다른 코드와 같은 방식으로 다룰 수 없고, DDL과도 1:1로 대응하지 않는다.
- 미분류 입력을 리포트하는 만큼, 패치 때마다 표를 갱신하는 수작업이 생긴다.
- **재현이 상류 저장소의 존속에 의존한다.** 산출물을 커밋하지 않으므로 데이터베이스를 다시 만들려면
  `data/manifest.json`의 커밋 해시로 원본을 재수집해야 한다. 상류가 중단되면 이 경로가 끊기며,
  현재는 로컬 `data/`가 사실상 유일한 사본이다. 대체 경로는 `docs/01-data-source.md` 8절의 미결로 남아 있다.

## 8. 재검토 시점

- 런 기록 테이블이 들어올 때 — 사용자 데이터는 재생성할 수 없으므로 마이그레이션 관리 방식을 다시 정한다.
- 미분류 입력 리포트가 패치마다 커질 때 — 수동 표 갱신이 감당되는지 판단한다.
- 원본 수집이 자동화될 때 — 수집과 변환을 한 파이프라인으로 합칠지 본다.
