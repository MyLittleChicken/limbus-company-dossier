# ADR-03. 다국어 표시 문자열 (Localized Text)

> 상태: 채택 / 결정일 2026-07-26
> 이름·설명 같은 **표시 문자열을 어떤 구조로 저장하고 어느 언어까지 담는가**를 정한다.
> 저장 형식은 `01-data-storage.md`, 변환 방식은 `02-pipeline.md`에서 정했다.
> 이 문서의 수치는 2026-07-25 스냅샷을 직접 측정한 값이다.
>
> **범위** — 이 문서는 현행 `public` 스키마의 결정이다. 신규 3스키마는 로케일이 **ko · en · ja** 셋이다 → [`06-three-schema-database.md`](06-three-schema-database.md).

## 1. 맥락

림버스 컴퍼니는 한국 게임이므로 한국어가 원문이다. 번역이 아니라 정본을 사용한다
(`docs/01-data-source.md` 5절). 세 언어가 모두 확보되어 있으나 구조를 정하지 않으면 담을 수 없다.

| 항목 | 실측 |
| --- | --- |
| 기프트 텍스트 (강화 단계 포함 673건) — 한국어 | 242 KB |
| 〃 영어 | 221 KB |
| 〃 일본어 | 253 KB |
| 설명문의 내부 토큰 | 119종 / 1,513회 |
| 치환표 표제어 | 1,785종 (`BattleKeywords` 1,409 + `Bufs` 1,496 + 거울 던전 `Bufs` 261 병합) |
| 치환 커버리지 (기프트 한국어 설명문) | 종 100% · 출현 100% |
| 한국어 결손 | 소속 태그 7/93 · 스킬 이름 3종 8행 · 코인 설명 3종 18행 · 상태 이름 자리표시자 7종 |

**소속 결손 정정 (2026-07-27).** 이 표는 소속 태그의 한국어 결손을 12/93으로 적고 있었다.
변환기가 `associations.json`(64종) 위에 로케일 파일의 `UnitKeyword` 대응쌍을 얹어 채우므로
**최종 산출의 결손은 7/93이다.** 12종은 그 보강이 붙기 전의 값이며, 현재 수치는
`npm run convert` 리포트의 확인 항목에서 재현된다. 2절의 결정은 영향을 받지 않는다.

기프트 하나만 봐도 세 언어를 다 담으면 716 KB다. 즉 **언어 범위가 산출물 크기를 좌우하는
가장 큰 변수**다. 구현 후 실측이 이를 확인한다 — 두 언어만 담은 산출물에서 표시 문자열
테이블이 7,498 KB, 나머지 전부가 1,959 KB로 **전체의 79%가 표시 문자열**이다.

## 2. 결정

| 항목 | 결정 |
| --- | --- |
| 저장 구조 | **로케일별 행으로 분리한다** |
| 언어 범위 | **한국어 · 영어** |
| 토큰 치환 | **빌드 시점에 치환해 저장한다** |
| 원문 | **치환 전 원문을 함께 저장한다** |
| 폴백 | **한국어가 없으면 영어를 노출한다. 없는 표기를 만들지 않는다** |

구조는 다음 형태다. 컬럼 구성은 예시이며 확정은 구현 시점의 몫이다.

```
gift(id, tier, keyword, attributeType, …)            언어 무관 — 엔티티
gift_text(gift_id, locale, enhance_level,
          name, desc, desc_raw)                      언어별 — 표시 문자열
```

엔티티 테이블에는 언어에 의존하는 값을 두지 않는다.

## 3. 근거

### 3.1 로케일별 행

언어를 늘리는 것이 **행 삽입**으로 끝나고 스키마가 바뀌지 않는다.
컬럼으로 병기하면(`name_ko` · `name_en` · …) 언어를 추가할 때마다 스키마를 고쳐야 하며,
한 언어만 필요한 화면도 전부를 읽게 된다.

`docs/02-data-model.md` 원칙 4가 "표시 문자열을 엔티티에서 분리한다"고 이미 정했고, 행 분리가 그 원칙의 직접적 구현이다.
조인이 한 번 더 붙지만, 이 규모에서 비용으로 볼 값이 아니다.

강화 단계도 이 구조로 흡수된다. 강화 단계는 구조 소스에서 `names[]` 배열이고 로컬라이즈 소스에서는
별도 id(`기본 id + 10000 × 단계`)인데(`02-pipeline.md` 1절), 표시 문자열 테이블에서
`enhance_level`을 키의 일부로 두면 두 표현이 한 곳에서 만난다.

### 3.2 한국어 · 영어

한국어는 정본이므로 당연히 담는다. 영어를 함께 담는 이유는 둘이다.

- **한국어 결손의 폴백이 된다.** 소속 태그 12종과 스킬 3종의 이름·코인 설명은 한국어가 존재하지 않는다.
  영어가 없으면 이 항목들은 표시할 문자열 자체가 없다.
- **상류 데이터·커뮤니티 자료와 대조할 때 쓰인다.** 상류 소스와 팬 자료는 영문 표기를 기준으로 삼는다.

일본어는 지금 소비처가 없어 제외한다. 3.1의 구조 덕분에 나중에 변환기를 다시 돌려 행을 채우면 되며,
스키마 변경이 필요 없다.

### 3.3 빌드 시점 치환

설명문에는 `[Combustion]` 같은 내부 토큰이 119종 1,513회 들어 있다. 이를 치환하지 않으면 읽을 수 없다.

**치환을 빌드 시점에 수행하고 결과를 저장한다.** 런타임 치환은 1,785종 표제어의 치환표를
소비 측에 함께 배포해야 하고, 로케일마다 표가 달라 언어 수만큼 늘어난다.

**대괄호 표기의 어휘는 하나가 아니다.** `[Sinking]` 은 상태이고 `[WhenUse]` 는 발동 시점이다.
상태 표만 쓰면 발동 시점 표기 40종 17,324회가 내부 식별자 그대로 화면에 나간다.
어휘마다 표를 따로 두고, 스킬·코인·패시브 설명문에는 상태 표 위에 발동 시점 표를 얹어 쓴다.

**두 어휘가 같은 열쇠를 다른 뜻으로 쓰는 경우가 있다.** `StartBattle` 은 상태 어휘에서
거울 던전 조우 알림 `전투 발생!` 이지만 스킬 어휘에서는 발동 시점 `[전투 시작시]` 다.
스킬 설명문 안의 표기는 스킬 어휘로 읽는다(`04-source-authority.md` 2.2 — 어휘가 출처를 정한다).
실측 충돌은 이 한 종뿐이다.

**그래도 모든 대괄호가 치환 대상은 아니다.** 두 표를 다 적용하고도 26종 56회가 남는다.
`[Hong Lu]` · `[Rouge]` · `[Cannot Stack]` 처럼 **표기 그대로가 의도인 리터럴**이며
게임의 원문에도 그대로 들어 있다. 결손이 아니므로 원문을 유지하고 리포트에 올린다.

**원문도 함께 저장한다.** `docs/01-data-source.md` 5절이 표시용과 파싱용의 분리를 요구하며,
설명문을 기계적으로 해석할 때는 `침잠`보다 `[Sinking]` 쪽이 매칭이 안정적이다.
원문에는 내부 식별자와 `<noparse>` 마커가 남아 있으므로 표시에는 쓰지 않는다.

## 4. 치환 정책

로케일별로 표를 만들고, 어휘별로 표를 나눈다.

**상태 표** — 모든 설명문에 쓴다.

| 소스 | 표제어 |
| --- | ---: |
| `BattleKeywords*.json` | 1,409 |
| `Bufs*.json` | 1,496 |
| 거울 던전 `Bufs*.json` | 261 |
| 병합 | **1,785** |

**발동 시점 표** — 스킬·코인·패시브 설명문에서 상태 표 위에 얹는다.

| 소스 | 담는 것 | 표제어 |
| --- | --- | ---: |
| `identities/limbus-assets/skill_tags.json` | 어휘 목록과 영문 표기 | 72 |
| `mechanics/limbus-data-mj/terms.json` | 한국어 표기 (보강) | 483 중 47 |

목록 자체가 **무엇이 발동 시점 표기인가**를 정의하므로 정본은 어휘를 가진 쪽이다.
두 소스가 겹치는 39종의 영문 표기를 전수 대조해 불일치 0을 확인했다.
한국어가 없는 표제어는 영문으로 폴백한다(5절). 실제 등장하는 40종 중 해당되는 것은
`TabExplain` 하나이며, 이것은 정본의 표기 자체가 빈 문자열인 UI 표식이다.

**미치환 토큰이 하나라도 남으면 빌드가 이를 리포트한다**(`02-pipeline.md` 원칙 1).
토큰을 조용히 남겨두면 화면에 `[AttackUp]` 같은 날 문자열이 노출된다.
발동 시점 표기는 어휘가 원본에 열거되어 있으므로 **검증기가 잔존 0을 강제한다.**

## 5. 폴백 정책

1. 요청한 로케일의 행이 있으면 그것을 쓴다.
2. 없으면 영어 행을 쓴다.
3. 영어도 없으면 **표시하지 않는다. 문자열을 만들어내지 않는다**(`docs/02-data-model.md` 6절).

폴백이 발생한 항목은 그 사실을 소비 측이 알 수 있어야 한다. 한국어 화면에 영문이 섞이는 것은
결손의 결과이지 설계 의도가 아니다.

**필터·조인 키에는 표시 문자열을 쓰지 않는다.** 소속 태그가 대표적이다 —
키는 원본 영문 태그를 유지하고 표시만 로케일 행에서 가져온다(`docs/02-data-model.md` 3.11).

## 6. 파생 값 저장에 대한 예외

`01-data-storage.md` 제약 4는 파생 값을 저장하지 않는다고 정했다.
치환된 설명문은 원문과 치환표로부터 계산할 수 있으므로 형식상 파생 값이다.

그럼에도 저장하는 이유는 제약 4의 취지가 **중복 저장으로 인한 불일치 방지**에 있기 때문이다.
치환 결과와 원문은 같은 빌드에서 함께 만들어지고 함께 폐기되며, 전체 재생성이 원칙이므로
(`02-pipeline.md` 원칙 2) 둘이 어긋날 경로가 없다. 이 조건이 깨지면 예외도 성립하지 않는다.

## 7. 결과

**얻는 것**

- 언어 추가가 스키마 변경 없이 행 삽입으로 끝난다.
- 표시 문자열이 엔티티에서 분리되어 언어 무관 질의가 텍스트를 읽지 않는다.
- 화면에 내부 토큰이 새어나갈 경로가 없다.

**감수하는 것**

- 표시 문자열을 읽을 때 조인이 한 번 더 붙는다.
- 원문을 함께 저장하므로 텍스트 저장량이 늘어난다.
- 치환표가 소스에 흩어져 있어(3소스 · 130여 파일) 병합 규칙을 유지해야 한다.
- 한국어 화면에 영문이 섞이는 항목이 남는다. 데이터에 없는 값이라 해소할 방법이 없다.

## 8. 재검토 시점

- 일본어 UI를 지원하기로 할 때 — 변환기를 다시 돌려 행을 채운다. 이 ADR의 변경은 필요 없다.
- 미치환 토큰이 0을 넘을 때 — 치환표 병합 규칙을 갱신한다.
- 표시 문자열이 전송량에 부담이 될 때 — 로케일별 분할 배포를 검토한다.
