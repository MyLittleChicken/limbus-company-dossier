# ADR-01. 데이터 저장 형식 (Data Storage Format)

> 상태: 채택 / 결정일 2026-07-26
> 1단계(데이터베이스 구축)의 산출물을 **어떤 형식으로 만들고 어디에 적재하는가**를 정한다.
> 무엇을 저장하는가는 `docs/02-data-model.md`, 원본의 생성 경로는 `docs/03-data-provenance.md`에 있다.
> 이 문서의 수치는 2026-07-25 스냅샷을 직접 측정한 값이며, 측정 대상과 방법은 3절에 있다.

## 1. 맥락

1단계의 대상은 정적 게임 데이터다. `data/`에는 출처별 원본만 있고 정규화 산출물이 없다.
같은 456종 기프트가 출처마다 다른 컨테이너 타입과 다른 필드 집합으로 존재하며, 이를 잇는 계층이 없다.

이 단계에서 필요한 것은 둘이다. **원본을 우리 스키마로 정리하는 것**, 그리고 **정리 결과가 옳음을 검증하는 것**이다.
화면에 어떻게 내보낼지는 이 단계의 문제가 아니다.

## 2. 결정

1단계의 산출물은 **정규화 JSON**이며, 이를 **PostgreSQL에 적재하고 검증하는 것**까지가 이 단계의 범위다.

JSON과 PostgreSQL은 대안 관계가 아니라 한 파이프라인의 두 단계다.

| 단계 | 형식 | 역할 |
| --- | --- | --- |
| 정리 | 정규화 JSON | 원본 → 우리 스키마 변환의 산출물. 사람이 읽고 비교할 수 있는 형태 |
| 적재 | PostgreSQL | 스키마 제약으로 정합성을 강제하고, 이후 런 기록을 함께 수용하는 저장소 |
| 검증 | — | 적재 결과를 `coverage.json`의 대조 수치와 맞춘다 |

**서빙 형식은 이 ADR에서 정하지 않는다.** 정적 배포인지 API인지는 웹페이지 단계의 문제이며,
이 산출물 위에서 따로 결정한다. 계산이 클라이언트에서 도는지 서버에서 도는지도 여기서 전제하지 않는다.

## 3. 측정 결과

결정의 근거는 추정이 아니라 스냅샷 실측이다.

### 3.1 관계의 규모

| 관계 | 행 수 | 출처 |
| --- | ---: | --- |
| 기프트–팩 (전체 풀) | 10,115 | `limbus-data-mj` **단독** |
| 인격–상태 | 1,179 | `limbus-assets` |
| 인격–소속 | 434 | `limbus-assets` |
| 기프트–전용팩 | 321 | `limbus-assets` (양방향 불일치 0) |
| 층–팩 | 288 | `limbus-assets` |
| 합성 재료 | 175 | 양쪽 (재료 쌍 기준 160) |
| **합계** | **12,512** | |

기프트–팩은 기프트당 median 2 · 평균 22.9 · **최대 90**, 팩당 median 73 · **최대 188**이다.
진성 N:M이며 전체 관계 행의 81%를 차지한다.

### 3.2 정규화 산출물의 크기

엔티티 3종(기프트 456 · 인격 184 · 팩 117) · 관계 6종 · 한국어 로케일 3종으로 프로토타입을 만들어 측정했다.
저작층 필드(`effects` / `triggers`)는 제외하고 표시 문자열은 분리했다.

| 구분 | raw | gzip |
| --- | ---: | ---: |
| 엔티티 | 183 KB | 17 KB |
| 관계 | 413 KB | 38 KB |
| 로케일(ko) | 208 KB | 42 KB |
| **합계** | **785 KB** | **96 KB** |

E.G.O · 스킬 · 상태는 아직 정규화하지 않았다(원본 4.5 MB). 전부 포함해도 raw 기준 한 자릿수 MB에 머문다.

### 3.3 관계 그래프의 형상

원본 관계는 **조밀하고 얕다.** 합성 레시피의 최대 홉 깊이는 2이며(레시피 보유 59종 중 51종이 깊이 1,
8종이 깊이 2 — `만 년 동안 끓는 솥` → `요리 비법 전서` → `진혼`), 재료로 쓰이는 132종 중 자신도 합성 결과인 것은 8종뿐이다.
기프트–팩은 홉이 없는 이분 관계다.

**다만 이 측정은 원본 관계에 한한다.** 추천이 순회하게 될 그래프는 원본에 존재하지 않는다.
"어떤 기프트가 어떤 상태를 공급하고, 그 상태가 어떤 상태를 파생시키며, 그 상태가 어떤 기프트를 켜는가"의
경로에서 가변 홉이 걸리는 지점은 **상태 간 파생 관계**다.
이는 원본에서 추출되는 값이 아니라 우리가 저작해야 하는 관계이며, 상태 노드는 10종 남짓이다.

## 4. 근거

**JSON을 중간에 두는 이유**

- 변환 결과를 사람이 검토할 수 있다. `docs/02-data-model.md`가 규정한 함정(동기화 델타 병합, 코인 수 상한 없음,
  스포일러 마크업 정제)이 제대로 처리됐는지는 값을 눈으로 봐야 판단할 수 있다.
- 스냅샷 간 비교가 텍스트 비교로 끝난다. 인격 수가 183에서 184로 바뀌는 변화는 실제로 관측되었다
  (`docs/03-data-provenance.md` 6절 위험 2).
- 적재 실패 시 원인이 변환에 있는지 적재에 있는지 분리된다.

**PostgreSQL을 적재 대상으로 삼는 이유**

- **런 기록을 서버로 수집하기로 결정했다.** 정적 파일로는 수용할 수 없으므로 DB는 선택이 아니라 확정이다.
  게임 데이터와 런 기록이 같은 저장소에 있어야 "추천을 따른 런의 결과"를 조인할 수 있다.
- 스키마 제약이 검증을 대신한다. 외래 키가 12,512개 관계 행의 참조 무결성을 강제하고,
  `NOT NULL`과 `UNIQUE`가 변환기의 누락을 적재 시점에 실패로 드러낸다. JSON만으로는 별도 검사기를 써야 한다.
- 이후 단계의 질의가 조인 중심이다. 기프트–팩–층을 잇는 질의가 추천의 핵심 입력이다.

**그래프 DB를 지금 도입하지 않는 이유**

- 원본 관계는 조밀하고 얕다(3.3). 전체 행의 81%가 단일 이분 관계에 몰려 있고 순회 깊이가 2이므로,
  이 부분에서 관계형이 불리하지 않다. 깊이 2는 조인 두 번이며 재귀 CTE조차 필요 없다.
- 순회가 실제로 필요한 것은 상태 파생 관계의 전파 범위인데(3.3), 이는 **원본 데이터가 아니라 저작 대상**이고
  상태 노드가 10종 남짓이다. 이 규모의 전파는 인메모리 계산으로 끝난다.
- PostgreSQL을 진실의 원천으로 두면 그래프는 **재생성 가능한 파생 저장소**가 된다.
  원천이 정규화되어 있으면 언제든 만들 수 있으므로, 지금 도입하지 않아도 잃는 것이 없다.

상태 파생 관계는 3단계(`docs/06-recommendation-engine.md`)의 저작 대상이며 1단계 산출물에 포함되지 않는다.
따라서 그래프 도입 판단도 그 시점으로 미룬다.

## 5. 산출물의 제약

1. **JSON 파일 하나가 테이블 하나에 대응한다.** 적재가 자명해지고, 행 수 대조만으로 1차 검증이 끝난다.
2. **참조는 언제나 원본 게임 id로 한다**(`docs/02-data-model.md` 원칙 3). 객체 임베딩으로 관계를 대신하지 않는다.
3. **N:M 관계는 독립된 관계 파일·테이블로 표현한다.** 기프트–팩은 기프트당 최대 90 · 팩당 최대 188이라
   어느 한쪽의 배열 필드로 두면 양방향 중복 저장이 된다.
4. **파생 값을 저장하지 않는다**(원칙 2).
5. **데이터셋에 기준 게임 버전을 스탬프로 남긴다**(원칙 5). 버전이 다른 데이터를 섞지 않는다.

## 6. 저장소 커밋 정책

정규화 JSON은 추출 파생 데이터이므로 **저장소에 커밋하지 않는다**(`docs/01-data-source.md` 7절).
`data/`와 동일하게 취급하며, 대신 다음을 추적한다.

| 대상 | 추적 |
| --- | --- |
| 변환 스크립트와 스키마 정의 | 커밋한다 |
| PostgreSQL DDL | 커밋한다 |
| 검증 결과(테이블별 행 수, 무결성 검사 결과) | 커밋한다 |
| 정규화 JSON 산출물 자체 | 커밋하지 않는다 |

`manifest.json` · `coverage.json`이 원본에 대해 하는 역할을 산출물에 대해서도 동일하게 둔다.

## 7. 출처 표기

**필드 단위 출처를 산출물에 남기지 않는다.**

`docs/03-data-provenance.md` 6절 위험 3은 추출층과 저작층의 구분을 데이터 구조에 반영할 것을 요구했다.
이 ADR은 그 요구를 다음 근거로 대체한다.

- 정보 제공에 저작층을 쓰지 않기로 이미 정했다(`docs/03-data-provenance.md` 4절). 산출물에 저작층이 들어가지 않으므로
  구분해야 할 두 층이 애초에 공존하지 않는다.
- 출처 이력은 `manifest.json`과 `docs/04-data-inventory.md`에 남아 있어 추적 가능성을 잃지 않는다.

다만 3.1이 드러낸 사실 하나는 문서로 남긴다 — **기프트–팩 전체 풀 10,115행의 출처는 `limbus-data-mj` 단독이며
대조할 다른 출처가 없다.** `docs/04-data-inventory.md`가 보고한 "기프트↔팩 양방향 불일치 0"은 전용 관계 321행에 대한 것이지
전체 풀에 대한 것이 아니다. 이 관계는 추천의 핵심 입력이면서 교차 검증되지 않은 유일한 대형 관계다.

## 8. 결과

**얻는 것**

- 변환의 정확성과 적재의 정합성을 서로 다른 수단으로 이중 검증한다.
- 런 기록이 들어올 때 저장소를 바꾸지 않아도 된다.
- 서빙 형식 결정을 미뤄도 1단계가 진행된다.

**감수하는 것**

- 파이프라인이 2단계가 되어 변환기와 적재기를 모두 유지해야 한다.
- 개발·검증 환경에 PostgreSQL 인스턴스가 필요하다.
- 산출물을 커밋하지 않으므로 스냅샷 간 비교는 로컬 작업이며, 저장소에는 검증 결과만 남는다.

## 9. 재검토 시점

- 상태 파생 관계를 저작한 뒤 그 규모가 커지거나 전파 계산이 병목이 될 때 —
  그래프를 파생 저장소로 승격할지 별도 ADR로 판단한다. 원천이 PostgreSQL이므로 언제 도입해도 재생성으로 끝난다.
- 서빙 형식을 정할 때 — 클라이언트 직접 조회가 필요해지면 읽기 전용 산출물을 따로 만들지 결정한다.
- 데이터 갱신이 자동 파이프라인으로 바뀔 때 — JSON 중간 단계의 존치 여부를 다시 본다.
