# 디자인 시스템 프로토타입

> 기준 저장소 `main` (`ff913f7`) · 데이터 스냅샷 MD7 / 2026-07-25

`app/` 과 `components/` 를 건드리지 않고 시각 설계를 세우기 위한 별도 작업 공간이다.
`app/globals.css` 첫 주석이 "여기 있는 색·타이포는 배치를 보기 위한 중립 값이며 디자인 단계에서
교체한다"고 남겨 둔 것을 이행한 결과물이며, 되돌려 옮기는 것을 전제로 만들었다.

## 1. 여는 법

`index.html` 을 브라우저로 직접 연다. 빌드 도구도 서버도 필요하지 않다.

```
publish/index.html
```

`publish/assets` 는 `data/assets` 로 향하는 디렉터리 접합이다. 애셋은 저장소에 없으므로
(`.gitignore`) 클론 직후에는 이미지가 비며, `npm run fetch -- --assets` 로 받은 뒤에 보인다.

서체는 Google Fonts 를 `@import` 한다. 오프라인에서는 시스템 서체로 물러선다 —
**배포 시에는 자체 호스팅으로 바꾼다.**

## 2. 구성

| 경로 | 내용 |
| --- | --- |
| `index.html` | 토큰 카탈로그와 화면 목록. 여기서 시작한다 |
| `css/tokens.css` | **토큰 정본.** 색·타이포·간격·중단점. 다른 산출물과 값이 어긋나면 이 파일이 기준이다 |
| `css/globals.css` | 컴포넌트 계층. 클래스 153 종. 구획 순서를 `app/globals.css` 와 맞췄다 |
| `css/proto-doc.css` | 카탈로그 페이지 전용 가구. **제품으로 옮기지 않는다.** 클래스에 `doc-` 접두어를 붙여 갈라 두었다 |
| `js/proto.js` | 축 색 훅 · 표기 교정 · 팩 카드 합성 · 정적 화면의 상태 전환 |
| `js/pack-names.js` | 팩 이름 글자 색 48 종과 보스 그림 맞춤 40 종. **측정으로 생성한 데이터**이며 근거는 [`PACK-ART.md`](PACK-ART.md) 5 절. 규칙으로 짝을 못 찾는 7 종의 예외 표는 `js/proto.js` 에 있다 |
| `screens/*.html` | 화면 27 종 |
| `tools/` | 측정·캡처·검증 스크립트. 재생성 순서는 그 폴더의 `README.md` |
| `assets` | `../data/assets` 로의 접합 |

전체를 한눈에 훑는 컨택트 시트가 필요하면 `node publish/tools/review-sheet.mjs` 로 만든다.
**산출물을 남겨 두지 않는다** — 화면이 바뀌면 곧 낡고, 실제 화면을 직접 열면 되기 때문이다.

## 3. 화면이 만들어진 방식

**마크업을 손으로 옮기지 않았다.** 실행 중인 앱의 DOM 을 헤드리스 Chrome 으로 CDP 를 통해
가져와 Next 런타임만 걷어내고 정적 파일로 만든 것이다. 클래스명과 구조가 보존되므로 되돌려
옮기는 일이 스타일시트 교체로 끝난다.

떠 오면서 바꾼 것은 넷뿐이다.

1. `<script>` · `<template>` · Next 개발 도구 오버레이 제거
2. `<head>` 재구성 — 스타일시트 링크를 이 프로토타입 것으로 교체
3. 애셋 경로를 상대 경로로 (`/assets/…` → `../assets/…`)
4. 내부 링크를 프로토타입 파일명으로 (`/ko/gifts` → `gifts.html`)

접힌 `<details>` 는 전부 펼친 상태로 떠 왔다. 접힌 안쪽도 스타일 대상이기 때문이다.

**떠 온 뒤에 고친 것이 둘 있다 — 상단 nav 와 필터 축이다.** 둘 다 제품에 아직 반영되지
않았으므로 재덤프하면 사라진다. 손으로 되돌리는 대신 `tools/patch-screens.mjs` 에 모아 두었다.

```
node publish/tools/publish-dump.mjs
node publish/tools/patch-screens.mjs      ← 덤프 뒤에 반드시 돌린다
```

여러 번 돌려도 결과가 같다. 무엇을 고치는지는 4.2 (7)·(8) 에 있고, 제품이 따라오면 그
항목과 함께 이 파일에서 지운다.

`screens/states.html` 만 예외로 **손으로 썼다.** 결손·부재·폴백처럼 특정 데이터에서만
렌더되는 여덟 클래스가 덤프로 잡히지 않았기 때문이며, 구조는 실제 컴포넌트에 맞췄으나
제품과 대조해 확인해야 하는 유일한 페이지다.

### 3.1 거울 던전 트래커 넷은 생성한다

`dungeon.html` · `dungeon-run.html` · `dungeon-floor.html` · `dungeon-gifts.html` 은
**떠 올 곳이 없다.** 제품의
`/dungeon` 은 시즌 정보 조회 화면이고 트래커는 아직 없기 때문이다. `tools/make-dungeon.mjs`
가 만든다.

```
node publish/tools/make-dungeon.mjs
```

**값을 지어내지 않는다.** 화면에 들어가는 것을 전부 기존 화면에서 뽑는다.

| 무엇 | 어디서 | 실측 |
| --- | --- | --- |
| 층별 후보 팩과 봉지 그림 | `screens/floors.html` | hard 3층 **27 종** |
| 점수 · 구성값 · 근거 | `screens/recommend.html` | 엔진이 낸 **상위 5** |
| 기프트 풀 | `screens/pack-boss.html` | 억눌린 분노 **63 종**(전용 0) |
| 덱 | `screens/squad.html` | 캡처 표본 12/12 · 출전 7 |

**나머지 22 팩의 점수는 비어 있다.** 추천 슬라이스가 상위 다섯만 인쇄했기 때문이며 0 이
아니다. 화면이 그 사실을 적는다. 채우려면 엔진을 27 종에 대해 돌려야 한다.

층 이력의 획득 기프트는 **공용 풀에서 가져온다.** 공용 기프트는 팩을 가리지 않으므로 어느
층에 놓아도 데이터와 어긋나지 않는다. 팩 한정 기프트를 쓰려면 그 팩의 기프트 목록이
필요한데 프로토타입에는 억눌린 분노 것뿐이다.

**팩을 고르는 것과 층을 도는 것은 다른 마디다.** 게임에서 팩 선택은 층을 여는 일이고,
기프트는 그 뒤 전투·상점·이벤트에서 여러 번 나뉘어 들어온다. 그래서 화면을 둘로 갈랐다 —
`dungeon-run` 이 고르는 자리, `dungeon-floor` 가 도는 자리이며 「기프트 추가」는 한 번 쓰고
닫히는 버튼이 아니라 층이 끝날 때까지 계속 열리는 자리다.

`docs/07-recommendation-system.md` 5.2 는 이 마디를 접어 두었다 —
`[이 팩 선택] → 획득 기프트 모달 → 층 +1` 로 적혀 있다. **문서 쪽에 마디가 빠져 있다.**

정적 파일이지만 **흐름은 걸어볼 수 있다** — 입장 → 팩 고르기 → 층 진행 중 → 기프트 추가 →
층 종료가 서로 이어져 있고 층 종료는 다시 팩 고르기로 돌아온다.

## 4. 되돌려 옮기는 법

### 4.1 스타일

`css/tokens.css` 를 새 파일로 두고, `css/globals.css` 의 내용으로 `app/globals.css` 를 갈아
끼운다. 구획 순서가 같으므로 구획끼리 대조할 수 있다. `css/proto-doc.css` 는 옮기지 않는다.

`app/layout.tsx` 가 `globals.css` 만 불러오고 있으므로 토큰 파일을 그 앞에 하나 더 넣거나,
`globals.css` 맨 위에서 `@import` 한다.

### 4.2 컴포넌트 변경이 필요한 항목

스타일 교체로 끝나지 않는 것들이다.

**(1) 축 색 훅** — 죄악·상태 키워드를 식별하는 속성이 마크업에 없다. 프로토타입은
`js/proto.js` 가 아이콘 파일명에서 유도해 `data-sin` · `data-kw` · `data-atk` 를 붙인다.
제품에서는 서버 렌더가 같은 속성을 내면 되고 그러면 이 JS 는 버린다. **구조 변경이 아니라
속성 하나다.** 이것이 없으면 죄악 7 행이 다시 모두 같은 색이 된다.

**(2) 원본 enum 노출** — `components/uptie-skills.tsx` 가 `{skill.defType}` ·
`{skill.affinity}` · `{skill.atkType}` 를 그대로 출력해 화면에 `attack` · `pride` ·
`slash` 가 나온다. `00-product.md` 3 절의 "표기는 게임 내 표기와 1:1 로 대응한다"에 걸린다.
한국어 라벨 맵은 이미 있다 — `lib/queries/squad.ts` 의 `listSquadAxes` 가 돌려주는 `labels`
이며 편성 화면은 그것을 쓰는데 상세 화면만 쓰지 않는다. 프로토타입은 보여주기 위해 JS 로
덮어썼으나 **고칠 자리는 컴포넌트다.**

**(3) 표기를 모르는 축** — 아래는 게임 표기를 확보하지 못했다. **지어내지 않았다**(5.1).

| 대상 | 현재 노출 |
| --- | --- |
| 팩 분류 | `canto` · `event` · `extreme` · `keyword` · `railway` · `sin` · `walpurgis` · `attack_type` |
| 코인 구분 | `normal` |
| 패시브 조건 | `조건 (owned): pride 4` — 엔진 DSL 이 그대로 나온다 |

앞의 둘은 데이터에서 표기를 확보하는 것이 선행 작업이고, 셋째는 라벨 교체가 아니라 DSL 을
읽는 렌더러가 필요하다.

**(4) 팩 그림 두 층 렌더** — `<Icon>` 하나로는 표현할 수 없다. 팩 그림은 봉지와 보스 두 장을
겹치는 구조이므로(6 절 2-1) `pack.icon` 과 `pack.bossIcon` 을 함께 받는 자리가 필요하다.
목록 화면(`app/[locale]/packs/page.tsx`)은 현재 `pack.icon` 만 받고 있어 쿼리도 함께 늘려야 한다.
프로토타입은 파일명 규칙(`{sprite}_boss.webp`)으로 짝을 찾아 실제로 불러 본 뒤 넣는다.

새로 쓴 클래스는 셋이며 원본 148 종에 더해지는 것이다 — `.packart` · `.packart-boss` ·
`.packart-gloss`.

**(5) 공격 타입 팩의 스프라이트** — 아래 데이터 문제다. 프로토타입은 위키 대조로 확정한
매핑 표를 `js/proto.js` 에 두어 그림은 나오게 했으나, **표가 있어야 한다는 사실 자체가
데이터 문제다.** 조사 전문은 [`PACK-ART.md`](PACK-ART.md) 3.1 에 있다.

`attack_type` 팩 6 종이 스프라이트를 범용 두 개로 공유한다.

| id | 이름 | sprite |
| --- | --- | --- |
| 1201 | 가르고 베는 이들 | `AttackType_normal` |
| 1203 | 꿰고 뚫는 이들 | `AttackType_normal` |
| 1205 | 부수고 깨뜨릴 이들 | `AttackType_normal` |
| 1202 | 베어낼 것 | `AttackType_effective` |
| 1204 | 꿰뚫을 것 | `AttackType_effective` |
| 1206 | 바스라질 것 | `AttackType_effective` |

`chapter` 와 `variant` 가 모두 `null` 이라 **참격·관통·타격을 가리는 필드가 없다.** 그래서
셋이 같은 빈 봉지로 렌더된다.

특정 아트는 애셋에 있다 — `AttackTypeSlash_hard_boss` · `AttackTypePierce_hard_boss` ·
`AttackTypeBlunt_hard_boss` 와 각각의 `_effective_boss`, 여섯 장이다. 그런데 DB 의 스프라이트
키로는 닿지 않고, **난이도 축도 맞지 않는다** — DB 는 `_normal` · `_effective` 인데 애셋은
`_hard` · `_effective` 다. `_normal` 팩 셋에는 대응하는 아트가 아예 없다.

**추측하지 않고 위키 카드 이미지와 로컬 애셋을 그림 단위로 대조해 확정했다** — 세 공격 타입
모두 직접 맞췄고 `_normal` 팩이 `_hard` 그림을 쓴다는 것도 그로써 확인됐다. 대조 표와 근거는
[`PACK-ART.md`](PACK-ART.md) 3.1 에 있다.

**파이프라인에서 공격 타입을 필드로 담거나 스프라이트를 교정하는 것이 근본 해결이다.**
프로토타입의 표는 팩 이름을 키로 잡는데, 제품에서는 팩 id 로 잡아야 한다.

**(5-1) 보스 그림은 층 단위다** — 1302 해방된 분노(`Crimson_hard`)는 상류에 `_hard_boss` 가
없어 비어 있었다. 인게임 HARD 5 층 화면에서 `해방된 분노` 와 `화왕지절`(`Burn_hard`)이 나란히
나오며 **같은 보스 그림**을 쓴다 — 보스 그림이 팩 테마가 아니라 **그 층의 보스**에 딸린다는
뜻이다. 없는 파일을 지어내지 않고 같은 보스의 파일을 가리켜 채웠고, 합성이 41 종이 되었다.

**함의가 있다.** `{sprite}_boss` 라는 파일명 규칙은 우연한 대응이다. 파이프라인이 팩–층–보스
관계로 애셋을 잇는 편이 옳고, 그러면 예외 표가 필요하지 않다.

**(5-2) 팩 이름 텍스트** — 게임은 카드에 이름을 **그려 넣는다.** 애셋이 아니다.
위키 완성 카드 113 장을 전수 확인해 **전 계열에 인쇄된다**는 것을 밝혔고(구워진 「CANTO I」·
「LINE 1 MADNESS」·「MirrorClock OrangeRoad」는 배경 아트이거나 로고이며 팩 이름이 아니다),
**117 종 전부에 인쇄했다.** 카드 형식이 둘이라 띠 위치가 다르고 파일명(`_Extreme` 접미)으로
갈린다 — 봉지 97 종은 74%~90%, 극한 20 종은 84%~99% 다. 자세한 근거는
[`PACK-ART.md`](PACK-ART.md) 5 절.

서체는 게임의 KOTRA Bold 가 아니다. 공공누리 제1유형이지만 **재배포가 금지**되어 웹폰트로 쓸 수
없다. 게임과 글자 모양이 다른 것은 결함이 아니라 라이선스 준수의 결과다.

**(6) 서체 자체 호스팅** — 지금은 두 곳에서 `@import` 한다. Google Fonts 에서 Chakra Petch ·
Bebas Neue 를, jsDelivr 에서 Pretendard 를 받는다. 셋 다 OFL 이라 자체 호스팅에 걸리는 것이
없으며, 배포 시에는 옮긴다.

**게임의 네 서체 중 둘은 같은 것을 쓴다** — 본문 Pretendard 와 숫자 Bebas Neue 다(BebasKai 의
원형). 타이틀의 KOTRA Bold 는 재배포가 금지되어 대체하며, 그것은 선택이 아니라 제약이다.
자세한 근거는 [`PACK-ART.md`](PACK-ART.md) 5.2.1.

**(7) nav 구성** — 프로토타입의 nav 가 제품과 다르다. 정본은 `lib/ui-text.ts` 의
`NAV_PRIMARY` · `NAV_SECONDARY` 이며 `app/[locale]/page.tsx` 의 홈 진입 카드도 그것을 읽는다.

| | 제품 (`lib/ui-text.ts`) | 프로토타입 |
| --- | --- | --- |
| 앞 갈래 | 기프트 · 팩 · 인격 · E.G.O | **인격 · E.G.O · 기프트 · 팩** |
| 뒤 갈래 | 편성 · 추천 · 층별 · 던전 · 용어 | **편성 · 던전** |

앞 갈래는 순서만 바꾼 것이다 — 인격과 E.G.O 가 게임의 1차 축이고 기프트·팩은 거울 던전
안쪽 개념이므로 바깥에서 안쪽으로 읽히게 세웠다.

뒤 갈래에서 셋을 내렸다. **층별 등장 팩과 추천은 거울 던전의 추천 기능으로 통합되어
덱 트래킹을 맡을 예정**이므로 독립 탭으로 둘 자리가 아니고, 용어는 노출하지 않기로 했다.
**화면 파일은 지우지 않았다** — `index.html` 하단에 따로 묶어 두었으며 통합 설계 때 참조한다.

**(8) 필터 축** — 목록 화면의 축 구성과 칩 모양이 제품과 다르다. 자리는
`app/[locale]/{identities,egos,gifts}/page.tsx` 와 `components/filters.tsx` 다.

| 화면 | 제품 | 프로토타입 |
| --- | --- | --- |
| 인격 | 수감자 · 등급 · 스킬 죄악 · 소속 | 등급과 죄악을 **엠블럼만**으로, **키워드 7 · 특수 2 축을 더한다** |
| E.G.O | 수감자 · 등급 · 각성 죄악 · (침식 있음 · 추출 가능) | 죄악을 엠블럼만으로, **키워드 7 을 더하고** 뒤의 둘을 내린다 |
| 기프트 | 등급 · 키워드 · 풀 · (강화 가능 · hard 전용) | 뒤의 둘을 내린다 |

**글자에서 엠블럼으로 옮긴다.** 게임이 죄악과 등급을 그림으로 다루고, 칩 일곱여덟 개가
글자로 늘어서면 목록보다 필터가 무거워진다. 이름은 버리지 않고 `aria-label` 로 남기므로
읽어 주는 쪽에는 그대로 들린다 — **`components/filters.tsx` 의 `ChipFilter` 가 아이콘만
내는 갈래를 갖고 그때 `aria-label` 을 붙여야 한다.** 지금은 `{o.label}` 을 늘 출력한다.

E.G.O 등급은 글자를 남긴다. `ZAYIN` · `TETH` 는 엠블럼만으로 읽히지 않는 이름이고, 인격의
`0` · `00` · `000` 과 달리 글자 자체가 등급 표기다.

더하는 두 축은 데이터가 이미 있다 — `lib/queries/squad.ts` 의 `listSquadAxes` 가 키워드와
특수(탄환 · 보호)를 라벨·아이콘과 함께 돌려주며 편성 프로필이 그것을 쓴다. 목록 화면이
쓰지 않을 뿐이다. **탄환과 보호는 아이콘이 없는 것이 정상이고**(공용 아이콘 목록에 없다)
그래서 글자로 낸다.

내린 넷은 성격이 같다 — 침식 있음 · 추출 가능 · 강화 가능 · hard 전용은 무엇을 고르는
축이 아니라 소지·해금 상태다. 축이 아닌 것이 축 자리에 있었다.

## 5. 지킨 제약

`docs/05-ui-foundation.md` 8 절과 `docs/00-product.md` 3 절이 정한 것이다.

| 제약 | 이행 |
| --- | --- |
| 표기를 새로 만들지 않는다 | 죄악·공격 타입·방어 구분은 게임 표기로 교정했고, 표기를 모르는 축은 그대로 두고 4.2 (3) 에 적었다 |
| 밀도가 장식보다 우선한다 | 타이포 아홉 종을 일곱 단으로 접으며 **어느 값도 키우지 않았다.** 간격 계단도 기존 실측값을 그대로 세운 것이다 |
| 색만으로 구분하지 않는다 | 죄악·키워드 색은 항상 아이콘과 이름을 동반한다. 분포 막대에는 수치가, 자원 트랙에는 수요 세로선이 함께 있다. 출전은 색 + 체크박스, 필터 칩은 색 + 좌측 바, 결손은 색 + 점선 밑줄이다 |
| 결손과 부재를 구분한다 | `.missing` · `.absent` · `.fellback` 이 서로 다른 기호를 쓴다. `screens/states.html` 이 셋을 나란히 놓는다 |
| 이미지를 축소해 쓰지 않는다 | 테마 팩 카드를 세로 봉지 카드로 세웠다. 6 절 참조 |
| 모바일을 지원한다 | 중단점 넷. 편성 12 칸이 390px 에서 2 열로 접힌다 |
| 다크 단일 | 라이트 테마를 두지 않았다 |

## 6. 시각 설계에서 바꾼 것

우선순위는 시각 격차 기준이다.

**1. 의미 색축을 만들었다.** 이전에는 색 토큰이 7 개뿐이어서 죄악 7 종이 모두 같은 금색으로
나왔다. 게임 엠블럼 픽셀 실측값으로 죄악 7 색과 상태 키워드 색을 넣었다. 둘은 **다른 축**이며
실측에서 서로 다른 색으로 나오므로 섞지 않는다. 공격 타입 3 종은 게임이 색을 나누지 않고 공용
브론즈로 다루므로 그대로 두었다 — 없는 체계를 만들지 않는다.

**2. 테마 팩 카드를 세웠다.** 애셋이 380 × 690(세로 1:1.8) 인 매달린 포일 팩 아트인데
이전 구현이 `shape="wide"` 로 56 × 34 가로 상자에 넣어 실제로는 19 × 34 로 렌더됐다.
`.cardgrid-wide` 가 팩 목록에만 쓰이므로 **CSS 만으로 고쳤다** — 컴포넌트 변경이 필요하지 않다.

**2-1. 팩 그림 두 장을 합성했다.** 애셋이 한 장이 아니다.

| 애셋 | 실측 | 내용 |
| --- | --- | --- |
| `{sprite}.webp` | 380 × 690 | 가운데가 빈 8각 창을 가진 봉지 |
| `{sprite}_boss.webp` | 391 × 432 | 프레임 없는 투명 그림. **41 종** (4.2 (5-1) 참조) |

게임 내 카드는 8각 창 자리에 보스가 채워져 있고 그 위로 비닐 광택이 지나간다. 봉지만 내면
가운데가 텅 빈 카드가 되어 팩을 식별할 수 없었고, 반대로 상세의 「보스 층」 그림은 봉지 없이
보스만 떠 있었다. 양쪽을 같은 구조로 합쳤다 — 목록 카드 34 종과 상세의 보스 층이 대상이다.

겹치는 위치는 봉지 그림의 8각 창 실측에서 나왔다. 창이 세로 25%~72% 에 있어 중심이 48.5% 이고
보스 그림 높이가 봉지의 62.6%(432/690) 이므로 위를 14% 로 두면 창에 맞는다. 보스 그림이 봉지
실루엣을 넘는 것은 게임도 같아서(가장자리에서 잘린다) `overflow` 로 자른다.

**3. 표면을 웜 차콜로 옮겼다.** 이전 배경 `#14141a` 는 차가운 청회색이라 원작과 반대
방향이었다. 위계도 두 단(`--bg` · `--bg-raised`)뿐이어서 패널이 전부 같은 무게로 보였다.
네 단으로 늘렸다.

**4. 프레이밍을 넣었다.** 패널·카드 우상단을 자르고(컷코너) 얇은 이중 외곽선을 두고 패널
머리에 레드 인덱스탭을 붙였다. 게임의 "관공서 서식" 언어다. 브릭레드는 두 자리에만 쓴다 —
패널 인덱스탭과 조건 초기화.

**5. 타이포를 갈랐다.** 라틴 디스플레이(Chakra Petch)와 국문 본문(Pretendard)을 분리하고,
작은 글자에는 국문 무거운 서체를 쓰지 않는다. 한국어 가독성이 디스플레이 톤보다 우선한다.
국문 얼굴은 제목과 본문이 같은 것을 쓰며 제목의 무게는 굵기와 자간이 만든다.

**6. 질감을 얹었다.** 인쇄 그레인과 방송 스캔라인. `--fx-grain` · `--fx-scanline` 을 0 으로
두면 완전히 꺼진다.
